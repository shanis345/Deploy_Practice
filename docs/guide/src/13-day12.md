# Day 12 — NetworkPolicy로 존 분리, 그리고 OpenShift의 차이

<div class="day-meta"><span><b>소요</b> 3시간</span><span><b>만드는 것</b> Day 6의 3존 구조를 쿠버네티스 정책으로, OpenShift 호환 점검</span><span><b>눈으로</b> k9s (<code>:netpol</code>), 임의 UID 실행 결과</span></div>

!!! why
    Day 6에서 Compose 네트워크로 만든 존 분리를 쿠버네티스에서 구현합니다. 그때 "도커 네트워크는 방향을 모른다"고 했습니다. NetworkPolicy는 **방향(ingress/egress)을 구분**하고, YAML 한 장이 고객사 보안팀에게 "존 분리를 플랫폼 수준에서 강제하고 있으며, 정책은 코드로 관리되고 검증 가능하다"는 증거가 됩니다.

    그리고 국내 대기업에서 가장 많이 만날 **OpenShift**의 차이를 미리 겪습니다. "로컬에서는 잘 되던 이미지가 OpenShift에서는 기동조차 안 된다"는 경험은 거의 통과의례입니다. 원인을 알고 가면 몇 시간 안에 끝나고, 모르면 며칠 걸립니다.

## 핵심 개념

### NetworkPolicy — 기본은 전부 허용

기본적으로 쿠버네티스는 **모든 Pod가 모든 Pod와 통신 가능**합니다. 네임스페이스가 달라도 됩니다. 고객사 보안팀이 반드시 지적하는 부분이고, NetworkPolicy로 제한합니다.

작동 방식의 핵심: **어떤 Pod에 대해 NetworkPolicy가 하나라도 적용되면, 그 방향의 통신은 명시적으로 허용된 것만 통과합니다.** 정책이 하나도 없으면 전부 허용입니다.

```text
[정책 없음]                 모두 허용
[Ingress 정책 있음]         명시된 출발지만 인바운드 허용, 나머지 차단
[Egress 정책 있음]          명시된 목적지만 아웃바운드 허용, 나머지 차단
```

그래서 관용구는 "네임스페이스에 `default-deny`를 걸고, 필요한 것만 허용 규칙을 추가"입니다.

!!! warn
    NetworkPolicy는 **CNI(네트워크 플러그인)가 지원해야** 동작합니다. 지원하지 않는 CNI에서는 정책을 적용해도 **아무 일도 일어나지 않습니다**(오류 없이 조용히 무시). Calico, Cilium, OVN-Kubernetes(OpenShift 기본), Antrea, k3s의 내장 컨트롤러(kube-router)는 지원합니다. 순수 Flannel은 지원하지 않습니다. 고객사에서 반드시 확인하세요:
    ```bash
    kubectl get pods -n kube-system | grep -Ei "calico|cilium|flannel|weave|ovn|antrea|kube-router"
    ```
    그리고 **정책이 실제로 막는지 probe로 검증**하세요. 오늘 실습이 그 검증 절차입니다.

### OpenShift의 차이

| 항목 | 표준 Kubernetes | OpenShift |
|---|---|---|
| 외부 노출 | Ingress | **Route** (Ingress도 지원) |
| 실행 UID | 이미지가 지정한 대로 | **임의의 높은 UID를 강제 할당** (SCC `restricted-v2`) |
| root 실행 | 가능 | 기본 금지 |
| CLI | `kubectl` | `oc` (kubectl도 동작) |
| 프로젝트 | Namespace | Project (Namespace + 부가 정책) |
| 이미지 빌드 | 외부 | 내장 BuildConfig / S2I |
| 레지스트리 | 외부 | 내장 레지스트리 + 외부 |
| 보안 정책 | Pod Security Admission | **SCC** (Security Context Constraints) |
| 웹 콘솔 | 별도 설치 | 내장 |

**두 번째 항목이 가장 많이 문제를 일으킵니다.** OpenShift는 기본 SCC에서 Pod에 임의의 높은 UID(예: 1000680000)를 할당합니다. 그래서 이런 일이 생깁니다.

- Dockerfile에서 `USER 10001`로 지정해도 무시되고 다른 UID로 실행됩니다.
- 그 UID는 `/etc/passwd`에 없으므로 이름이 없고, `HOME`이 `/`가 됩니다.
- 그 UID는 어떤 그룹에도 속하지 않으므로, **GID 0에 쓰기 권한이 없는 디렉터리에는 쓰기가 실패**합니다.
- 애플리케이션이 홈 디렉터리나 캐시 경로(`~/.cache`, HuggingFace 캐시)에 쓰려 하면 기동 실패합니다.

해결은 Day 0부터 우리 이미지에 넣어 둔 두 줄입니다.

```dockerfile
RUN useradd --create-home --uid 10001 --gid 0 appuser \
 && mkdir -p /app/config /app/tmp \
 && chgrp -R 0 /app && chmod -R g=u /app      # ← GID 0에 소유자와 같은 권한
ENV HOME=/app                                 # ← 홈을 쓰기 가능한 곳으로
```

OpenShift가 어떤 UID를 주더라도 **GID는 0**이므로, 그룹 쓰기 권한이 있으면 동작합니다. `PYTHONDONTWRITEBYTECODE=1`도 중요합니다 — 파이썬이 `.pyc`를 쓰려다 권한 오류로 실패하는 경우가 있습니다.

Day 6의 3존 구조를 네임스페이스 세 개로 재현합니다. 존은 네임스페이스의 **라벨**(`zone: dmz|biz|db`)로 표현하고, 정책은 이 라벨을 참조합니다.

### 정책 적용

```yaml
#file: 20-netpol.yaml
# ── DB존: 기본 전부 차단 (인바운드) ─────────────────────────────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: zone-db }
spec:
  podSelector: {}                    # 네임스페이스의 모든 Pod에 적용
  policyTypes: [Ingress]             # 인바운드만. 명시된 허용이 없으므로 전부 차단
---
# ── DB존: 업무망(zone=biz)에서 5432만 허용 ──────────────────────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-biz-to-db, namespace: zone-db }
spec:
  podSelector: { matchLabels: { app: postgres } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { zone: biz } }
      ports:
        - { protocol: TCP, port: 5432 }
---
# ── 업무망: 기본 전부 차단 (인바운드) ────────────────────────────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: zone-biz }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# ── 업무망: 에이전트는 DMZ(zone=dmz)와 Ingress 컨트롤러에서 8000만 허용 ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dmz-to-agent, namespace: zone-biz }
spec:
  podSelector: { matchLabels: { app: agent } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { zone: dmz } }
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }   # Ingress 컨트롤러(traefik/nginx)
      ports:
        - { protocol: TCP, port: 8000 }
---
# ── 업무망: LLM 게이트웨이는 같은 네임스페이스의 에이전트에서만 4000 허용 ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-agent-to-gateway, namespace: zone-biz }
spec:
  podSelector: { matchLabels: { app: llm-gateway } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: agent } }
      ports:
        - { protocol: TCP, port: 4000 }
```

```bash
kubectl apply -f 20-netpol.yaml && sleep 5

echo "① DMZ → DB : 차단되어야"
kubectl -n zone-dmz exec probe -- sh -c 'nc -z -w5 postgres.zone-db.svc.cluster.local 5432 && echo "위험: 열림" || echo "정상: 차단"'
echo "② 업무망 → DB : 허용되어야"
kubectl -n zone-biz exec probe -- sh -c 'nc -z -w5 postgres.zone-db.svc.cluster.local 5432 && echo "정상: 열림" || echo "문제: 차단"'
echo "③ DMZ → 에이전트 : 허용되어야"
kubectl -n zone-dmz exec probe -- sh -c 'curl -s -m5 -o /dev/null -w "%{http_code}\n" http://agent.zone-biz.svc.cluster.local:8000/healthz'
echo "④ DMZ → LLM 게이트웨이 : 차단되어야 (에이전트만 허용)"
kubectl -n zone-dmz exec probe -- sh -c 'curl -s -m5 -o /dev/null -w "%{http_code}\n" http://llm-gateway.zone-biz.svc.cluster.local:4000/ || echo "정상: 차단"'
echo "⑤ 에이전트 → LLM 게이트웨이 : 허용되어야"
kubectl -n zone-biz exec deploy/agent -- python -c "import urllib.request;print(urllib.request.urlopen('http://llm-gateway:4000/',timeout=5).read().decode())"
echo "⑥ DB → 에이전트 (역방향) : 차단되어야 — Day 6에서는 못 막았던 것"
kubectl -n zone-db exec probe -- sh -c 'nc -z -w5 agent.zone-biz.svc.cluster.local 8000 && echo "열림" || echo "정상: 차단"'
```

    ```text

    ② 정상: 열림
    ③ 200
    ④ 000
       정상: 차단
    ```

## 실습 12-2 — 아웃바운드도 막기 (egress)

에이전트가 LLM 게이트웨이와 DB로만 나가게 제한합니다. Day 7의 "아웃바운드를 한 곳으로"를 정책으로 강제하는 것입니다.

```yaml
#file: 21-egress.yaml
# 에이전트의 아웃바운드를 DNS · DB존 · LLM 게이트웨이로만 제한
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: agent-egress, namespace: zone-biz }
spec:
  podSelector: { matchLabels: { app: agent } }
  policyTypes: [Egress]
  egress:
    # DNS는 반드시 허용 — 빼먹으면 이름 해석이 전부 실패한다
    - to:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
    # DB존
    - to:
        - namespaceSelector: { matchLabels: { zone: db } }
      ports:
        - { protocol: TCP, port: 5432 }
    # LLM 게이트웨이 (같은 네임스페이스의 특정 Pod)
    - to:
        - podSelector: { matchLabels: { app: llm-gateway } }
      ports:
        - { protocol: TCP, port: 4000 }
```

```bash
kubectl apply -f 21-egress.yaml && sleep 5
echo "① 에이전트 → LLM 게이트웨이 : 허용"
kubectl -n zone-biz exec deploy/agent -- python -c "import urllib.request;print(urllib.request.urlopen('http://llm-gateway:4000/',timeout=5).read().decode().strip())"
echo "② 에이전트 → DB : 허용"
kubectl -n zone-biz exec deploy/agent -- python -c "import socket;socket.create_connection(('postgres.zone-db.svc.cluster.local',5432),3).close();print('DB OK')"
echo "③ 에이전트 → 인터넷 : 차단"
kubectl -n zone-biz exec deploy/agent -- python -c "
import urllib.request
try: urllib.request.urlopen('http://example.com',timeout=5); print('위험: 열림')
except Exception as e: print('정상: 차단 —', type(e).__name__)"
echo "④ 에이전트 → DMZ 게이트웨이 Pod (역방향) : 차단"
GW=$(kubectl -n zone-dmz get pod -l app=gateway -o jsonpath='{.items[0].status.podIP}')
kubectl -n zone-biz exec deploy/agent -- python -c "
import socket
try: socket.create_connection(('$GW',80),3); print('열림')
except Exception as e: print('정상: 차단 —', type(e).__name__)"
```

!!! expect
    ```text
    ① {"gateway":"ok"}
    ② DB OK
    ③ 정상: 차단 — URLError
    ④ 정상: 차단 — ConnectionRefusedError   (CNI에 따라 timeout 또는 refused)
    ```

가장 흔한 실수를 일부러 만들어 봅니다. **DNS 허용을 빼먹는 것**입니다.

```bash
kubectl -n zone-biz patch networkpolicy agent-egress --type json -p '[{"op":"remove","path":"/spec/egress/0"}]'
sleep 3
kubectl -n zone-biz exec deploy/agent -- python -c "
import socket
try: socket.create_connection(('postgres.zone-db.svc.cluster.local',5432),3); print('DB OK')
except Exception as e: print('실패 —', type(e).__name__, e)"
kubectl apply -f 21-egress.yaml      # 복구
```

!!! fail
    ```text
    실패 — gaierror [Errno -3] Temporary failure in name resolution
    ```
    DB존으로의 5432는 여전히 허용되어 있는데도 실패합니다. 이름을 못 풀기 때문입니다. Egress 정책을 걸면 **증상이 "갑자기 아무것도 안 된다"**로 나타나고, 원인은 DNS(UDP/TCP 53) 규칙 누락입니다. 항상 첫 규칙으로 넣으세요.

!!! verified
    실습 12-1·12-2는 k3s(내장 NetworkPolicy 컨트롤러)에서 실행해 위 출력을 확인했습니다. 차단의 형태(타임아웃 vs refused)는 CNI에 따라 다릅니다.

## 실습 12-3 — OpenShift 제약 흉내내기

OpenShift가 하는 일(임의 UID 할당)을 `--overrides`로 재현해, 우리 이미지가 견디는지 확인합니다.

```bash
# ① 우리 이미지 (chgrp 0 / chmod g=u / HOME=/app 처리됨)
kubectl -n zone-biz run oc-test --rm -i --restart=Never \
  --image=onprem-registry:5000/ax/agent:0.2.0 --image-pull-policy=IfNotPresent \
  --overrides='{"spec":{"securityContext":{"runAsUser":1000680000,"runAsGroup":0,"fsGroup":0}}}' \
  -- python -c "
import os
print('UID:', os.getuid(), 'GID:', os.getgid(), 'HOME:', os.getenv('HOME'))
for p in ['/app/tmp/x', '/app/config/x', '/tmp/x', '/app/x']:
    try: open(p,'w').write('x'); print(p, '쓰기 OK')
    except Exception as e: print(p, '쓰기 실패:', type(e).__name__)"

# ② 준비되지 않은 이미지 (베이스 이미지 그대로)
kubectl -n zone-biz run oc-fail --rm -i --restart=Never \
  --image=python:3.12.14-slim --image-pull-policy=IfNotPresent \
  --overrides='{"spec":{"securityContext":{"runAsUser":1000680000,"runAsGroup":0}}}' \
  -- python -c "
import os
print('UID:', os.getuid(), 'HOME:', os.getenv('HOME'))
for p in ['/root/.cache/x', '/usr/local/lib/x', '/app/x']:
    try: os.makedirs(os.path.dirname(p), exist_ok=True); open(p,'w').write('x'); print(p, '쓰기 OK')
    except Exception as e: print(p, '쓰기 실패:', type(e).__name__)"
```

!!! expect
    ```text
    UID: 1000680000 GID: 0 HOME: /app
    /app/tmp/x 쓰기 OK
    /app/config/x 쓰기 OK
    /tmp/x 쓰기 OK
    /app/x 쓰기 OK
    ```

!!! fail
    ```text
    UID: 1000680000 HOME: /
    /root/.cache/x 쓰기 실패: PermissionError
    /usr/local/lib/x 쓰기 실패: PermissionError
    /app/x 쓰기 실패: PermissionError
    ```
    ②가 OpenShift에서 "기동조차 안 되는" 이미지의 모습입니다. `HOME=/`이고, 어디에도 쓸 수 없습니다. 파이썬 라이브러리가 `~/.cache`에 모델이나 토크나이저를 받으려 하면 여기서 죽습니다. 해결은 위의 `chgrp 0 / chmod g=u` 패턴과 `HOME`·`XDG_CACHE_HOME`·`HF_HOME`을 쓰기 가능한 경로로 지정하는 것입니다.

!!! unverified
    실제 OpenShift(SCC, Route, `oc` CLI)는 세션에 없어 검증하지 못했습니다. 위 재현은 SCC `restricted-v2`가 하는 일 중 **UID 할당** 부분만 흉내 낸 것입니다. 실제 OpenShift는 추가로 capabilities를 전부 제거하고, `seccompProfile: RuntimeDefault`를 요구하며, 이미지의 `USER`가 숫자가 아니면(`USER appuser`처럼 이름이면) 검증에 실패합니다. Day 10의 `securityContext` 블록이 이 요건을 이미 만족합니다.

### OpenShift 배포 전 체크리스트

- [ ] `USER`를 **숫자 UID**로 지정했는가 (이름은 SCC 검증 실패)
- [ ] 쓰기가 필요한 경로에 `chgrp -R 0` / `chmod -R g=u`를 적용했는가
- [ ] `HOME`, `XDG_CACHE_HOME`, `HF_HOME`, `TIKTOKEN_CACHE_DIR` 등을 쓰기 가능한 경로로 지정했는가
- [ ] `PYTHONDONTWRITEBYTECODE=1`을 설정했는가
- [ ] **1024 미만 포트를 쓰지 않는가** (nginx 기본 이미지는 80번 → `nginxinc/nginx-unprivileged` 또는 8080)
- [ ] `hostPath` 볼륨, `privileged`, `hostNetwork`를 쓰지 않는가
- [ ] 임의 UID로 기동 테스트(실습 12-3 ①)를 했는가
- [ ] 외부 노출을 Route로 할지 Ingress로 할지 확인했는가 (Route는 `haproxy.router.openshift.io/timeout: 300s`)
- [ ] 네임스페이스(프로젝트)에 걸린 ResourceQuota·LimitRange에 맞춰 `resources`를 채웠는가
- [ ] NetworkPolicy가 프로젝트 기본으로 걸려 있는지 확인했는가 (OpenShift는 프로젝트 템플릿에 기본 정책이 들어 있는 경우가 많음 — Ingress 컨트롤러 네임스페이스 허용이 빠지면 Route가 503)

!!! note
    1024 미만 포트 바인딩: 도커 런타임(Docker Desktop, 세션 환경)은 컨테이너 안에서 `ip_unprivileged_port_start=0`을 설정해 non-root도 80번에 바인딩됩니다. 그러나 containerd 기반 쿠버네티스와 OpenShift에서는 기본적으로 **실패**합니다. 환경에 따라 다르므로 처음부터 8080 이상을 쓰는 것이 안전합니다. 우리 에이전트는 8000입니다.

## 눈으로 확인 — k9s에서 정책 보기

!!! eye
    `k9s -A`에서 `:netpol`을 치면 모든 네임스페이스의 NetworkPolicy가 보이고, 하나를 골라 `d`를 누르면 **어느 Pod에 적용되는지(Pod selector)와 허용 규칙**이 정리되어 나옵니다. `:ns`에서 네임스페이스의 라벨(`zone=biz`)을 확인하는 것도 잊지 마세요 — 정책은 라벨을 참조하므로 라벨이 빠지면 조용히 아무것도 허용되지 않습니다.

## 오류 대응

!!! rollback
    - 정책을 적용했는데 아무것도 안 막힘 → CNI가 NetworkPolicy를 지원하지 않음. k3d/k3s는 지원. 고객사에서는 플랫폼팀에 확인.
    - 정책 적용 후 **전부** 안 됨 → egress 정책에서 DNS 누락 (실습 12-2의 의도된 실패).
    - Ingress(외부 진입)가 503 → `allow-dmz-to-agent`에 Ingress 컨트롤러 네임스페이스 허용이 빠짐. 컨트롤러가 어느 네임스페이스에 있는지(`ingress-nginx`, `openshift-ingress` 등) 확인해 `namespaceSelector` 추가.
    - `namespaceSelector`가 안 먹음 → 네임스페이스에 라벨이 없음. `kubectl get ns --show-labels`.
    - `oc-test`가 `already exists` → `kubectl -n zone-biz delete pod oc-test --force`.
