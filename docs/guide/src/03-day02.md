# Day 2 — 리눅스 네트워크 기초: 네임스페이스·브리지·라우팅·DNS

<div class="day-meta"><span><b>소요</b> 2~3시간</span><span><b>만드는 것</b> 도커 없이 손으로 만든 "컨테이너 네트워크"</span><span><b>눈으로</b> <code>ip</code>, <code>bridge</code>, <code>tcpdump</code>로 패킷이 지나는 길</span></div>

!!! why
    고객사에서 "컨테이너에서 DB가 안 붙어요"라는 말을 들었을 때, 인프라 담당자는 이렇게 되묻습니다.

    > "컨테이너 IP 대역이 뭐예요? 브리지에서 NAT 타고 나가는 거죠? 그러면 방화벽엔 VM IP로 보일 텐데, DB존 정책은 VM IP로 열어 놨거든요. 그런데 안 된다고요?"

    이 대화를 따라가려면 도커가 뒤에서 하는 일 — 네임스페이스를 만들고, 가상 랜선(veth)을 꽂고, 브리지에 연결하고, NAT 규칙을 넣는 것 — 을 한 번은 손으로 해 봐야 합니다. 오늘 만든 것이 곧 Day 4의 Docker 네트워크이고, Day 12의 쿠버네티스 Pod 네트워크입니다. 오늘 이해하면 나머지는 같은 그림의 반복입니다.

## 핵심 개념

### 네 가지 부품

컨테이너 네트워크는 리눅스 커널의 네 가지 부품으로 조립됩니다.

| 부품 | 비유 | 명령 | 도커에서의 이름 |
|---|---|---|---|
| 네트워크 네임스페이스 | 서버 한 대의 "빈 네트워크 카드 슬롯" | `ip netns` | 컨테이너의 네트워크 |
| veth 쌍 | 양쪽 끝이 각각 다른 네임스페이스에 꽂히는 랜선 | `ip link add ... type veth` | `vethXXXX@ifN` |
| 브리지 | 가상 스위치 (L2) | `ip link add ... type bridge` | `docker0`, `br-<id>` |
| 라우팅 + NAT | 스위치 밖으로 나가는 길과 주소 변환 | `ip route`, `iptables -t nat` | 도커가 자동 생성하는 MASQUERADE 규칙 |

<pre class="diagram">
  호스트(VM) 네트워크 네임스페이스
  ┌────────────────────────────────────────────────────────────────┐
  │  eth0 (192.0.2.2)  ←── 방화벽·DB존이 보는 "VM IP"                │
  │    ▲                                                            │
  │    │ NAT (MASQUERADE: 10.42.0.x → 192.0.2.2)                     │
  │  br-lab (10.42.0.1)  ── 가상 스위치                              │
  │    ├── veth-biz ══════╗                                         │
  │    └── veth-db  ══╗   ║  veth 쌍 (한쪽 끝은 호스트, 다른 끝은 ns) │
  └───────────────────║───║─────────────────────────────────────────┘
                      ║   ║
   ┌──────────────────║─┐ ║ ┌────────────────────┐
   │ ns "db"          ║ │ ║ │ ns "biz"           │
   │ eth0 10.42.0.20 ═╝ │ ╚═│ eth0 10.42.0.10    │
   │ lo               │   │ lo                   │
   │ (route: 없음)     │   │ default via 10.42.0.1│
   └────────────────────┘   └────────────────────┘
</pre>

**핵심 사실 하나**: 네임스페이스 안에서 나간 패킷은 브리지를 거쳐 호스트의 NAT를 타고 **호스트(VM)의 IP로 바뀌어** 밖으로 나갑니다. 그래서 고객사 방화벽은 컨테이너 IP를 모릅니다. VM IP만 압니다. 방화벽 신청서에 컨테이너 대역을 적을 필요가 없고, 적으면 오히려 혼란을 줍니다. (예외: 쿠버네티스에서 Pod IP가 라우팅되는 CNI 구성 — Day 12에서 확인 항목으로 다룹니다.)

### 라우팅 테이블 읽기

`ip route`의 출력은 위에서부터 "가장 구체적인 경로"가 우선입니다.

```text
default via 10.42.0.1 dev eth0            ← 나머지 전부는 10.42.0.1(게이트웨이)로
10.42.0.0/24 dev eth0 proto kernel ...    ← 같은 대역은 직접 (스위치로)
```

`default` 줄이 없으면 같은 대역 밖으로는 한 발짝도 못 나갑니다. 오늘 실습에서 이 실패를 일부러 봅니다. 고객사에서 "핑은 되는데 인터넷이 안 된다"는 절반은 라우팅, 절반은 프록시(Day 7)입니다.

### DNS — 이름 해석은 별개의 문제

연결이 되어도 이름을 못 풀면 "안 된다"고 보입니다. 리눅스에서 이름 해석 순서는:

1. `/etc/hosts` (정적 매핑)
2. `/etc/resolv.conf`의 `nameserver` (DNS 서버) — `search` 도메인이 있으면 짧은 이름 뒤에 붙여 재시도
3. (`nsswitch.conf`의 순서에 따라)

도커는 컨테이너마다 `/etc/resolv.conf`를 **자기가 다시 씁니다**. 사용자 정의 네트워크에서는 `127.0.0.11`(도커 내장 DNS)을 넣고 컨테이너 이름을 풀어 주며, 기본 bridge에서는 호스트의 nameserver를 그대로 복사합니다. 이 차이가 Day 4의 "이름으로 통신"을 결정합니다.

### cgroup — 얼마나 쓸 수 있는가

네임스페이스가 "무엇을 볼 수 있는가"라면 cgroup은 "얼마나 쓸 수 있는가"입니다. `docker run --memory=64m`은 cgroup의 메모리 상한을 64MiB로 쓰는 것과 같고, 쿠버네티스의 `resources.limits`도 결국 같은 파일에 값을 씁니다. 상한을 넘으면 커널이 프로세스를 죽입니다(OOMKilled). 고객사에서 "에이전트가 이유 없이 재시작된다"의 흔한 원인입니다.

## 실습 2-1 — 빈 네임스페이스에서 출발

!!! os
    **Linux / WSL2**: 아래를 그대로 실행합니다 (`sudo` 필요).
    **macOS**: 도커 데스크톱의 리눅스 VM 안에서 실행합니다. 아래 한 줄로 특권 컨테이너에 들어간 뒤 같은 명령을 (`sudo` 없이) 실행하세요. 이 컨테이너는 호스트 VM의 네트워크 네임스페이스를 공유하므로 결과가 같습니다.
    ```bash
    docker run --rm -it --privileged --network=host nicolaka/netshoot:v0.13 bash
    # 나갈 때 exit. 컨테이너가 사라지면 만든 네임스페이스도 정리된다.
    ```

```bash
mkdir -p ~/onprem-lab/day02 && cd ~/onprem-lab/day02

# 0. 정리 (여러 번 실행해도 안전)
sudo ip netns del biz 2>/dev/null; sudo ip netns del db 2>/dev/null; sudo ip link del br-lab 2>/dev/null

# 1. 호스트(=VM)의 인터페이스. 이 목록을 기억해 두세요.
ip -brief addr

# 2. 빈 네임스페이스 하나
sudo ip netns add biz
sudo ip netns exec biz ip -brief addr

# 3. 그 안에서는 아무 데도 못 나간다
sudo ip netns exec biz ping -c1 -W1 8.8.8.8; echo "종료코드=$?"
```

!!! expect
    ```text
    lo               UNKNOWN        127.0.0.1/8
    eth0             UP             192.0.2.2/24        ← 호스트 IP (환경마다 다름)
    docker0          DOWN           172.17.0.1/16       ← 도커가 만든 기본 브리지

    lo               DOWN                                ← 새 네임스페이스: 루프백뿐, 그것도 DOWN
    ```

!!! fail
    ```text
    ping: connect: Network is unreachable
    종료코드=2
    ```
    네트워크 네임스페이스는 **아무 데도 연결되지 않은 상태**로 태어납니다. 인터페이스도, 경로도 없습니다. 도커가 컨테이너를 만들 때 하는 일은 이 빈 공간에 랜선을 꽂아 주는 것입니다.

## 실습 2-2 — 브리지와 veth로 연결하기

```bash
# 4. 가상 스위치
sudo ip link add br-lab type bridge
sudo ip addr add 10.42.0.1/24 dev br-lab
sudo ip link set br-lab up

# 5. 랜선 한 줄: 한쪽(veth-biz)은 호스트, 다른 쪽(eth0)은 biz 네임스페이스에
sudo ip link add veth-biz type veth peer name eth0 netns biz
sudo ip link set veth-biz master br-lab      # 호스트 쪽 끝을 스위치에 꽂음
sudo ip link set veth-biz up

# 6. 네임스페이스 쪽 끝에 주소
sudo ip netns exec biz ip addr add 10.42.0.10/24 dev eth0
sudo ip netns exec biz ip link set eth0 up
sudo ip netns exec biz ip link set lo up

# 7. 브리지(게이트웨이)까지 닿는가
sudo ip netns exec biz ping -c1 -W1 10.42.0.1
```

!!! expect
    ```text
    PING 10.42.0.1 (10.42.0.1) 56(84) bytes of data.
    64 bytes from 10.42.0.1: icmp_seq=1 ttl=64 time=0.061 ms
    ```

이제 두 번째 네임스페이스 `db`를 같은 스위치에 붙입니다. Day 6에서 "업무망 존"과 "DB존"이 될 두 칸입니다.

```bash
sudo ip netns add db
sudo ip link add veth-db type veth peer name eth0 netns db
sudo ip link set veth-db master br-lab && sudo ip link set veth-db up
sudo ip netns exec db ip addr add 10.42.0.20/24 dev eth0
sudo ip netns exec db ip link set eth0 up && sudo ip netns exec db ip link set lo up

# 도커가 FORWARD 체인 기본 정책을 DROP으로 바꿔 두므로, 우리 브리지의 통과를 허용한다
sudo iptables -I FORWARD -i br-lab -j ACCEPT
sudo iptables -I FORWARD -o br-lab -j ACCEPT

sudo ip netns exec biz ping -c1 -W1 10.42.0.20
bridge link            # 스위치 포트 목록
```

!!! expect
    ```text
    64 bytes from 10.42.0.20: icmp_seq=1 ttl=64 time=0.040 ms

    36: veth-biz@ifb0: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1500 master br-lab state forwarding ...
    37: veth-db@ifb0:  <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1500 master br-lab state forwarding ...
    ```
    `bridge link`의 `master br-lab state forwarding`이 "이 포트는 스위치에 꽂혀 있고 트래픽을 전달 중"이라는 뜻입니다. 도커 네트워크에 붙은 컨테이너 수만큼 이 줄이 생깁니다.

!!! note
    `iptables -I FORWARD` 두 줄이 없으면 같은 브리지 안의 두 네임스페이스끼리도 ping이 안 됩니다(100% packet loss). 도커가 설치된 호스트는 `FORWARD` 체인 기본 정책이 `DROP`이고, 브리지를 지나는 패킷도 이 체인을 통과하기 때문입니다. 도커는 자기가 만든 네트워크마다 이 허용 규칙을 자동으로 넣습니다 — 우리는 손으로 넣은 것뿐입니다. 이것이 "도커를 설치했더니 VM의 다른 서비스가 안 된다"는 고객사 민원의 한 원인이기도 합니다.

## 실습 2-3 — 라우팅: 게이트웨이가 없으면 못 나간다

```bash
sudo ip netns exec biz ip route
sudo ip netns exec biz ping -c1 -W1 1.1.1.1; echo "종료코드=$?"
```

!!! fail
    ```text
    10.42.0.0/24 dev eth0 proto kernel scope link src 10.42.0.10
    ping: connect: Network is unreachable
    종료코드=2
    ```
    같은 대역(10.42.0.0/24) 경로만 있고 `default`가 없습니다. 밖으로 나갈 길 자체가 없는 상태입니다. 고객사에서 VM 안 컨테이너가 "사내 다른 대역"에 못 갈 때 첫 번째로 볼 것이 이 출력입니다.

```bash
sudo ip netns exec biz ip route add default via 10.42.0.1
sudo ip netns exec biz ip route
sudo ip netns exec biz ping -c1 -W1 1.1.1.1; echo "종료코드=$?"
```

!!! fail
    ```text
    default via 10.42.0.1 dev eth0
    10.42.0.0/24 dev eth0 proto kernel scope link src 10.42.0.10
    --- 1.1.1.1 ping statistics ---
    1 packets transmitted, 0 received, 100% packet loss
    종료코드=1
    ```
    이번엔 "unreachable"이 아니라 **응답이 없습니다**(패킷은 나갔는데 돌아오지 않음). 길은 생겼지만 호스트가 이 패킷을 밖으로 전달(forward)하지 않고, 전달해도 출발지 주소가 10.42.0.10이라 응답이 돌아올 곳이 없기 때문입니다. 두 가지 오류의 차이 — "길이 없다" vs "응답이 없다" — 를 구분하는 것이 진단의 시작입니다.

## 실습 2-4 — NAT: 호스트 IP로 위장해 나가기

```bash
sudo sysctl -w net.ipv4.ip_forward=1                  # 호스트가 라우터 역할을 하도록
sudo iptables -t nat -A POSTROUTING -s 10.42.0.0/24 ! -o br-lab -j MASQUERADE
sudo iptables -t nat -L POSTROUTING -n

# ICMP를 막는 환경이 많으니 TCP로 확인
sudo ip netns exec biz nc -zv 1.1.1.1 443
```

!!! expect
    ```text
    Chain POSTROUTING (policy ACCEPT)
    target      prot opt source          destination
    MASQUERADE  0    --  172.17.0.0/16   0.0.0.0/0      ← 도커가 docker0용으로 넣어 둔 것
    MASQUERADE  0    --  10.42.0.0/24    0.0.0.0/0      ← 방금 우리가 넣은 것

    Connection to 1.1.1.1 443 port [tcp/https] succeeded!
    ```
    도커가 넣어 둔 규칙과 우리 규칙이 **완전히 같은 모양**입니다. `docker network create`가 하는 일이 정확히 이것입니다.

!!! verified
    실습 2-1~2-4는 세션 안(Ubuntu, Docker 설치 상태)에서 실행해 위 출력을 확인했습니다. 다만 세션 환경은 ICMP 아웃바운드가 막혀 있어 외부 `ping`은 확인하지 못했고, TCP 443으로 대신 확인했습니다. 회사 PC도 ICMP가 막힌 경우가 많으니 **외부 연결 확인은 항상 `nc -zv <호스트> <포트>`로** 하는 습관을 들이세요.

## 실습 2-5 — 눈으로 확인: 패킷이 실제로 지나는가

`db` 네임스페이스에 "DB 서버"를 흉내 내는 리스너를 띄우고, `biz`에서 접속하며 `tcpdump`로 봅니다. 고객사에서 "방화벽은 열었다는데 안 된다"를 판정하는 방법이 이것입니다: **패킷이 도착하는지, 도착했는데 응답이 없는지, 애초에 출발을 안 하는지.**

```bash
# DB 서버 흉내 (5432 리슨)
sudo ip netns exec db sh -c 'nc -l -k 10.42.0.20 5432 >/dev/null 2>&1 &'

# 터미널 A: db 쪽에서 패킷 관찰 (3초 후 종료)
sudo ip netns exec db timeout 3 tcpdump -ni eth0 -c 2 tcp port 5432 &
sleep 0.5
# 터미널 B(같은 터미널이어도 됨): biz에서 접속
sudo ip netns exec biz nc -zv 10.42.0.20 5432
wait
```

!!! eye
    **tcpdump** — "패킷이 도착했는가"를 보는 유일한 도구입니다. 아래 두 줄을 읽는 법:
    ```text
    14:19:56.519119 IP 10.42.0.10.51474 > 10.42.0.20.5432: Flags [S], seq ...   ← SYN: 접속 요청 도착
    14:19:56.519133 IP 10.42.0.20.5432 > 10.42.0.10.51474: Flags [S.], seq ...  ← SYN-ACK: 서버가 응답
    ```
    - `[S]`만 있고 `[S.]`가 없다 → 패킷은 도착했지만 서버가 리슨하지 않음(서비스 미기동) 또는 서버 쪽 방화벽이 버림
    - 아무것도 안 찍힌다 → 패킷이 여기까지 안 옴(중간 방화벽, 라우팅)
    - `[R.]`(RST)가 온다 → 도착했고 포트가 닫혀 있음("Connection refused")

    이 세 가지 구분을 고객 인프라팀에 전달하면 "안 됩니다"보다 열 배 빨리 해결됩니다.

```bash
sudo pkill -f "nc -l -k 10.42.0.20"
```

## 실습 2-6 — 도커가 만든 것과 비교하기

이제 도커에게 같은 일을 시키고, 우리가 만든 것과 비교합니다.

```bash
docker network create demo-net
docker run -d --rm --name who1 --network demo-net alpine:3.20 sleep 300

ip -brief link | grep -E "br-|veth"                # 도커가 만든 브리지와 veth
sudo iptables -t nat -S POSTROUTING | grep -v DOCKER  # 도커가 만든 MASQUERADE

PID=$(docker inspect who1 --format '{{.State.Pid}}')
sudo nsenter -t "$PID" -n ip -brief addr           # 컨테이너 네임스페이스 안의 인터페이스
sudo nsenter -t "$PID" -n ip route                 # 컨테이너 안의 라우팅 테이블
docker exec who1 cat /etc/resolv.conf              # 도커가 다시 쓴 DNS 설정
```

!!! expect
    ```text
    br-c157d965c4df  UP   ...                         ← 우리의 br-lab
    veth672c767@if2  UP   ...                         ← 우리의 veth-biz
    -A POSTROUTING -s 172.18.0.0/16 ! -o br-c157d965c4df -j MASQUERADE   ← 우리의 NAT 규칙과 동일
    -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE

    lo         UNKNOWN  127.0.0.1/8
    eth0@if40  UP       172.18.0.2/16                  ← 우리의 10.42.0.10
    default via 172.18.0.1 dev eth0                   ← 우리가 손으로 넣은 default route
    172.18.0.0/16 dev eth0 proto kernel scope link src 172.18.0.2

    nameserver 127.0.0.11                             ← 도커 내장 DNS (사용자 정의 네트워크)
    options timeout:2 attempts:3 ndots:0
    ```

이제 기본 bridge 네트워크의 컨테이너와 비교합니다.

```bash
docker run -d --rm --name who2 alpine:3.20 sleep 300     # --network 없음 = 기본 bridge
docker exec who2 cat /etc/resolv.conf
docker exec who1 nslookup who1 | tail -2                 # 사용자 정의 네트워크: 이름 해석 됨
docker exec who2 nslookup who2 2>&1 | tail -1            # 기본 bridge: 안 됨
```

!!! expect
    ```text
    nameserver 8.8.8.8          ← 기본 bridge: 호스트의 resolv.conf를 그대로 복사
    nameserver 8.8.4.4

    Address: 172.18.0.2         ← who1은 자기 이름을 풀 수 있다
    ** server can't find who2: NXDOMAIN   ← who2는 못 푼다
    ```
    이것이 Day 4에서 "실무에서는 항상 사용자 정의 네트워크를 쓴다"고 말하는 이유입니다.

## 실습 2-7 — cgroup: 메모리 상한 걸어 보기

```bash
docker run -d --rm --name lim --memory=64m alpine:3.20 sleep 300
docker stats --no-stream lim
docker exec lim sh -c 'cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes'
```

!!! expect
    ```text
    CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   ...
    5d390494379f   lim    0.00%   604KiB / 64MiB      0.92%
    67108864                                          ← 64 × 1024 × 1024. 커널이 보는 상한
    ```
    `docker run --memory`도, Compose의 `deploy.resources.limits.memory`도, 쿠버네티스의 `resources.limits.memory`도 결국 이 파일 하나에 숫자를 씁니다. 상한을 넘으면 `OOMKilled`. 에이전트가 문서를 파싱하다 죽는다면 여기부터 봅니다.

## 오류 대응

!!! rollback
    - `RTNETLINK answers: File exists` → 이미 만들어진 것. 실습 2-1의 0번 정리 명령을 먼저 실행하고 다시.
    - `Cannot find device "br-lab"` → 브리지 생성 단계(4번)를 건너뜀. 순서대로 다시.
    - 같은 브리지의 두 네임스페이스끼리 ping 100% loss → `iptables -I FORWARD` 두 줄을 넣었는지 확인.
    - `nsenter: command not found` → `util-linux` 패키지. macOS는 netshoot 컨테이너 안에서 실행.
    - macOS에서 `ip netns`가 `Operation not permitted` → `--privileged` 없이 컨테이너를 띄운 것.
    - 전부 엉켰으면 아래 정리 명령 후 처음부터. 5분이면 다시 만들 수 있습니다.
