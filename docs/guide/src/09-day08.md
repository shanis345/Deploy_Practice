# Day 8 — 사내 CA와 TLS 검사(SSL 인스펙션)

<div class="day-meta"><span><b>소요</b> 2~3시간</span><span><b>만드는 것</b> 사내 CA를 병합한 이미지 <code>agent:0.2.0-ca</code>, 인증서 진단 명령</span><span><b>눈으로</b> mitmweb (복호화된 HTTPS), openssl</span></div>

!!! why
    대기업 망에서 외부 HTTPS 호출이 실패하는 원인 1순위입니다. 그리고 증상을 처음 보면 무슨 말인지 알기 어렵습니다.

    ```text
    ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED]
    certificate verify failed: unable to get local issuer certificate
    ```

    브라우저에서는 잘 되는데 파이썬에서만 실패하고, 회사 노트북에서는 되는데 컨테이너에서는 안 되고, `pip install`은 되는데 `docker build` 안의 `pip install`은 안 됩니다. 이 모든 것이 하나의 원인 — **사내 CA를 신뢰 목록에 갖고 있느냐** — 에서 나옵니다. 오늘 그 이유를 이해하고, 재현하고, 해결합니다. 이것만 알아도 첫 케이스에서 며칠을 법니다.

## 핵심 개념

### 왜 사내 CA가 등장하는가

기업 보안팀은 직원과 서버가 HTTPS로 무엇을 주고받는지 검사하고 싶어 합니다(DLP, 악성코드 탐지, 데이터 반출 통제). 그런데 HTTPS는 암호화되어 있습니다. 그래서 프록시가 중간에서 연결을 끊고 두 개로 나눕니다.

<pre class="diagram">
[정상]
클라이언트 ────────── TLS ──────────▶ api.openai.com
                     (진짜 인증서: DigiCert 등 공인 CA가 서명)

[TLS 검사 환경]
클라이언트 ── TLS ──▶ 검사 프록시 ── TLS ──▶ api.openai.com
                          │
                 여기서 내용을 복호화해 검사
                 클라이언트에게는 "사내 CA가 서명한 가짜 api.openai.com 인증서"를 제시
</pre>

즉 프록시가 **의도적인 중간자(MITM)**가 됩니다. 클라이언트가 이 가짜 인증서를 신뢰하려면 **사내 CA의 루트 인증서를 신뢰 목록에 갖고 있어야** 합니다. 회사 PC는 관리자가 미리 심어 두기 때문에 브라우저가 잘 됩니다.

!!! note
    Day 7의 포워드 프록시(squid)는 CONNECT 터널만 열어 주고 내용을 보지 않았습니다. TLS 검사 프록시는 그 터널 안까지 들어옵니다. 고객사에 따라 ① 검사 안 함, ② 특정 카테고리만 검사, ③ 전부 검사, ④ 프록시 없이 네트워크 장비가 투명하게 검사(이 문서를 만든 세션 환경이 이 경우) — 네 가지가 있고, **어느 것인지 물어야 합니다.**

### 브라우저는 되고 파이썬은 안 되는 이유 — 신뢰 저장소가 여러 개

| 주체 | 신뢰 저장소 | 사내 CA 추가 방법 |
|---|---|---|
| OS (Debian/Ubuntu) | `/etc/ssl/certs/ca-certificates.crt` | `/usr/local/share/ca-certificates/*.crt` + `update-ca-certificates` |
| OS (RHEL/UBI/Rocky) | `/etc/pki/tls/certs/ca-bundle.crt` | `/etc/pki/ca-trust/source/anchors/*.crt` + `update-ca-trust extract` |
| 브라우저 (Chrome/Edge) | OS 저장소 (Windows/macOS) | 그룹 정책으로 자동 배포 — 그래서 브라우저는 됨 |
| Firefox | **자체 저장소** | 별도 설정 |
| 파이썬 `urllib` / `ssl` | OS 저장소 (기본) | `SSL_CERT_FILE` |
| 파이썬 `requests` | **certifi 패키지에 내장된 자체 번들** | `REQUESTS_CA_BUNDLE` |
| 파이썬 `httpx` | certifi | `SSL_CERT_FILE` |
| Node.js | **자체 내장 번들** | `NODE_EXTRA_CA_CERTS=파일` (추가 방식) |
| Java | `$JAVA_HOME/lib/security/cacerts` | `keytool -importcert -cacerts -alias corp -file corp-ca.crt` |
| curl | OS 저장소 | `--cacert`, `CURL_CA_BUNDLE` |
| Git | OS 저장소 또는 자체 설정 | `git config http.sslCAInfo` |
| pip | certifi | `PIP_CERT=파일` 또는 `pip.conf`의 `cert` |
| npm | Node 번들 | `npm config set cafile 파일` |
| Docker 데몬 (레지스트리 접속) | OS 저장소 + `/etc/docker/certs.d/<레지스트리>/ca.crt` | Day 9 |
| .NET | OS 저장소 | |

회사 PC는 OS 저장소에 사내 CA가 심겨 있으므로 브라우저와 curl은 됩니다. 그런데 `requests`는 certifi를 보므로 실패합니다. **컨테이너는 아예 아무것도 심겨 있지 않으므로 전부 실패합니다.**

### 해결 방법

| 방법 | 적용 대상 | 비고 |
|---|---|---|
| OS 저장소에 병합 (이미지 빌드 시) | 그 컨테이너의 curl, urllib, OS 기반 도구 전부 | **권장**. 공인 CA와 사내 CA를 모두 가짐 |
| `SSL_CERT_FILE` | 파이썬 ssl, httpx, 다수 도구 | 파일 하나로 **번들을 대체** — 병합 번들을 가리켜야 안전 |
| `REQUESTS_CA_BUNDLE` | 파이썬 requests | 위와 동일 |
| `NODE_EXTRA_CA_CERTS` | Node.js | "추가"라서 사내 CA 파일만 가리켜도 됨 |
| `CURL_CA_BUNDLE` / `--cacert` | curl | |
| 런타임 마운트 (`-v`, ConfigMap) | 이미지를 못 고칠 때 | Day 11의 쿠버네티스 방식 |
| `verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0` | — | **절대 하지 마세요** |

마지막 항목을 강조합니다. 검색하면 `verify=False`가 가장 먼저 나오지만, 이건 TLS 검증을 끄는 것이고 보안 심의에서 즉시 지적됩니다. 그리고 한번 넣으면 코드에서 빠지지 않습니다. 올바른 해결은 **사내 CA를 신뢰 목록에 추가**하는 것입니다.

## 실습 8-1 — 사내 TLS 검사 환경 재현하기

`mitmproxy`를 사내 TLS 검사 프록시로 씁니다. 자체 CA를 자동 생성해 주므로 실습에 이상적입니다.

```bash
cd ~/onprem-lab/day08
ls    # compose.yaml  certs/ (처음엔 비어 있음)
```

```yaml
#file: compose.yaml
name: day08

services:
  # 사내 TLS 검사 프록시 역할. 처음 실행 시 자체 CA를 만들어 ./certs 에 둔다.
  tls-proxy:
    image: mitmproxy/mitmproxy:11.0.0
    command: >
      mitmweb --web-host 0.0.0.0 --web-port 8081
      --set block_global=false --set web_password=lab
    networks: [closed, outside]
    ports:
      - "127.0.0.1:8081:8081"          # 웹 UI (검사된 요청을 눈으로)
    volumes:
      - ./certs:/home/mitmproxy/.mitmproxy
    restart: unless-stopped

  agent:                               # CA를 심지 않은 이미지
    image: agent:0.2.0
    networks: [closed]
    environment: &proxyenv
      HTTPS_PROXY: "http://tls-proxy:8080"
      https_proxy: "http://tls-proxy:8080"
      HTTP_PROXY:  "http://tls-proxy:8080"
      http_proxy:  "http://tls-proxy:8080"
      NO_PROXY:    "localhost,127.0.0.1,tls-proxy"
      no_proxy:    "localhost,127.0.0.1,tls-proxy"

  agent-envca:                         # 해결 1: 환경변수로 CA 파일 지정
    image: agent:0.2.0
    networks: [closed]
    environment:
      <<: *proxyenv
      SSL_CERT_FILE: /certs/mitmproxy-ca-cert.pem
      REQUESTS_CA_BUNDLE: /certs/mitmproxy-ca-cert.pem
    volumes:
      - ./certs:/certs:ro

  agent-ca:                            # 해결 2: 이미지에 CA 병합 (권장)
    image: agent:0.2.0-ca
    networks: [closed]
    environment: *proxyenv

  probe:
    image: nicolaka/netshoot:v0.13
    networks: [closed]
    command: sleep infinity

networks:
  closed:
    internal: true
  outside:
    driver: bridge
```

```bash
docker compose up -d tls-proxy && sleep 6
ls certs/
openssl x509 -in certs/mitmproxy-ca-cert.pem -noout -subject -issuer -dates
```

!!! expect
    ```text
    mitmproxy-ca-cert.cer  mitmproxy-ca-cert.p12  mitmproxy-ca-cert.pem  mitmproxy-ca.p12  mitmproxy-ca.pem  mitmproxy-dhparam.pem
    subject=CN = mitmproxy, O = mitmproxy
    issuer=CN = mitmproxy, O = mitmproxy
    notBefore=Sep 20 05:54:00 2026 GMT
    notAfter=Sep 19 05:54:00 2036 GMT
    ```
    `mitmproxy-ca-cert.pem`이 "사내 CA 루트 인증서"에 해당합니다. 고객사에서는 보안팀에게 이 파일을 받게 됩니다.

!!! say
    "TLS 검사(SSL 인스펙션)를 하시나요? 하신다면 **루트 CA 인증서 파일(PEM)**을 주시고, **검사 예외 대상 도메인 목록**도 알려주세요. 그리고 인증서 갱신 주기(사내 CA가 교체되면 저희 이미지도 재빌드해야 합니다)를 알려주세요."

## 실습 8-2 — 실패 재현과 해결 두 가지

CA가 없는 이미지로 TLS 검사 프록시를 통과시킵니다. 이미지에 CA를 병합한 버전(`agent:0.2.0-ca`)은 먼저 빌드해 둡니다.

```bash
# 사내 CA를 병합한 이미지 빌드 (Dockerfile.ca는 부록 F 참고)
cp certs/mitmproxy-ca-cert.pem ~/onprem-lab/agent/corp-ca.crt
docker build -f ~/onprem-lab/agent/Dockerfile.ca --build-arg BASE_IMAGE=agent:0.2.0 -t agent:0.2.0-ca ~/onprem-lab/agent
rm ~/onprem-lab/agent/corp-ca.crt

docker compose up -d && sleep 5
q() { docker compose exec -T probe curl -s -m 20 "http://$1:8000/$2"; }

echo "① CA 없음"
q agent       "egress?url=https://example.com" | jq -c '{ok,error_type,error}'
echo "② 환경변수로 CA 파일 지정"
q agent-envca "egress?url=https://example.com" | jq -c '{ok,status}'
echo "③ 이미지에 CA 병합"
q agent-ca    "egress?url=https://example.com" | jq -c '{ok,status}'
q agent-ca    diag | jq -c '{ca}'
```

!!! fail
    ```text
    ① {"ok":false,"error_type":"SSLCertVerificationError",
        "error":"[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate (_ssl.c:1010)"}
    ```
    **이 메시지를 기억하세요.** 고객 환경에서 이 메시지를 보면 바로 사내 CA 문제라고 판단할 수 있습니다. `unable to get local issuer certificate` = "이 인증서를 서명한 CA를 내 신뢰 목록에서 못 찾겠다".

!!! expect
    ```text
    ② {"ok":true,"status":200}
    ③ {"ok":true,"status":200}
    {"ca":{"SSL_CERT_FILE":"/etc/ssl/certs/ca-certificates.crt","REQUESTS_CA_BUNDLE":"/etc/ssl/certs/ca-certificates.crt","CURL_CA_BUNDLE":"/etc/ssl/certs/ca-certificates.crt"}}
    ```

두 해결책의 차이:

- **②(환경변수로 파일 하나 지정)**는 빠르지만 `SSL_CERT_FILE`이 **기존 공인 CA 번들을 대체**합니다. 검사를 거치지 않는 목적지(예: 검사 예외 도메인, 사내 시스템의 공인 인증서)와의 통신이 깨질 수 있습니다. 급할 때만.
- **③(이미지에 병합)**은 `update-ca-certificates`가 공인 CA + 사내 CA를 **모두 포함한 번들**을 만들고, 환경변수는 그 병합 번들을 가리킵니다. 검사를 타는 목적지와 안 타는 목적지가 섞여 있어도 둘 다 동작합니다. 운영은 이쪽입니다.

```dockerfile
#file: agent/Dockerfile.ca
# 사내 CA를 OS 신뢰 저장소에 병합한 이미지. 빌드 컨텍스트에 corp-ca.crt 가 있어야 한다.
#   docker build -f Dockerfile.ca --build-arg BASE_IMAGE=agent:0.2.0 -t agent:0.2.0-ca .
ARG BASE_IMAGE=agent:0.2.0
FROM ${BASE_IMAGE}
USER 0
COPY corp-ca.crt /usr/local/share/ca-certificates/corp-ca.crt
# Debian/Ubuntu 계열: update-ca-certificates 가 /etc/ssl/certs/ca-certificates.crt 를 재생성 (공인 CA + 사내 CA)
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates \
 && update-ca-certificates \
 && rm -rf /var/lib/apt/lists/*
# 파이썬 requests(certifi)·Node·curl 이 OS 번들을 보도록 지정. 병합된 번들이므로 공인 CA도 그대로 유효.
ENV SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt \
    REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt \
    CURL_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt \
    NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/corp-ca.crt
USER 10001

# ── RHEL / UBI 계열이라면 위 COPY/RUN/ENV 대신 ──────────────────────────
# COPY corp-ca.crt /etc/pki/ca-trust/source/anchors/corp-ca.crt
# RUN update-ca-trust extract
# ENV SSL_CERT_FILE=/etc/pki/tls/certs/ca-bundle.crt REQUESTS_CA_BUNDLE=/etc/pki/tls/certs/ca-bundle.crt
```

!!! verified
    ①②③ 모두 세션 안에서 실행해 위 출력을 확인했습니다. 세션 환경 자체에 투명 TLS 검사가 있어서, 검증할 때는 mitmproxy가 상위(세션) CA를 신뢰하도록 옵션을 하나 더 주었습니다. 이는 **"TLS 검사가 이중으로 걸린 환경"**(사내 프록시 검사 + 인터넷 관문 검사)의 재현이기도 한데, 국내 대기업에서도 실제로 있는 구성입니다. 그 경우 CA 파일을 두 개 받아 둘 다 병합해야 합니다.

!!! check
    - 고객사가 **RHEL UBI 기반 승인 이미지**만 허용하면 `Dockerfile.ca`의 주석 처리된 RHEL 블록을 쓰세요. 경로가 다릅니다.
    - 사내 CA가 **중간 CA(intermediate)**로 발급되는 경우, 루트와 중간 인증서를 모두 받아 하나의 파일에 이어 붙입니다 (`cat root.crt intermediate.crt > corp-ca.crt`).
    - CA 인증서 **갱신 주기**. 사내 CA가 바뀌면 이미지를 재빌드·재반입해야 합니다. 갱신 일정을 미리 받아 두세요.

## 실습 8-3 — 인증서 진단 명령

고객 환경에서 인증서 문제를 만났을 때 쓸 명령입니다. netshoot(`probe`)에서 실행합니다.

```bash
# 1. 실제로 어떤 인증서가 제시되는가 — 누가 서명했나
docker compose exec -T probe sh -c \
  'openssl s_client -connect example.com:443 -proxy tls-proxy:8080 </dev/null 2>/dev/null | grep -E "issuer=|subject=|Verify return"'

# 2. 컨테이너 안 번들에 사내 CA가 들어 있는가
docker compose exec -T agent-ca sh -c 'grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt'
docker compose exec -T agent    sh -c 'grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt'

# 3. 번들 안의 특정 CA 찾기
docker compose exec -T agent-ca sh -c \
  'awk -v cmd="openssl x509 -noout -subject" "/BEGIN/{close(cmd)};{print | cmd}" < /etc/ssl/certs/ca-certificates.crt | grep -i mitm'

# 4. curl로 같은 것 (CA 유무 비교)
docker cp certs/mitmproxy-ca-cert.pem day08-probe-1:/tmp/corp-ca.pem
docker compose exec -T probe sh -c 'curl -s -m10 -x http://tls-proxy:8080 -o /dev/null -w "CA 없음: exit=%{exitcode}\n" https://example.com'
docker compose exec -T probe sh -c 'curl -s -m10 -x http://tls-proxy:8080 --cacert /tmp/corp-ca.pem -o /dev/null -w "--cacert: %{http_code}\n" https://example.com'
```

!!! expect
    ```text
    subject=CN=example.com
    issuer=CN=mitmproxy, O=mitmproxy                     ← 발급자가 공인 CA가 아니라 "사내 CA"
    Verify return code: 21 (unable to verify the first certificate)
    151                                                  ← CA 병합 이미지: 공인 CA 150개 + 사내 CA 1개
    150                                                  ← 원본 이미지
    subject=CN=mitmproxy, O=mitmproxy
    CA 없음: exit=60                                     ← curl 60 = SSL certificate problem
    --cacert: 200
    ```
    1번이 가장 먼저 할 진단입니다. **발급자(issuer)에 회사 이름(또는 검사 장비 이름)이 보이면 TLS 검사 환경이 확실**하고, DigiCert·Let's Encrypt 같은 공인 CA가 보이면 검사를 타지 않는 경로입니다. `-proxy` 옵션으로 프록시 경유 결과를 봐야 합니다 — 프록시를 안 거치면 다른 인증서가 보입니다.

## 실습 8-4 — 눈으로 확인: 복호화된 HTTPS

브라우저에서 `http://localhost:8081/?token=lab`을 엽니다. `agent-ca`가 보낸 HTTPS 요청이 **복호화되어** 헤더와 본문까지 보입니다.

## 증상 → 원인 판별표

| 증상 | 유력한 원인 | 확인 |
|---|---|---|
| `CERTIFICATE_VERIFY_FAILED` / `unable to get local issuer certificate` | 사내 CA 미설치 | `openssl s_client -proxy`로 issuer 확인 |
| `self-signed certificate in certificate chain` | 사내 CA 미설치 (검사 장비가 자체 서명 루트 사용) | 위와 동일 |
| `Network is unreachable` / 이름 해석 실패 | 프록시 미설정 | `/diag`로 환경변수 확인 (Day 7) |
| 타임아웃(무응답) | 방화벽 미개방 | `nc -z proxy 3128` |
| `403 Forbidden` from proxy / `Tunnel connection failed: 403` | 화이트리스트 미등록 | 프록시 로그 확인 요청 |
| `407 Proxy Authentication Required` | 프록시 인증 필요 | 계정 발급 요청, `http://user:pass@proxy` |
| curl은 되는데 파이썬만 실패 | certifi 번들 문제 | `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE` 설정 |
| HTTP는 되고 HTTPS만 실패 | TLS 검사 + CA 문제 | 위와 동일 |
| 어떤 사이트는 되고 어떤 사이트만 실패 | 검사 예외 목록 + `SSL_CERT_FILE`로 번들 대체 | 병합 번들로 교체 (해결 2) |
| 되다가 어느 날부터 실패 | 사내 CA 갱신 | issuer의 유효기간 확인, 새 CA 병합 |
| `hostname mismatch` | 프록시가 SNI를 못 읽음 / IP로 직접 호출 | FQDN으로 호출 |

이 표를 [부록 C](#부록-c-트러블슈팅-플레이북-증상-원인)에도 넣어 두었습니다. 첫 케이스에 프린트해서 가세요.

## 오류 대응

!!! rollback
    - `certs/`가 비어 있음 → `tls-proxy`가 아직 안 떴거나 볼륨 권한 문제. `docker compose logs tls-proxy`. 6초 이상 기다리세요.
    - `agent:0.2.0-ca` 빌드 실패 (`apt-get` 단계) → 회사 PC라면 빌드 자체가 프록시·CA를 타야 합니다. Day 7 실패 4의 `--build-arg`로 프록시를 주고, 그래도 안 되면 베이스 이미지에 이미 `ca-certificates`가 있으므로 `apt-get` 줄을 지우고 `update-ca-certificates`만 남겨 보세요.
    - ②③이 `502`로 실패 → mitmproxy가 **상위**(인터넷 관문) 인증서를 신뢰하지 못하는 것. 회사 PC라면 이중 검사 환경입니다. 상위 CA 파일을 받아 `--set ssl_verify_upstream_trusted_ca=/경로`로 지정하세요.
    - `web_password` 오류로 UI가 안 열림 → URL 뒤 `?token=lab`.
