# Day 5 — Docker Compose: 다중 서비스와 그 한계

<div class="day-meta"><span><b>소요</b> 2~3시간</span><span><b>만드는 것</b> nginx → 에이전트 → DB 3티어, 장애 재현 3종</span><span><b>눈으로</b> lazydocker (프로젝트·로그·헬스)</span></div>

!!! why
    국내 대기업 파일럿에서 가장 흔한 배포 형태입니다. 쿠버네티스가 없는 고객사에서 에이전트를 올릴 때 현실적인 첫 선택지가 Compose이고, 실제로 파일럿의 절반 이상이 "VM 한 대 + Compose"로 끝납니다.

    동시에 **한계를 정확히 아는 것**이 중요합니다. 스폰서가 "이 구성으로 전사 운영이 가능합니까?"라고 물었을 때, "가능합니다"라고 답하면 3개월 뒤 문제가 됩니다. 오늘 장애를 세 종류 만들어 보면서 Compose가 무엇을 되살리고 무엇을 못 되살리는지 눈으로 확인합니다. 그 목록이 곧 정식 전환 조건(Day 14)입니다.

## 핵심 개념

### Compose가 해 주는 것과 안 해 주는 것

| 해 주는 것 | 안 해 주는 것 |
|---|---|
| 여러 컨테이너를 한 번에 기동·정지 | 여러 서버에 걸친 배포 |
| 서비스 간 네트워크와 DNS 자동 구성 | 자동 수평 확장 |
| 의존 순서와 헬스체크 대기 | 무중단 롤링 업데이트 |
| 볼륨과 환경변수 관리 | 노드 장애 시 자동 이전 |
| 프로세스 종료 시 재시작 | **살아 있지만 응답 없는 컨테이너 교체** |

즉 Compose는 **서버 한 대 안에서의 오케스트레이션**입니다. 그 서버가 죽으면 서비스도 죽습니다. 파일럿에서는 충분하고, 정식 운영 전환 시에는 오른쪽 열이 전환 조건 목록이 됩니다.

### 알아야 할 핵심 지시어

| 지시어 | 역할 | 실무 포인트 |
|---|---|---|
| `image` | 이미지 지정 | 고객사에서는 항상 사내 레지스트리 주소 (`harbor.corp.local/ax/agent:0.2.0`) |
| `environment` / `env_file` | 환경변수 | 비밀은 `.env`로 분리, `.env`는 git에 넣지 않음. `${VAR:-기본값}` 치환 |
| `volumes` | 마운트 | 프롬프트·설정은 `:ro`로 마운트. DB 데이터는 이름 있는 볼륨 |
| `networks` | 소속 네트워크 | 망 구분을 여기서 표현 (Day 6) |
| `healthcheck` | 정상 여부 판정 | 없으면 `depends_on: condition: service_healthy`가 무의미 |
| `depends_on` | 기동 순서 | `condition: service_healthy`까지 써야 실제 효과 |
| `restart` | 재시작 정책 | 운영은 `unless-stopped` |
| `deploy.resources` | 자원 상한 | Compose v2에서도 동작. 없으면 에이전트가 VM 메모리를 다 먹을 수 있음 |
| `logging` | 로그 드라이버·크기 | **필수**. 안 걸면 디스크가 찬다 |
| `ports` | 호스트 포트 게시 | `127.0.0.1:`을 붙여 내부만 |

`logging`을 빠뜨려서 고객 VM 디스크를 채우는 사고가 실제로 자주 납니다. 컨테이너 로그는 기본적으로 무제한으로 쌓입니다. 반드시 넣으세요.

## 실습 5-1 — 3티어 애플리케이션

```bash
cd ~/onprem-lab/day05
ls    # compose.yaml  nginx.conf  config/  .env.example
```

```yaml
#file: compose.yaml
name: day05

x-log: &logopt
  driver: json-file
  options: { max-size: "10m", max-file: "3" }

services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "127.0.0.1:8080:80"          # 호스트 내부에서만. 고객사에서는 여기에 사내 LB가 붙는다
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      agent:
        condition: service_healthy   # 에이전트가 healthy 될 때까지 기다린다
    restart: unless-stopped
    logging: *logopt

  agent:
    image: ${AGENT_IMAGE:-agent:0.2.0}
    environment:
      DB_DSN: "postgresql://appuser:${POSTGRES_PASSWORD:-apppass}@postgres:5432/appdb"
      PROMPT_PATH: /app/config/prompt.txt
      RUBRIC_PATH: /app/config/rubric.yaml
      LOG_LEVEL: ${LOG_LEVEL:-INFO}
    volumes:
      - ./config:/app/config:ro       # 프롬프트·rubric은 이미지 밖에
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 5s
    logging: *logopt

  postgres:
    image: postgres:16.4-alpine
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-apppass}
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 10s
      timeout: 3s
      retries: 5
    restart: unless-stopped
    logging: *logopt

volumes:
  pgdata:
```

```nginx
#file: nginx.conf
server {
    listen 80;
    server_name _;
    client_max_body_size 20m;

    location / {
        proxy_pass http://agent:8000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Request-Id $request_id;
        # 에이전트는 응답이 길다. 기본 60초로 두면 LLM 호출이 긴 요청에서 502/504
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

`config/prompt.txt`와 `config/rubric.yaml`은 이미지 밖에 두는 설정입니다([부록 F](#부록-f-전체-실습-파일-트리)).

```bash
docker compose config --quiet && echo "문법 OK"     # 올리기 전에 항상
docker compose up -d
sleep 12
docker compose ps
curl -s localhost:8080/healthz
curl -s localhost:8080/diag | jq '{prompt_exists, prompt_sha, rubric, db_dsn_set}'
curl -s "localhost:8080/tcp?host=postgres&port=5432" | jq -c .
```

!!! expect
    ```text
    NAME               IMAGE                  SERVICE    STATUS                    PORTS
    day05-agent-1      agent:0.2.0            agent      Up 17 seconds (healthy)   8000/tcp
    day05-nginx-1      nginx:1.27-alpine      nginx      Up 12 seconds             127.0.0.1:8080->80/tcp
    day05-postgres-1   postgres:16.4-alpine   postgres   Up 28 seconds (healthy)   5432/tcp

    {"status": "ok", "version": "0.2.0", "host": "7456eeeb65f0"}
    {"prompt_exists": true, "prompt_sha": "258e1f7baff4", "rubric": {...}, "db_dsn_set": true}
    {"ok":true,"host":"postgres","port":5432,"elapsed_ms":0}
    ```
    `STATUS`의 `(healthy)`가 핵심입니다. nginx가 agent보다 늦게 뜬 것(12초 vs 17초)은 `depends_on: condition: service_healthy`가 기다렸기 때문입니다. `PORTS` 열에서 외부로 게시된 것은 nginx의 `127.0.0.1:8080` 하나뿐입니다 — Day 4에서 말한 "입구 하나"입니다.

## 실습 5-2 — 장애를 세 종류 만들어 보기

이 실습이 오늘의 핵심입니다. 에이전트 이미지에는 실습용 엔드포인트 `/_lab/exit`(프로세스 강제 종료)와 `/_lab/hang`(무응답 상태)이 있습니다.

### ① 프로세스가 죽는다 → Compose가 살린다

```bash
curl -s localhost:8080/_lab/exit; sleep 2
docker compose ps agent --format "table {{.Service}}\t{{.Status}}"
sleep 8
docker compose ps agent --format "table {{.Service}}\t{{.Status}}"
docker inspect day05-agent-1 --format 'RestartCount={{.RestartCount}}'
```

!!! expect
    ```text
    {"bye": true}
    SERVICE   STATUS
    agent     Up 1 second (health: starting)      ← 죽자마자 재시작됨
    agent     Up 10 seconds (healthy)
    RestartCount=1
    ```
    `restart: unless-stopped` 덕분입니다. 단, **`docker compose kill`이나 `docker stop`으로 멈춘 것은 살리지 않습니다** — 도커는 사람이 멈춘 것으로 간주합니다. 그래서 실습에서는 프로세스가 스스로 죽게 했습니다.

### ② 의존 서비스가 죽는다 → 에이전트는 살아 있지만 기능은 안 된다

```bash
docker compose stop postgres
curl -s localhost:8080/healthz | jq -c .
curl -s "localhost:8080/tcp?host=postgres&port=5432" | jq -c '{ok,error_type}'
docker compose start postgres
```

!!! expect
    ```text
    {"status":"ok","version":"0.2.0","host":"aa4270e1abc2"}
    {"ok":false,"error_type":"gaierror"}
    ```
    `/healthz`는 OK인데 DB는 안 됩니다. **헬스체크가 "프로세스가 살아 있음"만 확인하면 이런 상태를 못 잡습니다.** `gaierror`(이름 해석 실패)인 이유는 컨테이너가 멈추면 도커 DNS에서 그 이름이 빠지기 때문입니다 — Day 4의 3단계 진단에서 1단계 실패에 해당합니다. 정식 운영에서는 의존성까지 확인하는 readiness 개념이 필요하고, 쿠버네티스가 이것을 구분합니다(Day 10).

### ③ 살아 있지만 응답이 없다 → Compose는 못 살린다

```bash
sleep 12; curl -s localhost:8080/_lab/hang
sleep 40                                   # 헬스체크 3회 실패 대기 (10s × 3 + 여유)
docker compose ps agent --format "table {{.Service}}\t{{.Status}}"
curl -s -m3 localhost:8080/healthz; echo "종료코드=$?"
docker inspect day05-agent-1 --format 'RestartCount={{.RestartCount}} Health={{.State.Health.Status}}'
```

!!! fail
    ```text
    {"hang": true}
    SERVICE   STATUS
    agent     Up About a minute (unhealthy)     ← unhealthy인데 재시작되지 않는다
    종료코드=28                                  ← 타임아웃
    RestartCount=1 Health=unhealthy             ← RestartCount가 그대로
    ```
    **이것이 Compose의 결정적 한계입니다.** 도커의 헬스체크는 상태를 "표시"만 하고, `unhealthy`가 되어도 재시작하지 않습니다. 프로세스는 살아 있으므로 `restart` 정책도 발동하지 않습니다. 데드락, GC 정지, 외부 API 대기에 스레드가 전부 묶인 상태가 여기 해당하고, 에이전트에서는 LLM 응답 대기가 쌓이면 실제로 일어납니다. 쿠버네티스의 liveness probe가 이 문제를 해결합니다(Day 10).

```bash
docker compose restart agent          # 사람이 개입해야 한다
sleep 12; docker compose ps agent --format "table {{.Service}}\t{{.Status}}"
```

!!! verified
    세 시나리오 모두 세션 안에서 실행해 위 출력을 확인했습니다.

!!! say
    "Compose 구성은 프로세스가 죽으면 자동 재시작되지만, 응답 없이 멈춘 상태는 사람이 재시작해야 합니다. 파일럿 기간에는 저희가 모니터링하고, 정식 전환 시에는 쿠버네티스(또는 OpenShift)의 liveness probe로 이 부분을 자동화하는 것을 전환 조건에 넣겠습니다."

## 실습 5-3 — 설정을 이미지 밖으로: 재배포 없이 프롬프트 바꾸기

Day 9와 Day 11에서 다시 강조할 원칙입니다. **이미지 재반입 없이 바꿀 수 있는 것과 없는 것을 분리하는 것**이 폐쇄망 프로젝트의 생산성을 좌우합니다. 프롬프트 한 줄 바꾸려고 3일짜리 반입 절차를 다시 타면 튜닝이 불가능합니다.

```bash
curl -s localhost:8080/prompt
echo "추가 지침: 답변은 5문장 이내로." >> config/prompt.txt
sleep 6                                    # 에이전트는 5초 간격으로 파일 변경을 확인한다
curl -s localhost:8080/prompt
docker compose logs agent --tail 3 --no-log-prefix | grep prompt_reloaded
```

!!! expect
    ```text
    당신은 사내 업무 지원 에이전트입니다.
    제공된 데이터에 근거해서만 답하고, 근거가 없으면 모른다고 답하십시오.

    당신은 사내 업무 지원 에이전트입니다.
    제공된 데이터에 근거해서만 답하고, 근거가 없으면 모른다고 답하십시오.
    추가 지침: 답변은 5문장 이내로.

    {"event": "prompt_reloaded", "path": "/app/config/prompt.txt", "sha": "a9099fd31924", ...}
    ```
    이미지 재빌드도, 반입도, 컨테이너 재시작도 없이 반영되었습니다. 애플리케이션이 파일을 다시 읽도록 만들어져 있어야 한다는 조건이 붙습니다(우리 에이전트는 mtime을 확인). 이 조건을 첫 케이스의 애플리케이션에 요구하세요.

| 이미지 안 | 이미지 밖 (볼륨·환경변수) |
|---|---|
| 애플리케이션 코드 | 프롬프트 |
| 라이브러리 의존성 | 평가 rubric, 임계값 |
| 실행 방식 (CMD, USER) | 접속 정보 (DB, LLM 엔드포인트) |
| | 기능 on/off 플래그 |
| | 로그 레벨 |

오른쪽 열은 고객 환경에서 실데이터를 보며 조정해야 하는 것들입니다. 이게 이미지 안에 박혀 있으면 임계값 하나 바꾸는 데 며칠이 걸립니다.

```bash
sed -i '$d' config/prompt.txt     # 원복 (macOS: sed -i '' '$d' config/prompt.txt)
```

## 실습 5-4 — 비밀값과 `docker compose config`

```bash
cat .env.example
# 실제 값은 .env에 (git 제외). 치환 결과를 미리 본다
POSTGRES_PASSWORD=s3cret docker compose config | grep -E "DB_DSN|POSTGRES_PASSWORD"
```

!!! expect
    ```text
          DB_DSN: postgresql://appuser:s3cret@postgres:5432/appdb
          POSTGRES_PASSWORD: s3cret
    ```
    `docker compose config`는 변수 치환·앵커 병합이 끝난 **최종 설정**을 보여 줍니다. "설정이 왜 이렇게 들어갔지?"라는 질문에 답하는 명령이고, 고객사에 인계할 때 이 출력을 첨부하면 오해가 줄어듭니다(비밀값은 가리고).

!!! warn
    `.env` 파일은 `docker compose config` 출력과 `docker inspect`에 평문으로 보입니다. 서버 접근 권한이 있는 사람은 볼 수 있습니다. "비밀을 이미지에 넣지 않는다"(Day 3)는 지켰지만 "서버에 평문으로 있다"는 남습니다. 보안팀이 지적하면 Day 11의 Secret, 그리고 고객사 비밀 관리 솔루션(Vault, 사내 KMS) 연동이 답입니다.

## 눈으로 확인 — lazydocker에서 프로젝트 보기

!!! eye
    **lazydocker → Containers**. 프로젝트 `day05`의 컨테이너 세 개가 한 그룹으로 보이고, 각 행의 상태에 `healthy`/`unhealthy`가 표시됩니다. 컨테이너를 고르고 오른쪽 탭을 <kbd>[</kbd> <kbd>]</kbd>로 넘기면 **Logs**(실시간), **Stats**(CPU·메모리 — `deploy.resources.limits`가 적용됐는지), **Config**(환경변수 — 비밀값이 보임)를 볼 수 있습니다. 실습 5-2 ③을 다시 실행하고 상태가 `unhealthy`로 바뀌는 것을 여기서 보세요.

```screen
# lazydocker — Containers 패널 (프로젝트 day05)
├─Containers──────────────────────┤│ Logs                      Stats   Env   Config   Top
│ ● day05-nginx-1     running     ││ {"event":"request","path":"/healthz","status":200,"ms":0,...}
│ ● day05-agent-1     healthy ◀   ││ {"event":"prompt_reloaded","sha":"a9099fd31924",...}
│ ● day05-postgres-1  healthy     ││ {"event":"request","path":"/prompt","status":200,"ms":0,...}
├─Images──────────────────────────┤│
│ agent:0.2.0                     ││  CPU 0.3%   MEM 38MiB / 512MiB   ← limits.memory 적용됨
```

## 오류 대응

!!! rollback
    - `service "agent" is not healthy` / nginx가 안 뜸 → `docker compose logs agent`로 에이전트가 왜 unhealthy인지 확인. 대개 `config/` 마운트 경로 오타.
    - `port is already allocated` → 8080을 다른 것이 쓰는 중. `compose.yaml`의 `127.0.0.1:8080`을 `127.0.0.1:8090`으로.
    - 헬스체크가 `health: starting`에서 멈춤 → `start_period`·`interval` 대기. 30초는 기다리세요.
    - 완전히 엉켰으면 `docker compose down -v`(볼륨까지 삭제) 후 `up -d`. DB 데이터는 날아갑니다.
    - macOS의 `sed -i`는 `-i ''` 형식입니다.

## 정리

docker compose down          # 볼륨(pgdata)은 유지
