# Day 0 — 환경 준비

<div class="day-meta"><span><b>소요</b> 1~2시간 (이미지 다운로드 시간 별도)</span><span><b>만드는 것</b> 실습 PC 한 대, 학습용 에이전트 이미지</span><span><b>다음</b> Day 1 가상화 계층</span></div>

!!! why
    고객사에 들어가면 "노트북에 뭘 설치해도 되는지"부터 통제받습니다. 그 전에 내 PC에서 전 과정을 한 번 돌려 본 사람과 아닌 사람의 차이는 큽니다. 오늘은 설치만 하는 날이 아니라, 앞으로 14일간 **어떤 도구로 무엇을 보게 되는지** 목록을 손에 쥐는 날입니다.

## 필요한 것

한 대의 PC로 전부 완결됩니다. 메모리 8GB 이상, 여유 디스크 30GB 이상을 권장합니다(이미지가 수 GB, Day 10 이후 k3d 클러스터가 2~3GB를 씁니다).

| 도구 | 버전(고정) | 용도 | 어느 Day부터 |
|---|---|---|---|
| Docker Engine / Docker Desktop | 27 이상 (Compose v2 포함) | 전 실습 | Day 3 |
| `ip` (iproute2) | — | 리눅스 네트워크 실습 | Day 2 |
| k3d | v5.7.4 (k3s v1.30) | 도커 위에 쿠버네티스 | Day 10 |
| kubectl | v1.31.0 | 쿠버네티스 CLI | Day 10 |
| helm | v3.16.2 | 차트 | Day 11 |
| k9s | v0.32.5 | 쿠버네티스 TUI (눈으로 확인) | Day 10 |
| lazydocker | 0.23.3 | 도커 TUI (눈으로 확인) | Day 3 |
| dive | 0.12.0 | 이미지 레이어 탐색 | Day 3 |
| jq, curl, git, python3 | — | 보조 | Day 0 |

trivy(취약점 스캔), mitmproxy(TLS 검사 재현), squid(프록시), registry UI, LiteLLM은 컨테이너로 실행하므로 따로 설치하지 않습니다.

!!! os
    **Windows는 반드시 WSL2(Ubuntu) 안에서 진행하세요.** 고객사 리눅스 서버와 가장 비슷하고, Day 2의 네임스페이스 실습은 리눅스 커널이 있어야 합니다. Docker Desktop을 쓴다면 Settings → Resources → WSL Integration에서 Ubuntu 배포판을 켜 두세요. PowerShell/CMD에서 직접 진행하면 절반의 실습이 동작하지 않습니다.

    **macOS**는 Docker Desktop(또는 OrbStack)을 씁니다. Day 2의 `ip netns` 실습만은 리눅스 커널이 필요하므로 컨테이너 안에서 진행하는 대안 절차를 Day 2에 적어 두었습니다.

    **Linux**는 Docker Engine을 직접 설치합니다. 고객사 서버와 동일한 조건이므로 가장 정확한 결과가 나옵니다.

## 0-1. 한 번에 설치 — 부트스트랩 스크립트

아래 스크립트는 OS를 감지해 없는 도구만 설치하고, 실습 디렉터리를 만들고, 이미지를 미리 받습니다. 여러 번 실행해도 안전합니다.

```bash
mkdir -p ~/onprem-lab && cd ~/onprem-lab
# 부록 F의 압축본을 풀었다면 bootstrap.sh가 이미 있습니다. 없으면 부록 F에서 내용을 복사해 만드세요.
chmod +x bootstrap.sh
./bootstrap.sh check     # 먼저 현재 상태만 본다 (아무것도 바꾸지 않음)
./bootstrap.sh           # 설치 + 디렉터리 + 이미지
```

!!! expect
    `check`의 결과가 전부 ✓ 이면 됩니다. 아래는 Linux에서 실행한 실제 출력입니다.

    ```text
    ==> 도구 점검 (OS=Linux ARCH=amd64 WSL=0)
      ✓ docker Docker version 29.4.3, build 055a478
      ✓ kubectl Client Version: v1.31.0
      ✓ k3d k3d version v5.7.4
      ✓ helm v3.16.2+g13654a5
      ✓ k9s Version              v0.32.5

      ✓ dive dive 0.12.0
      ✓ jq jq-1.7

      ✓ docker 데몬 응답
      ✓ docker compose v2
      ✓ iproute2 (ip)
    ```

!!! verified
    이 스크립트는 Linux(amd64) 경로를 실제로 실행해 확인했습니다. macOS 경로(Homebrew)는 명령이 표준적이지만 세션 안에서 실행하지는 못했습니다.

스크립트 전문은 [부록 F](#부록-f-전체-실습-파일-트리)에 있습니다. 직접 설치하고 싶다면 아래 OS별 절차를 따르세요.

### macOS

```bash
# Homebrew가 없으면 https://brew.sh
brew install --cask docker          # Docker Desktop. 설치 후 한 번 실행해 초기화
brew install kubectl k3d helm k9s lazydocker dive jq
docker --version && docker compose version
```

### Windows + WSL2 (Ubuntu)

```powershell
# PowerShell (관리자) — WSL2와 Ubuntu 설치. 이미 있으면 건너뜀
wsl --install -d Ubuntu
```

이후 **Ubuntu 터미널 안에서** Linux 절차를 그대로 따릅니다. Docker Desktop을 쓰는 경우 WSL Integration을 켜면 Ubuntu 안에서 `docker` 명령이 바로 동작합니다. Docker Desktop 없이 WSL2 안에 Docker Engine을 직접 설치해도 됩니다(아래 Linux 절차의 `get.docker.com`). 어느 쪽이든 실습 결과는 같습니다.

!!! os
    WSL2 + Docker Desktop 조합에서 `host.docker.internal`은 동작하지만, WSL2 안에 Docker Engine을 직접 설치한 경우에는 없습니다. Day 4·8에서 `--add-host=host.docker.internal:host-gateway` 옵션으로 통일합니다.

### Linux (Ubuntu/Debian 계열)

```bash
# Docker Engine
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"      # 로그아웃 후 재로그인 필요
sudo apt-get install -y jq curl git iproute2

# 바이너리 (버전 고정)
ARCH=amd64   # Apple Silicon 위의 VM 등 arm64면 arm64
curl -fsSLo kubectl "https://dl.k8s.io/release/v1.31.0/bin/linux/${ARCH}/kubectl" && sudo install -m 0755 kubectl /usr/local/bin/ && rm kubectl
curl -fsSLo k3d "https://github.com/k3d-io/k3d/releases/download/v5.7.4/k3d-linux-${ARCH}" && sudo install -m 0755 k3d /usr/local/bin/ && rm k3d
curl -fsSL "https://get.helm.sh/helm-v3.16.2-linux-${ARCH}.tar.gz" | tar xz && sudo install -m 0755 linux-${ARCH}/helm /usr/local/bin/ && rm -rf linux-${ARCH}
curl -fsSL "https://github.com/derailed/k9s/releases/download/v0.32.5/k9s_Linux_${ARCH}.tar.gz" | tar xz k9s && sudo install -m 0755 k9s /usr/local/bin/ && rm k9s
curl -fsSL "https://github.com/jesseduffield/lazydocker/releases/download/v0.23.3/lazydocker_0.23.3_Linux_x86_64.tar.gz" | tar xz lazydocker && sudo install -m 0755 lazydocker /usr/local/bin/ && rm lazydocker
curl -fsSL "https://github.com/wagoodman/dive/releases/download/v0.12.0/dive_0.12.0_linux_${ARCH}.tar.gz" | tar xz dive && sudo install -m 0755 dive /usr/local/bin/ && rm dive
```

!!! note
    lazydocker의 arm64 파일명은 `lazydocker_0.23.3_Linux_arm64.tar.gz`입니다. 버전이 오래되어 링크가 죽으면 각 프로젝트의 GitHub Releases 페이지에서 최신 안정 버전으로 바꾸세요. 이 문서의 실습은 메이저 버전이 같으면 동작합니다.

## 0-2. 도커가 실제로 동작하는지

```bash
docker run --rm hashicorp/http-echo:1.0 -version
docker run --rm -d --name hello -p 127.0.0.1:8081:8080 traefik/whoami:v1.10 --port 8080
sleep 1
curl -s localhost:8081
docker rm -f hello
```

!!! expect
    `whoami`는 자기 호스트명과 IP, 받은 요청 헤더를 그대로 출력합니다. 앞으로 "이 요청이 어느 컨테이너에 어떤 헤더로 도착했는가"를 볼 때 계속 쓸 이미지입니다.

    ```text
    Hostname: 3f2a9c1d4e5b
    IP: 127.0.0.1
    IP: 172.17.0.2
    RemoteAddr: 172.17.0.1:54321
    GET / HTTP/1.1
    Host: localhost:8081
    User-Agent: curl/8.5.0
    Accept: */*
    ```

## 0-3. 학습용 에이전트 이미지 한 번 만들기

앞으로 14일 동안 "배포 대상"으로 쓸 최소 에이전트입니다. 로직은 일부러 단순하고, 이 과정에서 코드를 고칠 일은 없습니다. 파일은 `~/onprem-lab/agent/`에 있습니다([부록 F](#부록-f-전체-실습-파일-트리)에 전문).

| 엔드포인트 | 하는 일 | 어느 Day에 쓰는가 |
|---|---|---|
| `GET /healthz` | 생존 확인 | 전부 |
| `GET /diag` | 프록시·CA·LLM·DB **설정 여부**를 보고 (값 자체는 노출하지 않음) | Day 7·8·14 |
| `GET /egress?url=` | 외부 연결이 되는지, 안 되면 어떤 예외인지 | Day 7·8 |
| `GET /tcp?host=&port=` | 특정 호스트:포트에 TCP가 닿는지 | Day 6·12·14 |
| `GET /prompt` | 현재 프롬프트 (파일이 바뀌면 자동 재적재) | Day 5·11 |
| `POST /ask` | LLM 게이트웨이 호출 (없으면 에코) | Day 13·14 |
| `GET /metrics` | Prometheus 형식 요청 수 | Day 13 |

```bash
cd ~/onprem-lab/agent
ls          # app.py  requirements.txt  Dockerfile  .dockerignore
docker build -t agent:0.1.0 .
docker run -d --rm --name agent -p 127.0.0.1:8000:8000 agent:0.1.0
sleep 2
curl -s localhost:8000/healthz
curl -s localhost:8000/diag | jq '{uid, gid, llm_base_url, proxy}'
curl -s -X POST localhost:8000/ask -H 'Content-Type: application/json' -d '{"question":"안녕"}'
docker exec agent id
docker rm -f agent
```

!!! expect
    ```text
    {"status": "ok", "version": "0.1.0", "host": "c657f467d210"}
    {
      "uid": 10001,
      "gid": 0,
      "llm_base_url": "(unset)",
      "proxy": { "HTTP_PROXY": "(unset)", "HTTPS_PROXY": "(unset)", "NO_PROXY": "(unset)", ... }
    }
    {"answer": "(echo) 안녕", "mode": "offline", "prompt_sha": "e3b0c44298fc"}
    uid=10001(appuser) gid=0(root) groups=0(root)
    ```

    `uid=10001`, `gid=0`이 핵심입니다. 이미지는 처음부터 non-root로 동작하고, GID 0으로 실행됩니다. 이것이 왜 보안 심의와 OpenShift에서 중요한지는 Day 3과 Day 12에서 다룹니다.

!!! verified
    이 이미지는 세션 안에서 빌드하고 위 명령을 실제로 실행해 출력을 확인했습니다.

!!! rollback
    - `docker build`가 `pip install` 단계에서 실패하면 **회사 PC의 프록시/TLS 검사** 때문일 가능성이 큽니다. 바로 Day 7·8의 주제이므로, 지금은 `docker build --build-arg HTTPS_PROXY=http://<프록시>:<포트> ...`로 우회하고 Day 8에서 정식으로 해결합니다.
    - 포트 8000이 이미 쓰이고 있으면 `-p 127.0.0.1:8000:8000`의 앞 숫자를 바꾸세요. 컨테이너 안 포트(뒤 숫자)는 그대로 둡니다.
    - 컨테이너 이름 충돌(`Conflict. The container name "/agent" is already in use`)이면 `docker rm -f agent` 후 다시 실행합니다.
