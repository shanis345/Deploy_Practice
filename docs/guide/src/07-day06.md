!!! why

    > "에이전트 서버는 업무망에 두시고요, 사용자 접속은 DMZ의 웹 게이트웨이 거쳐서 들어오게 하세요. DB존은 업무망에서만 열립니다. 인터넷은 프록시 통해서만 나가고, 목적지 화이트리스트 신청하셔야 해요. 방화벽 신청서에 출발지·목적지·포트·용도·기간 적어서 보안팀 결재 받아 주세요."

    이 문단을 그대로 내 PC에 재현해 보면, 방화벽 신청서에 무엇을 적어야 하는지가 손에 잡힙니다. 그리고 한 가지 중요한 판단을 직접 확인합니다 — **에이전트를 DMZ에 두면 안 되는 이유**, 그리고 **클라우드에 두면 협의가 왜 어려운지**.

## 핵심 개념

### 대기업 데이터센터의 전형적인 존 구성

<pre class="diagram">
      인터넷 / 사내 사용자 PC 대역
            │
      [ 방화벽 FW-1 ]
            │
   ┌──── DMZ ────────────────────────────┐   외부(또는 사용자)가 직접 닿는 서버
   │  웹 게이트웨이 · 리버스 프록시 · API GW │   (WAF, L7 스위치가 앞에 붙음)
   └────────────┬────────────────────────┘
      [ 방화벽 FW-2 ]   ← 가장 엄격. DMZ→내부 방향은 특히
            │
   ┌──── 업무망(내부망) ──────────────────┐   내부 시스템. WAS, 사내 포털, ERP API, **에이전트**
   │  agent-vm · erp-api · llm-gateway    │
   └────────────┬────────────────────────┘
      [ 방화벽 FW-3 ]
            │
   ┌──── DB존 ───────────────────────────┐   데이터베이스. 최고 등급 통제. 계정+IP+포트 단위 허용
   │  postgres · oracle                  │
   └─────────────────────────────────────┘

   + 관리망(모니터링·백업·SAC)  + 개발망(개발 서버, 운영망과 분리)  + 인터넷망(사용자 PC의 인터넷 전용)
</pre>

"망분리"라는 말은 두 층위로 쓰입니다. ① 위 그림처럼 **서버 존을 방화벽으로 나눈 것**, ② 국내 금융·공공에서 규제로 요구하는 **업무용 PC망과 인터넷용 PC망의 물리/논리 분리**. 에이전트 배포에서 부딪히는 것은 주로 ①이지만, ②가 있는 고객사에서는 "인터넷망 PC에서만 외부 LLM을 쓸 수 있고 업무망 서버에서는 못 쓴다"는 제약이 추가됩니다. 첫 미팅에서 어느 쪽 이야기인지 확인하세요.

### 방향이 중요하다

방화벽 정책은 **출발지 → 목적지 → 포트** 단위이고, 방향이 다르면 다른 정책입니다. 그리고 안쪽에서 바깥쪽으로 나가는 것보다 **바깥쪽에서 안쪽으로 들어오는 것이 압도적으로 어렵습니다**.

| 방향 | 난이도 | 비고 |
|---|---|---|
| 업무망 → DB존 | 보통 | 계정 발급과 함께 신청. 조회 전용 계정이면 빠름 |
| 업무망 → 인터넷 (프록시 경유) | 보통~어려움 | 목적지 FQDN 화이트리스트. LLM API가 여기 해당 |
| 인터넷 → DMZ | 보통 | 외부 공개 서비스의 정상 경로 |
| DMZ → 업무망 | 어려움 | 강한 근거 필요. 포트 하나, 목적지 하나로 최소화 |
| 클라우드 → 사내 업무망 | 매우 어려움 | 전용선(Direct Connect)이 있어도 별건. 수개월 |
| DB존 → 업무망 (역방향) | 원칙적 불허 | DB가 밖으로 연결을 시작하는 구성은 거의 승인 안 됨 |

**이 표가 아키텍처 결정을 지배합니다.** 에이전트를 클라우드에 두면 클라우드→사내 인바운드가 필요해지고, 이건 가장 어려운 항목입니다. 반대로 에이전트를 업무망에 두면 사내→외부 LLM 아웃바운드 하나만 필요합니다. 그래서 **"에이전트 런타임은 온프렘, LLM만 외부"**가 현실적인 기본값입니다.

같은 이유로 에이전트를 DMZ에 두는 것도 좋지 않습니다. 에이전트는 사내 시스템(ERP, DB)을 호출해야 하는데, DMZ→업무망은 가장 뚫기 어려운 방향입니다. 게다가 DMZ 서버는 "외부에서 닿는 서버"로 취급되어 보안 요건(WAF, 취약점 점검 주기)이 훨씬 무겁습니다.

### 도커 네트워크로 존을 흉내 낼 때의 한계

도커 네트워크의 `internal: true`는 "인터넷으로 나가는 NAT가 없다"는 뜻이고, 서로 다른 네트워크는 라우팅이 없어 격리됩니다. 이것으로 **분리(segmentation)**는 재현되지만 **방향(direction)**은 재현되지 않습니다. 같은 네트워크 안에서는 어느 쪽이든 연결을 시작할 수 있습니다. 실제 방화벽은 방향을 구분하고, 쿠버네티스 NetworkPolicy도 ingress/egress를 구분합니다(Day 12). 오늘 실습에서 이 차이를 직접 봅니다.

## 실습 6-1 — 3존 구조 만들기

```bash
cd ~/onprem-lab/day06
ls    # compose.yaml  gateway.conf  break.sh
```

```yaml
#file: compose.yaml
name: day06

x-log: &logopt
  driver: json-file
  options: { max-size: "10m", max-file: "3" }

services:
  # ── DMZ: 외부 사용자 진입점 ─────────────────────────────────────────
  gateway:
    image: nginx:1.27-alpine
    networks: [dmz, biz]             # DMZ와 업무망 양쪽에 발을 걸침 (리버스 프록시의 정상 위치)
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./gateway.conf:/etc/nginx/conf.d/default.conf:ro
    restart: unless-stopped
    logging: *logopt

  # ── 업무망: 에이전트 본체 ───────────────────────────────────────────
  agent:
    image: agent:0.2.0
    networks: [biz, dbzone]          # 업무망 + DB존. 인터넷 경로 없음
    environment:
      DB_DSN: "postgresql://appuser:apppass@postgres:5432/appdb"
    restart: unless-stopped
    logging: *logopt

  # ── 업무망: 사내 기간계 시스템 흉내 (ERP API) ─────────────────────────
  erp:
    image: traefik/whoami:v1.10
    networks: [biz]
    command: ["--port", "8080", "--name", "erp-api"]
    restart: unless-stopped
    logging: *logopt

  # ── DB존 ───────────────────────────────────────────────────────────
  postgres:
    image: postgres:16.4-alpine
    networks: [dbzone]
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: apppass
      POSTGRES_DB: appdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 10s
      retries: 5
    restart: unless-stopped
    logging: *logopt

  # ── 진단용 단말 (각 존에 하나씩) ─────────────────────────────────────
  probe-dmz:
    image: nicolaka/netshoot:v0.13
    networks: [dmz]
    command: sleep infinity
  probe-biz:
    image: nicolaka/netshoot:v0.13
    networks: [biz]
    command: sleep infinity
  probe-db:
    image: nicolaka/netshoot:v0.13
    networks: [dbzone]
    command: sleep infinity

networks:
  dmz:
    driver: bridge                   # 인터넷과 연결됨 (NAT)
  biz:
    driver: bridge
    internal: true                   # 인터넷 아웃바운드 차단
  dbzone:
    driver: bridge
    internal: true
```

```nginx
#file: gateway.conf
server {
    listen 80;
    location / {
        proxy_pass http://agent:8000/;
        proxy_set_header Host $host;
        proxy_read_timeout 300s;
    }
}
```

```bash
docker compose up -d
sleep 10
docker compose ps --format "table {{.Service}}\t{{.Status}}"
docker network ls --format '{{.Name}} internal={{.Internal}}' | grep day06
```

## 실습 6-2 — 존 간 통신 검증

여기가 오늘의 핵심입니다. 각 경로가 되는지 안 되는지를 **직접** 확인하고 표에 적습니다. 이 표가 방화벽 신청서의 근거가 됩니다.

```bash
echo "① 외부 → DMZ → 에이전트 : 되어야 한다"
curl -s localhost:8080/healthz | jq -c .

echo "② 에이전트 → DB존 : 되어야 한다 (에이전트가 dbzone 소속)"
curl -s "localhost:8080/tcp?host=postgres&port=5432" | jq -c '{ok}'

echo "③ DMZ → DB존 : 안 되어야 한다 (가장 중요한 검증)"
docker compose exec -T probe-dmz sh -c 'nc -z -w3 postgres 5432 && echo "위험: DMZ에서 DB 접근됨" || echo "정상: 차단"'

echo "④ 업무망 → 인터넷 : 안 되어야 한다 (internal: true)"
docker compose exec -T probe-biz sh -c 'nc -z -w3 example.com 80; echo "종료코드=$?"; ip route'

echo "⑤ 에이전트 → ERP : 되어야 한다 (둘 다 biz 소속)"
docker compose exec -T probe-biz sh -c 'curl -s -m3 http://erp:8080 | head -2'

echo "⑥ 에이전트 → 인터넷 : 안 되어야 한다"
curl -s "localhost:8080/egress?url=http://example.com" | jq -c '{ok,error_type}'

echo "⑦ DB존 → 에이전트 (역방향) : 실제 방화벽이면 차단, 도커에서는?"
docker compose exec -T probe-db sh -c 'nc -z -w3 agent 8000 && echo "열림" || echo "차단"'
```

!!! expect
    ```text
    ① {"status":"ok","version":"0.2.0","host":"1ba7d44b8f06"}
    ② {"ok":true}
    ③ nc: getaddrinfo for host "postgres" port 5432: Name does not resolve
       정상: 차단
    ④ nc: getaddrinfo for host "example.com" port 80: Try again
       종료코드=1
       172.20.0.0/16 dev eth0 proto kernel scope link src 172.20.0.3     ← default route가 없다 (Day 2)
    ⑤ Name: erp-api
       Hostname: aa109ce9bff5
    ⑥ {"ok":false,"error_type":"gaierror"}
    ⑦ Connection to agent (172.18.0.4) 8000 port [tcp/*] succeeded!
       열림
    ```
    ③④⑥이 차단되고 ①②⑤가 통과하면 구조가 맞습니다. 차단의 형태가 "타임아웃"이 아니라 "이름 해석 실패"인 점을 눈여겨보세요 — 도커 DNS는 같은 네트워크의 이름만 알려 줍니다.

    ⑦은 **열립니다.** 에이전트가 DB존 네트워크에 발을 걸치고 있으므로 DB존의 다른 컨테이너가 에이전트 쪽으로 연결을 시작할 수 있습니다. 실제 고객사 방화벽은 "업무망→DB존 5432"만 허용하고 역방향은 막습니다. 도커 네트워크는 방향을 모른다는 것을 여기서 확인해 두세요. Day 12의 NetworkPolicy가 이 차이를 메웁니다.

## 실습 6-3 — 실무에서 자주 생기는 설정 실수

에이전트의 `networks`에 `dmz`를 하나 더 붙여 봅니다. "게이트웨이가 에이전트를 못 찾길래 같은 네트워크에 넣어 줬다"는, 현장에서 실제로 자주 일어나는 수정입니다.

```bash
cp compose.yaml compose.yaml.bak
sed -i 's/networks: \[biz, dbzone\]          # 업무망 + DB존. 인터넷 경로 없음/networks: [dmz, biz, dbzone]/' compose.yaml
# macOS: sed -i '' 's/.../.../' compose.yaml
docker compose up -d agent && sleep 6
curl -s "localhost:8080/egress?url=http://example.com" | jq -c '{ok,status}'
```

!!! fail
    ```text
    {"ok":true,"status":200}
    ```
    아무 오류도 없이, 조용히 **통제 밖의 경로**가 생겼습니다. 에이전트가 프록시(Day 7)를 거치지 않고 인터넷에 직접 나갑니다. 사용자 진입도 여전히 잘 되고, 헬스체크도 정상입니다. 이런 실수는 증상이 없어서 보안 감사에서 발견됩니다. **"동작한다"와 "통제된다"는 다릅니다.**

```bash
cp compose.yaml.bak compose.yaml && rm compose.yaml.bak
docker compose up -d agent && sleep 6
curl -s "localhost:8080/egress?url=http://example.com" | jq -c '{ok,error_type}'    # 다시 차단
```

이 상태 — 에이전트는 인터넷에 직접 못 나가고, 외부로 나가는 유일한 길은 Day 7에서 만들 프록시 — 가 우리가 원하는 구성입니다.

!!! verified
    실습 6-1~6-3은 세션 안에서 실행해 위 출력을 확인했습니다.

## 실습 6-4 — 방화벽 신청서 만들기

지금 만든 구조를 고객사 양식에 맞춰 적어 봅니다. 첫 케이스 1주 차에 그대로 쓸 수 있는 형태이며, 전체 템플릿은 [부록 E-2](#e-2-방화벽-정책-신청서)에 있습니다.

| # | 출발지 | 목적지 | 포트/프로토콜 | 용도 | 방향 | 기간 |
|---|---|---|---|---|---|---|
| 1 | 사내 사용자 PC 대역 (10.10.0.0/16) | GW-VM (DMZ, 10.1.1.10) | 443/TCP | 사용자 웹 접근 | 인바운드 | 파일럿 종료일까지 |
| 2 | GW-VM (DMZ) | AGENT-VM (업무망, 10.20.5.11) | 8000/TCP | 리버스 프록시 → 에이전트 | DMZ→내부 | 〃 |
| 3 | AGENT-VM (업무망) | DB-SVR (DB존, 10.30.1.5) | 5432/TCP | 조회 전용 계정 `ro_agent` | 내부→DB | 〃 |
| 4 | AGENT-VM (업무망) | ERP-API (업무망, 10.20.3.20) | 443/TCP | 업무 데이터 조회 | 내부 | 〃 |
| 5 | AGENT-VM (업무망) | 사내 프록시 (10.20.0.8) | 3128/TCP | LLM 호출 아웃바운드 (목적지 FQDN 목록 별첨) | 아웃바운드 | 〃 |
| 6 | AGENT-VM (업무망) | 사내 레지스트리 Harbor (10.20.0.30) | 443/TCP | 컨테이너 이미지 수신 | 내부 | 〃 |
| 7 | AGENT-VM (업무망) | 로그 수집 서버 (관리망, 10.99.1.7) | 9200/TCP | 감사 로그 전송 | 내부→관리망 | 〃 |

**신청 시 함께 준비할 것**

- 데이터 흐름도 1장 — 존 경계를 넘는 화살표마다 번호를 위 표와 일치시킵니다. [부록 E-3](#e-3-보안-협의-패키지)의 양식.
- 각 연결의 최소 권한 근거 — 예: 3번은 읽기 전용 계정, 특정 스키마만.
- 5번의 목적지 FQDN 목록 — IP가 바뀌는 SaaS는 FQDN 기반 허용을 요청합니다. **Day 13에서 이 목록을 1개로 줄이는 설계**를 합니다.
- 종료 시점 — "파일럿 종료 후 회수" 조건을 먼저 제시하면 승인 속도가 눈에 띄게 빨라집니다. "언제 닫힐지 정해진 구멍"은 승인 부담이 훨씬 작습니다.

!!! say
    "에이전트는 업무망에 두고, 사용자 진입은 DMZ 게이트웨이 한 곳, 외부로 나가는 경로는 사내 프록시 한 곳입니다. 방화벽 정책은 7건이고 전부 파일럿 종료일에 회수 조건입니다. 데이터 흐름도에 번호를 맞춰 두었습니다."

!!! check
    - 출발지를 **VM IP**로 적을지 **대역**으로 적을지는 고객사 관례를 따릅니다. 컨테이너 IP는 적지 않습니다(Day 2 — NAT로 VM IP가 됩니다).
    - 쿠버네티스/OpenShift 환경이면 출발지는 "노드 대역" 또는 "egress IP"가 됩니다. Day 12에서 확인 항목으로 다룹니다.
    - 방화벽 신청과 별개로 **L4/L7 스위치·WAF 정책**이 있는 고객사가 많습니다. 1번 경로에 WAF가 있으면 에이전트의 긴 응답·SSE 스트리밍이 WAF 타임아웃에 걸릴 수 있습니다(Day 11).
