## 핵심 개념

### ConfigMap과 Secret

| | ConfigMap | Secret |
|---|---|---|
| 용도 | 설정값, 프롬프트, rubric | 비밀번호, API 키, 인증서 |
| 저장 | 평문 | base64 인코딩 (**암호화 아님**) |
| 크기 제한 | 1 MiB | 1 MiB |
| 쓰는 방법 | 환경변수 또는 파일 마운트 | 환경변수 또는 파일 마운트 |

**Secret은 암호화가 아닙니다.** base64는 인코딩일 뿐이라 누구나 디코딩할 수 있습니다. 실제 보호는 RBAC(누가 Secret을 읽을 수 있는가)과 etcd 암호화 설정(클러스터 수준)으로 합니다. 고객사 보안팀이 이 점을 지적하면 아래처럼 답하세요.

!!! say
    "Secret 자체는 인코딩이므로 접근 통제는 RBAC으로 하고, 저장 암호화는 클러스터의 etcd encryption 설정을 따릅니다. 더 강한 요건이면 사내 비밀 관리(Vault, KMS)와 External Secrets Operator로 연동할 수 있습니다. Secret은 git에 커밋하지 않고 `kubectl create secret`으로 클러스터에서 직접 만듭니다."

### 환경변수 vs 파일 마운트 — 어느 쪽으로 넣을 것인가

| 방식 | 장점 | 단점 |
|---|---|---|
| 환경변수 | 간단 | **값을 바꾸면 Pod 재시작 필요** |
| 파일 마운트 | 파일 내용이 자동 갱신됨 (약 1분 내) | 애플리케이션이 파일을 다시 읽어야 함 |

프롬프트나 rubric처럼 **자주 바꿀 것은 파일 마운트**로 두고, 애플리케이션이 파일 변경을 감지하게 만드세요(우리 에이전트는 mtime 확인). 그러면 Pod 재시작 없이 반영됩니다. 로그 레벨이나 모델명처럼 가끔 바꾸는 것은 환경변수로 두고 `rollout restart`(무중단)로 반영합니다. 이 구분이 현장에서 체감 생산성 차이를 만듭니다.

### Ingress — 온프렘의 사용자 진입 경로

<pre class="diagram">
  사용자 PC ── 사내 DNS (agent.corp.local → 사내 LB VIP)
                │
          [사내 L4/L7 로드밸런서 · WAF]        ← 플랫폼/네트워크팀 소관. 타임아웃·버퍼링 협의 필요
                │
          [Ingress 컨트롤러 (nginx / Traefik / OpenShift Router)]   ← 클러스터 안. 우리가 Ingress 리소스로 규칙을 줌
                │  host: agent.corp.local, path: /
          [Service agent:8000] ── Pod, Pod
</pre>

| 항목 | 확인할 것 |
|---|---|
| Ingress 컨트롤러 종류 | `kubectl get ingressclass`. nginx? Traefik? OpenShift Route? — **어노테이션 문법이 다름** |
| 도메인 | 사내 DNS 등록 신청 필요 (리드타임 며칠) |
| TLS 인증서 | 사내 CA 발급 인증서를 Secret(`kubernetes.io/tls`)으로 등록. 자동 발급(cert-manager) 여부 |
| 타임아웃 | 에이전트는 응답이 길다. Ingress·LB·WAF **세 곳 모두** 300초 이상으로 |
| SSE/WebSocket | 버퍼링 해제 필요. 안 하면 스트리밍이 끝날 때까지 아무것도 안 보임 |
| 경로 재작성 | `/agent/` 하위로 붙이라는 요구가 흔함. 앱이 prefix를 지원해야 함 |

### Helm — 고객사 배포의 표준 형식

Helm 차트는 매니페스트의 **템플릿 + 값(values)** 입니다. 실무적 가치는 **같은 차트로 개발·파일럿·운영 환경을 values 파일만 바꿔 배포**하는 것입니다. Day 9의 "이미지는 그대로, 설정만 바꾼다"가 환경 단위로 확장된 형태이고, 플랫폼팀이 "차트로 주세요"라고 하는 이유는 그들의 배포 파이프라인(ArgoCD, Jenkins)이 차트를 입력으로 받기 때문입니다.

## 실습 11-1 — 프롬프트를 ConfigMap으로, 비밀은 Secret으로

Day 10의 클러스터와 `ax-pilot` 네임스페이스를 그대로 씁니다.

```bash
mkdir -p ~/onprem-lab/day11 && cd ~/onprem-lab/day11
```

```yaml
#file: 30-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: agent-config
  namespace: ax-pilot
data:
  # 자주 바뀌는 것: 파일로 마운트 → Pod 재시작 없이 반영
  prompt.txt: |
    당신은 사내 업무 지원 에이전트입니다.
    근거가 없는 내용은 추측하지 말고 모른다고 답하십시오.
    답변은 5문장 이내로 작성하십시오.
  rubric.yaml: |
    thresholds:
      min_confidence: 0.7
      max_retries: 3
    weights:
      grounding: 0.5
      completeness: 0.3
      format: 0.2
  # 잘 안 바뀌는 것: 환경변수로 → 바꾸면 rollout restart 필요
  LOG_LEVEL: "INFO"
  LLM_MODEL: "gpt-4o-mini"
```

Secret은 파일로 커밋하지 않고 명령으로 만듭니다(`31-secret.example.yaml`은 형식 참고용).

```bash
kubectl apply -f 30-configmap.yaml
kubectl -n ax-pilot create secret generic agent-secret \
  --from-literal=LLM_API_KEY='sk-dummy-for-lab' \
  --from-literal=DB_DSN='postgresql://appuser:apppass@postgres:5432/appdb'
```

Deployment는 Day 10의 것을 통째로 교체합니다(`11-deployment.yaml`, 전문은 [부록 F](#부록-f-전체-실습-파일-트리)). 바뀐 부분만 보면:

```yaml
#file: 11-deployment.yaml (바뀐 부분)
          env:
            - { name: PROMPT_PATH, value: /app/config/prompt.txt }
            - { name: RUBRIC_PATH, value: /app/config/rubric.yaml }
            - name: LOG_LEVEL                              # ConfigMap의 키를 환경변수로
              valueFrom: { configMapKeyRef: { name: agent-config, key: LOG_LEVEL } }
            - name: LLM_MODEL
              valueFrom: { configMapKeyRef: { name: agent-config, key: LLM_MODEL } }
            - name: LLM_API_KEY                            # Secret의 키를 환경변수로
              valueFrom: { secretKeyRef: { name: agent-secret, key: LLM_API_KEY } }
            - name: DB_DSN
              valueFrom: { secretKeyRef: { name: agent-secret, key: DB_DSN } }
          volumeMounts:
            - { name: tmp, mountPath: /app/tmp }
            - { name: config, mountPath: /app/config, readOnly: true }   # ConfigMap을 파일로
      volumes:
        - { name: tmp, emptyDir: {} }
        - name: config
          configMap:
            name: agent-config
            items:                                          # 파일로 낼 키만 고른다 (환경변수용 키는 제외)
              - { key: prompt.txt, path: prompt.txt }
              - { key: rubric.yaml, path: rubric.yaml }
```

```bash
kubectl apply -f 11-deployment.yaml
kubectl -n ax-pilot rollout status deployment/agent
kubectl -n ax-pilot exec probe -- sh -c 'curl -s http://agent:8000/diag | jq "{prompt_exists, prompt_sha, rubric: .rubric.thresholds, llm_key_set, db_dsn_set, log_level}"'

# Secret은 base64일 뿐
kubectl -n ax-pilot get secret agent-secret -o jsonpath='{.data.LLM_API_KEY}' | base64 -d; echo
```

!!! expect
    ```text
    {
      "prompt_exists": true,
      "prompt_sha": "07515128d5c0",
      "rubric": { "min_confidence": 0.7, "max_retries": 3 },
      "llm_key_set": true,
      "db_dsn_set": true,
      "log_level": "INFO"
    }
    sk-dummy-for-lab                     ← 네임스페이스에 get secret 권한이 있으면 누구나 본다
    ```

!!! note
    `probe` Pod가 없으면 Day 10 실습 10-3의 명령으로 다시 만드세요. `readOnlyRootFilesystem: true`인데 ConfigMap 마운트가 되는 이유는 마운트된 볼륨은 루트 파일시스템이 아니기 때문입니다.

## 실습 11-2 — 재배포 없이 프롬프트 바꾸기

오늘의 핵심 실습입니다.

```bash
kubectl -n ax-pilot patch configmap agent-config --type merge -p '{"data":{"prompt.txt":"당신은 사내 업무 지원 에이전트입니다.\n반드시 출처를 함께 제시하십시오.\n확인되지 않은 수치는 제시하지 마십시오.\n"}}'

# 반영될 때까지 관찰 (kubelet이 약 1분 주기로 마운트를 갱신하고, 에이전트가 5초 주기로 파일을 확인)
START=$(date +%s)
for i in $(seq 1 24); do
  S=$(kubectl -n ax-pilot exec probe -- curl -s http://agent:8000/diag | jq -r .prompt_sha)
  [ "$S" != "07515128d5c0" ] && { echo "반영됨: $(( $(date +%s) - START ))초 후, prompt_sha=$S"; break; }
  sleep 5
done
kubectl -n ax-pilot exec probe -- curl -s http://agent:8000/prompt
kubectl -n ax-pilot get pods -l app=agent -o custom-columns=NAME:.metadata.name,RESTARTS:.status.containerStatuses[0].restartCount
```

!!! expect
    ```text
    configmap/agent-config patched
    반영됨: 63초 후, prompt_sha=89275b04355f
    당신은 사내 업무 지원 에이전트입니다.
    반드시 출처를 함께 제시하십시오.
    확인되지 않은 수치는 제시하지 마십시오.
    NAME                     RESTARTS
    agent-5fccddd5df-gxqfx   0
    agent-5fccddd5df-mh52x   0
    ```
    **이미지 재빌드도, 반입도, Pod 재시작도 없이** 1분 안에 반영되었습니다. RESTARTS가 0입니다. 조건은 애플리케이션이 파일을 다시 읽는 것뿐입니다.

환경변수로 넣은 값은 이 방식으로 안 바뀝니다.

```bash
kubectl -n ax-pilot patch configmap agent-config --type merge -p '{"data":{"LOG_LEVEL":"DEBUG"}}'
sleep 5; kubectl -n ax-pilot exec probe -- curl -s http://agent:8000/diag | jq -r .log_level    # 여전히 INFO
kubectl -n ax-pilot rollout restart deployment/agent          # 무중단 롤링 재시작
kubectl -n ax-pilot rollout status deployment/agent
kubectl -n ax-pilot exec probe -- curl -s http://agent:8000/diag | jq -r .log_level    # DEBUG
```

!!! expect
    ```text
    INFO
    deployment.apps/agent restarted
    deployment "agent" successfully rolled out
    DEBUG
    ```
    `rollout restart`는 롤링 방식이라 서비스 중단이 없습니다. Compose의 `restart`(Day 5)와 다른 점입니다.

!!! tip
    `subPath`로 파일 하나만 마운트하면(`mountPath: /app/config/prompt.txt, subPath: prompt.txt`) **자동 갱신이 되지 않습니다.** 디렉터리 단위로 마운트해야 갱신됩니다. 현장에서 "ConfigMap을 바꿨는데 반영이 안 된다"의 흔한 원인입니다.

## 실습 11-3 — Ingress로 사용자 진입점 만들기

```yaml
#file: 40-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: agent
  namespace: ax-pilot
  annotations:
    # ── nginx ingress controller (국내 고객사에서 가장 흔함) ─────────────────
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"     # 에이전트 응답은 길다 (기본 60초 → 504)
    nginx.ingress.kubernetes.io/proxy-send-timeout: "300"
    nginx.ingress.kubernetes.io/proxy-body-size: "20m"
    nginx.ingress.kubernetes.io/proxy-buffering: "off"        # SSE 스트리밍이면 필수
    # ── Traefik (k3d/k3s 기본) 은 어노테이션 대신 아래 ServersTransport/Middleware 를 쓴다 ──
spec:
  ingressClassName: traefik          # 고객사에서는 nginx 등, `kubectl get ingressclass` 로 확인
  rules:
    - host: agent.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: agent
                port:
                  number: 8000
```

```bash
kubectl get ingressclass
kubectl apply -f 40-ingress.yaml && sleep 5
kubectl -n ax-pilot get ingress

# k3d가 호스트 8080 → 클러스터 80 으로 연결해 두었으므로 Host 헤더만 맞추면 된다
curl -s -H "Host: agent.local" http://localhost:8080/healthz | jq -c .
curl -s -o /dev/null -w "Host 헤더 없이: %{http_code}\n" http://localhost:8080/healthz
```

!!! expect
    ```text
    NAME      CONTROLLER                      PARAMETERS   AGE
    traefik   traefik.io/ingress-controller   <none>       18m
    NAME    CLASS     HOSTS         ADDRESS     PORTS   AGE
    agent   traefik   agent.local   172.18.0.2  80      6s
    {"status":"ok","version":"0.2.0","host":"agent-847948fc5b-nccbp"}
    Host 헤더 없이: 404               ← Ingress는 호스트 이름으로 라우팅한다
    ```
    고객사에서는 `agent.local` 대신 사내 DNS에 등록한 이름(`agent-pilot.corp.local`)이 되고, 그 이름이 사내 LB의 VIP를 가리키고, LB가 Ingress 컨트롤러 노드로 보냅니다. **사내 DNS 등록과 LB 설정은 우리가 할 수 없고 신청해야 합니다** — 부록 A 질문지에 있습니다.

Traefik에서 백엔드 타임아웃을 늘리는 방법은 어노테이션이 아니라 별도 리소스입니다. 고객사가 nginx 컨트롤러라면 위 어노테이션으로 충분합니다.

```yaml
#file: 41-traefik-transport.yaml
# Traefik 전용: 백엔드 응답 대기 시간을 늘린다. nginx 컨트롤러라면 40-ingress.yaml 의 어노테이션으로 충분.
apiVersion: traefik.io/v1alpha1
kind: ServersTransport
metadata:
  name: agent-slow
  namespace: ax-pilot
spec:
  forwardingTimeouts:
    responseHeaderTimeout: 300s
    dialTimeout: 10s
```

```bash
kubectl apply -f 41-traefik-transport.yaml
kubectl -n ax-pilot annotate service agent traefik.ingress.kubernetes.io/service.serverstransport=ax-pilot-agent-slow@kubernetescrd --overwrite
```

!!! check
    - **컨트롤러 종류에 따라 타임아웃 설정 위치가 다릅니다.** nginx: Ingress 어노테이션. Traefik: ServersTransport. OpenShift Route: `haproxy.router.openshift.io/timeout: 300s` 어노테이션. 첫 미팅에서 종류를 확인하고 해당 문법을 준비하세요.
    - Ingress 앞의 **사내 LB와 WAF의 타임아웃**은 별도입니다. Ingress를 300초로 늘려도 LB가 60초면 60초에 끊깁니다. 세 곳을 전부 확인하세요.
    - TLS: 고객사 표준은 보통 "LB에서 TLS 종료(사내 CA 인증서), LB→Ingress는 HTTP" 또는 "Ingress에서 TLS 종료(Secret에 인증서)". 어느 쪽인지에 따라 인증서를 누가 관리하는지가 달라집니다.

!!! verified
    실습 11-1~11-3은 k3s(Traefik 포함)에서 실행해 위 출력을 확인했습니다. nginx 컨트롤러 어노테이션은 문법이 표준적이지만 세션에 nginx 컨트롤러가 없어 동작을 확인하지는 못했습니다.

## 실습 11-4 — Helm 차트 만들기

Day 10·11의 매니페스트를 템플릿으로 바꾼 최소 차트입니다. `helm create`가 만드는 예제는 너무 크므로 직접 씁니다. 전문은 [부록 F](#부록-f-전체-실습-파일-트리)의 `day11/ax-agent/`에 있습니다.

```text
ax-agent/
├── Chart.yaml              # 이름, 차트 버전, 앱 버전
├── values.yaml             # 기본값
└── templates/
    ├── _helpers.tpl        # 이름·라벨 헬퍼
    ├── configmap.yaml
```

!!! check
    - 플랫폼팀이 **차트 저장소(Harbor의 OCI 차트, ChartMuseum, Nexus)**를 요구하는지, 아니면 git 경로면 되는지.
    - values 파일 중 비밀값(`imagePullSecrets`, DB 비밀번호)을 어떻게 전달하는지 — 보통 Secret은 플랫폼팀이 만들고 우리는 이름만 참조합니다.
    - 네임스페이스에 **ResourceQuota / LimitRange**가 걸려 있으면 `resources`를 반드시 채워야 Pod가 뜹니다(없으면 `Pending`이 아니라 생성 자체가 거부됨).

## 눈으로 확인 — k9s에서 ConfigMap과 Ingress

!!! eye
    `k9s -n ax-pilot`에서 `:cm`(ConfigMap) → `agent-config` 선택 → `y`로 YAML을 보면 방금 patch한 내용이 보입니다. `:ing`에서 Ingress의 HOSTS·ADDRESS를 확인하고, `:secrets` → `agent-secret` → `x`(decode)를 누르면 base64가 풀린 값이 보입니다 — **Secret이 암호화가 아님을 눈으로 확인하는 가장 빠른 방법**입니다. `:helm`은 릴리스 목록입니다.

## 오류 대응

!!! rollback
    - `CreateContainerConfigError` → ConfigMap/Secret 이름 오타. `kubectl -n ax-pilot get cm,secret`으로 존재 확인.
    - 프롬프트가 1분이 지나도 안 바뀜 → `subPath` 마운트인지, 애플리케이션이 파일을 다시 읽는지(`/diag`의 `prompt_sha`) 확인.
    - Ingress `ADDRESS`가 비어 있음 → 컨트롤러가 없거나 `ingressClassName` 불일치. `kubectl get ingressclass`.
    - `curl -H Host:` 가 404 → Ingress의 `host`와 헤더가 다름. 503 → Service 이름/포트 불일치 또는 Pod가 not ready.
    - `helm install`이 `already exists` → 같은 이름의 리소스가 있음. 릴리스 이름을 바꾸거나 기존 리소스 삭제.
    - `helm upgrade` 후 Pod가 안 바뀜 → checksum 어노테이션이 템플릿에 있는지 확인.
