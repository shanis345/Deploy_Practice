# Day 4 — Docker 네트워크와 진단 3단계

<div class="day-meta"><span><b>소요</b> 2시간</span><span><b>만드는 것</b> 손에 익은 진단 순서 (이름 → 포트 → 응답)</span><span><b>눈으로</b> lazydocker Networks, <code>docker network inspect</code></span></div>

!!! why
    고객 환경에서 발생하는 문제의 대부분은 네트워크 문제이고, 그 대화는 보통 이렇게 시작합니다.

    > "컨테이너에서 DB가 안 붙습니다." — "방화벽은 열어드렸는데요? 서버에서는 telnet 되던데."

    서버(호스트)에서는 되는데 컨테이너에서는 안 되는 상황. 원인은 여러 가지지만, Day 2에서 손으로 만든 구조를 도커의 언어로 다시 보면 대부분 진단할 수 있습니다. 오늘의 진짜 산출물은 명령이 아니라 **순서**입니다. 이름이 풀리는가 → 포트가 열려 있는가 → 애플리케이션이 응답하는가. 이 순서로 확인한 결과를 적어서 전달하면 "안 됩니다"보다 열 배 빨리 해결됩니다.

## 핵심 개념

### 네트워크 드라이버

| 드라이버 | 동작 | 언제 쓰나 |
|---|---|---|
| `bridge` | 도커가 만든 가상 스위치(Day 2의 br-lab)에 연결. 기본값 | 대부분 |
| `host` | 호스트의 네트워크 네임스페이스를 그대로 사용. 격리 없음 | 성능이 극단적으로 중요할 때, 또는 진단용 |
| `none` | 네트워크 없음 | 완전 격리 (Day 9의 오프라인 빌드 검증) |
| `overlay` | 여러 호스트에 걸친 네트워크 | Swarm. 대기업에서는 쿠버네티스가 이 역할 |
| `macvlan` | 컨테이너에 물리 네트워크의 IP를 직접 부여 | 드묾. 고객사 네트워크팀이 싫어함 |

### 기본 bridge와 사용자 정의 bridge의 결정적 차이

**사용자 정의 네트워크에서는 컨테이너 이름이 DNS 이름으로 동작합니다.** 기본 `bridge`에서는 안 됩니다(Day 2에서 본 `resolv.conf` 차이). 실무에서는 항상 사용자 정의 네트워크를 만들어 쓰고, Compose는 자동으로 만들어 줍니다.

```text
사용자 정의 네트워크:  http://llm-gateway:4000  → 동작
기본 bridge:          http://llm-gateway:4000  → 이름 해석 실패 (curl 종료코드 6)
```

### 포트 게시(publish)의 의미

```text
-p 127.0.0.1:8080:80
    │         │    └─ 컨테이너 안의 포트
    │         └────── 호스트의 포트
    └──────────────── 호스트의 어느 주소에 열 것인가 (생략하면 0.0.0.0 = 모든 곳)
```

**컨테이너끼리 통신할 때는 포트 게시가 필요 없습니다.** 같은 네트워크에 있으면 컨테이너 포트로 바로 붙습니다. 포트 게시는 "호스트 바깥에서 들어오는 것"을 위한 것입니다. 이걸 모르면 고객사에 "포트를 30개 열어주세요"라고 요청하는 사고가 납니다. 실제로는 사용자가 접근하는 입구 하나만 열면 됩니다.

고객 환경에서는 `127.0.0.1:`을 붙여 호스트 내부에서만 접근되게 두고, 앞단의 리버스 프록시(nginx)나 사내 로드밸런서만 외부에 노출하는 구성이 안전합니다. `0.0.0.0`으로 열면 도커가 **호스트 방화벽(iptables)을 우회해서** 그 포트를 외부에 여는데, 이것이 고객사 보안팀이 도커를 경계하는 이유 중 하나입니다.

### 컨테이너 안의 `localhost`는 호스트가 아니다

컨테이너 안의 `127.0.0.1`은 컨테이너 자기 자신입니다. 호스트에서 돌고 있는 것(예: 호스트에 설치된 DB, 사내 에이전트)을 가리키려면 `host.docker.internal`을 쓰는데, 두 가지 조건이 더 있습니다.

| 조건 | 설명 |
|---|---|
| 이름이 존재해야 함 | Docker Desktop은 기본 제공. Linux Docker Engine은 `--add-host=host.docker.internal:host-gateway` 필요 |
| 호스트 서비스가 `0.0.0.0`(또는 브리지 IP)에 바인딩되어 있어야 함 | `127.0.0.1`에만 리슨하는 서비스는 컨테이너에서 못 붙음 |

## 실습 4-1 — 이름으로 통신하기

```bash
mkdir -p ~/onprem-lab/day04 && cd ~/onprem-lab/day04

# 사용자 정의 네트워크 + 웹 서버 + 진단용 컨테이너
docker network create lab-net
docker run -d --name web    --network lab-net nginx:1.27-alpine
docker run -d --name client --network lab-net nicolaka/netshoot:v0.13 sleep 3600

docker exec client curl -s -o /dev/null -w "%{http_code}\n" http://web
docker exec client nslookup web | tail -2
```

!!! expect
    ```text
    200
    Name:	web
    Address: 172.18.0.2
    ```

이번엔 기본 네트워크에서 같은 것을 해 봅니다.

```bash
docker run -d --name web2    nginx:1.27-alpine
docker run -d --name client2 nicolaka/netshoot:v0.13 sleep 3600
docker exec client2 curl -s -m3 http://web2; echo "종료코드=$?"
docker exec client2 nslookup web2 2>&1 | tail -1
```

!!! fail
    ```text
    종료코드=6                                  ← curl 6 = Could not resolve host
    ** server can't find web2: NXDOMAIN
    ```
    같은 도커, 같은 이미지인데 기본 bridge에서는 이름이 안 풀립니다. "로컬에서는 됐는데 고객사 서버에서 안 된다"의 한 원인이 `docker run`을 `--network` 없이 실행한 것입니다.

## 실습 4-2 — 격리와 양쪽 붙이기

```bash
docker network create other-net
docker run -d --name isolated --network other-net nicolaka/netshoot:v0.13 sleep 3600

# 다른 네트워크의 컨테이너에는 못 붙는다
docker exec isolated curl -s -m3 http://web; echo "종료코드=$?"

# 컨테이너를 두 네트워크에 동시에 연결하면 가능해진다
docker network connect lab-net isolated
docker exec isolated curl -s -o /dev/null -w "%{http_code}\n" http://web
docker exec isolated ip -brief addr | grep eth
```

!!! expect
    ```text
    종료코드=6              ← 이름조차 못 푼다 (다른 네트워크의 DNS 항목이 없음)
    200                     ← 연결 후 성공
    eth0@if97   UP   172.19.0.2/16   ← other-net
    eth1@if98   UP   172.18.0.4/16   ← lab-net. 랜선이 두 개 꽂힌 서버
    ```
    **이 마지막 동작이 Day 6의 핵심입니다.** 고객사 망분리 구조에서 "업무망과 DB존 양쪽에 붙은 애플리케이션 서버"가 정확히 이 모습이고, 반대로 "붙으면 안 되는 네트워크에 실수로 붙은 컨테이너"도 이 모습입니다.

## 실습 4-3 — 포트 게시와 바인딩 주소

```bash
docker run -d --name pub  -p 127.0.0.1:8080:80 nginx:1.27-alpine
docker run -d --name pub2 -p 8081:80           nginx:1.27-alpine
docker port pub; docker port pub2

# 호스트에서 실제로 무엇이 리슨하는가
sudo ss -ltnp | grep -E "8080|8081"

HOSTIP=$(hostname -I 2>/dev/null | awk '{print $1}')   # macOS: ipconfig getifaddr en0
curl -s -o /dev/null -w "127.0.0.1:8080 → %{http_code}\n" http://127.0.0.1:8080
curl -s -m2 -o /dev/null -w "$HOSTIP:8080 → %{http_code}\n" http://$HOSTIP:8080; echo "종료코드=$?"
curl -s -m2 -o /dev/null -w "$HOSTIP:8081 → %{http_code}\n" http://$HOSTIP:8081

# 컨테이너끼리는 게시가 없어도 통신한다
docker exec client curl -s -o /dev/null -w "client→web:80 (게시 안 함) %{http_code}\n" http://web:80
```

!!! expect
    ```text
    80/tcp -> 127.0.0.1:8080
    80/tcp -> 0.0.0.0:8081
    LISTEN 0 4096   127.0.0.1:8080   0.0.0.0:*   users:(("docker-proxy",pid=12620,fd=9))
    LISTEN 0 4096     0.0.0.0:8081   0.0.0.0:*   users:(("docker-proxy",pid=12705,fd=9))
    127.0.0.1:8080 → 200
    192.0.2.2:8080 → 000      ← 호스트 IP로는 안 열림
    종료코드=7                 ← curl 7 = Failed to connect
    192.0.2.2:8081 → 200      ← 0.0.0.0은 어디서나 열림
    client→web:80 (게시 안 함) 200
    ```
    `ss` 출력의 `docker-proxy`가 호스트 포트를 컨테이너로 넘겨주는 프로세스입니다. 고객사 인프라팀이 "이 서버에 8081이 열려 있는데 누가 열었나요?"라고 물으면 이 출력을 보여 주면 됩니다.

!!! os
    macOS·Windows(Docker Desktop)에서는 도커가 VM 안에서 돌기 때문에 `ss`로 `docker-proxy`가 보이지 않습니다. `docker port`와 `curl` 결과는 같습니다. `hostname -I`는 리눅스 전용이며 macOS는 `ipconfig getifaddr en0`을 쓰세요.

## 실습 4-4 — 왜 호스트에서는 되는데 컨테이너에서는 안 되는가

현장에서 가장 자주 만나는 상황을 재현합니다. 호스트에 "사내 에이전트"가 127.0.0.1에만 리슨하고 있습니다.

```bash
python3 -m http.server 9999 --bind 127.0.0.1 >/dev/null 2>&1 &
sleep 1
curl -s -o /dev/null -w "호스트에서: %{http_code}\n" http://127.0.0.1:9999

# ① 컨테이너 안에서 127.0.0.1 → 실패 (그건 컨테이너 자신)
docker run --rm nicolaka/netshoot:v0.13 sh -c 'curl -s -m2 -o /dev/null -w "컨테이너에서 127.0.0.1: %{http_code}\n" http://127.0.0.1:9999; echo "종료코드=$?"'

# ② host.docker.internal → 그래도 실패 (호스트 서비스가 127.0.0.1에만 리슨)
docker run --rm --add-host=host.docker.internal:host-gateway nicolaka/netshoot:v0.13 sh -c \
  'getent hosts host.docker.internal; curl -s -m2 -o /dev/null -w "host.docker.internal: %{http_code}\n" http://host.docker.internal:9999; echo "종료코드=$?"'

# ③ 호스트 서비스를 0.0.0.0에 바인딩하면 성공
kill %1; python3 -m http.server 9999 --bind 0.0.0.0 >/dev/null 2>&1 &
sleep 1
docker run --rm --add-host=host.docker.internal:host-gateway nicolaka/netshoot:v0.13 sh -c \
  'curl -s -m2 -o /dev/null -w "host.docker.internal (0.0.0.0 바인딩): %{http_code}\n" http://host.docker.internal:9999'
kill %1
```

!!! expect
    ```text
    호스트에서: 200
    컨테이너에서 127.0.0.1: 000        종료코드=7
    172.17.0.1  host.docker.internal
    host.docker.internal: 000          종료코드=7
    host.docker.internal (0.0.0.0 바인딩): 200
    ```
    ②가 핵심입니다. 이름은 풀렸고(172.17.0.1) 경로도 있는데, **호스트 쪽 서비스가 루프백에만 묶여 있어서** 실패합니다. 고객사 VM에 설치된 사내 프록시 에이전트, 로그 수집 에이전트, DB가 이 상태인 경우가 많습니다. 해결은 두 가지 중 하나입니다 — 서비스의 바인딩 주소를 바꾸거나, 컨테이너를 `--network host`로 띄우거나. 후자는 격리를 포기하는 것이므로 보안팀이 싫어합니다.

!!! verified
    실습 4-1~4-4는 세션 안(Linux Docker Engine)에서 실행해 위 출력을 확인했습니다.

## 실습 4-5 — 진단 3단계 (외우세요)

고객 환경에서 막혔을 때 쓸 명령입니다. 순서가 중요합니다.

```bash
# 증상: A(client)에서 B(web)로 연결이 안 된다

# 1) 이름이 풀리는가?          실패 → DNS/네트워크 소속 문제
docker exec client nslookup web | tail -2

# 2) 포트가 열려 있는가?        실패 → 방화벽, B 미기동, B가 127.0.0.1에만 바인딩
docker exec client nc -zv -w3 web 80

# 3) HTTP 응답이 오는가?        실패 → 애플리케이션 문제 (인증, 경로, TLS, 타임아웃)
docker exec client curl -sv -m5 http://web/ -o /dev/null 2>&1 | grep -E "^< HTTP|Connected"
```

!!! expect
    ```text
    Name:	web
    Address: 172.18.0.2
    Connection to web (172.18.0.2) 80 port [tcp/http] succeeded!
    * Connected to web (172.18.0.2) port 80
    < HTTP/1.1 200 OK
    ```

2단계의 실패는 **두 종류**로 갈립니다. 이 구분이 "누구에게 말할 것인가"를 정합니다.

```bash
docker exec client nc -zv -w3 web 81                # 포트는 닫혔지만 서버는 응답함
docker exec client nc -zv -w3 10.255.255.1 80       # 아무 응답 없음 (일반 환경에서)
```

| 2단계 결과 | 뜻 | 누구에게 |
|---|---|---|
| `Connection refused` (즉시) | 패킷은 도착했고 서버가 **거절**함 → 서비스 미기동, 다른 포트, 127.0.0.1 바인딩 | 서비스 담당자 (또는 나) |
| `Operation timed out` (3초 뒤) | 패킷이 **버려짐** → 중간 방화벽, 라우팅 없음, 잘못된 IP | 네트워크/보안팀 |
| `succeeded` | 포트 OK → 3단계로 | — |

!!! note
    이 문서를 만든 세션 환경은 모든 TCP 80/443을 가로채는 투명 프록시가 있어서, 존재하지 않는 IP `10.255.255.1:80`에도 `succeeded`가 나왔습니다. 일반 PC와 고객사 환경에서는 타임아웃이 납니다. **회사 PC에서 `succeeded`가 이상하게 잘 나오면 투명 프록시를 의심하세요** — Day 7·8의 주제입니다.

이어서 자주 쓰는 확인 명령입니다.

```bash
# 컨테이너의 IP와 소속 네트워크
docker inspect web --format '{{json .NetworkSettings.Networks}}' | python3 -m json.tool | grep -E '"[a-z-]+": \{|IPAddress'
# 네트워크에 어떤 컨테이너가 붙어 있나
docker network inspect lab-net --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
# 컨테이너 안의 라우팅
docker exec client ip route
# 진단 도구가 풍부한 컨테이너를 잠깐 띄우기 (현장에서 유용)
docker run --rm -it --network lab-net nicolaka/netshoot:v0.13 sh -c "dig +short web; curl -sI http://web | head -1"
```

!!! tip
    `nicolaka/netshoot` 이미지는 현장에서 매우 유용합니다. dig, curl, nc, tcpdump, netstat, iperf가 다 들어 있습니다. 다만 폐쇄망에서는 미리 반입해 두어야 씁니다. **반입 목록에 진단용 이미지를 꼭 포함시키세요.** 이걸 빠뜨리면 문제가 생겼을 때 진단 도구가 없어서 며칠을 허비합니다. 용량이 부담되면(775MB) `curlimages/curl`(20MB) + `alpine`에 `apk add bind-tools`로 대신할 수 있지만, 폐쇄망에서는 `apk add`도 안 되므로 netshoot이 낫습니다.

## 실습 4-6 — 사내 DNS와 정적 호스트

고객사 VM은 사내 DNS를 쓰고, 사내 도메인(`erp.corp.local`)은 사내 DNS만 압니다. 컨테이너는 호스트의 DNS 설정을 상속하지만, 명시적으로 지정해야 하는 경우도 있습니다.

```bash
# 컨테이너 단위 지정
docker run --rm --dns 10.0.0.53 --dns-search corp.local alpine:3.20 cat /etc/resolv.conf | grep -v "^#"
# DNS에 없는 이름을 임시로 박기 (사내 DNS 등록 대기 중일 때)
docker run --rm --add-host erp.corp.local:10.20.30.40 alpine:3.20 grep erp /etc/hosts
```

!!! expect
    ```text
    nameserver 10.0.0.53
    search corp.local
    options timeout:2 attempts:3

    10.20.30.40	erp.corp.local
    ```

VM 전체에 적용하려면 `/etc/docker/daemon.json`에 넣습니다(Day 1의 Ansible 플레이북이 만든 파일이 이것입니다). sudo가 없으면 IT운영에 요청합니다.

```json
{
  "dns": ["10.0.0.53", "10.0.0.54"],
  "dns-search": ["corp.local"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

!!! check
    - 사내 DNS 서버 주소, 사내 도메인 접미사, **컨테이너 대역(172.16.0.0/12)에서 사내 DNS로 UDP 53이 허용되는지**. 마지막 항목이 막혀 있으면 "호스트에서는 되고 컨테이너에서만 이름이 안 풀리는" 증상이 납니다.
    - 도커 기본 대역(172.17.0.0/16, 172.18.0.0/16 …)이 **사내 대역과 겹치는지**. 겹치면 컨테이너에서 그 사내 시스템에 영원히 못 갑니다(라우팅이 브리지로 빠짐). 겹치면 `daemon.json`의 `default-address-pools`로 바꿉니다. 첫 미팅 확인 항목입니다.

## 눈으로 확인 — lazydocker Networks

!!! eye
    **lazydocker → Networks** 패널에 `lab-net`, `other-net`이 추가된 것과, 각 네트워크를 골랐을 때 오른쪽에 붙어 있는 컨테이너 목록·서브넷이 나오는지 봅니다. `isolated`가 두 네트워크 모두에 나타나야 합니다.

```screen
# lazydocker — Networks 패널에서 lab-net 선택
├─Networks─────────────┤│ Name: lab-net          Driver: bridge         Scope: local
│ bridge               ││ Subnet: 172.18.0.0/16  Gateway: 172.18.0.1
│ host                 ││
│ lab-net       ◀      ││ Containers:
│ none                 ││   web        172.18.0.2/16
│ other-net            ││   client     172.18.0.3/16
└──────────────────────┘│   isolated   172.18.0.4/16   ← other-net에도 붙어 있음
```

## 오류 대응

!!! rollback
    - `network lab-net not found` → 순서대로 `docker network create`부터.
    - `Conflict. The container name "/web" is already in use` → 아래 정리 명령 후 재실행.
    - `curl: (6)`은 이름, `(7)`은 연결, `(28)`은 타임아웃. 종료코드로 단계를 바로 알 수 있습니다.
    - `hostname -I`가 없으면(macOS) `ipconfig getifaddr en0`.
    - 9999 포트 서버가 남아 있으면 `pkill -f "http.server 9999"`.

## 정리

```bash
pkill -f "http.server 9999" 2>/dev/null
docker rm -f web client web2 client2 isolated pub pub2 2>/dev/null
docker network rm lab-net other-net 2>/dev/null
docker network ls --format '{{.Name}}'
```
