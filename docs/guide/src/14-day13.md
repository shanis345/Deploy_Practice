!!! why
    보안 협의의 마지막 질문은 늘 같습니다.

    > "외부로 나간 데이터가 통제된다는 걸 어떻게 증명하시죠? 누가, 언제, 어떤 모델에, 무엇을 보냈는지 나중에 확인할 수 있습니까? 비용은 부서별로 나눌 수 있나요?"

    답은 **게이트웨이 하나**입니다. 에이전트가 외부 LLM을 직접 부르지 않고 사내 게이트웨이를 거치면 — 방화벽 목적지는 하나가 되고(Day 7), 모든 요청·응답이 사내에 기록되며, 모델 교체·비용 집계·키 관리가 한 곳에서 됩니다. 오늘 이것을 LiteLLM으로 직접 만들고, 파일럿 성과를 측정하는 전제인 **구조화 로그와 메트릭**의 기초를 함께 다룹니다.

## 핵심 개념

### 게이트웨이가 해결하는 것

<pre class="diagram">
  [게이트웨이 없음]                          [게이트웨이 있음]
  agent ──▶ api.openai.com                    agent ──▶ llm-gateway ──▶ (사내 프록시) ──▶ 목적지 1개
  agent ──▶ api.anthropic.com                          │
  agent ──▶ xxx.openai.azure.com                       ├─ 키 보관 (에이전트는 게이트웨이 키만 가짐)
  agent ──▶ embedding 서비스                            ├─ 모델 라우팅·폴백 (외부 API 장애 시 사내 vLLM으로)
                                                        ├─ 감사 로그 (누가·언제·어떤 모델·토큰·비용)
  · 화이트리스트 N줄, 키 N개 분산                       ├─ 예산·속도 제한 (부서별 가상 키)
  · 기록 없음, 비용 집계 불가                            └─ 응답 캐시 (선택)
</pre>

| 기능 | 고객사 협의에서의 의미 |
|---|---|
| 아웃바운드 단일화 | 방화벽 목적지 1개. Day 7의 협상 카드 |
| 키 보관 | 외부 API 키가 에이전트 컨테이너·개발자 PC에 없음 |
| 가상 키(virtual key) | 부서·용도별 키 발급, 예산 상한, 사용량 집계 |
| 감사 로그 | "무엇이 나갔는가"의 증거. 사고 조사·비용 정산 |
| 모델 라우팅 | 에이전트 코드 변경 없이 외부 API ↔ 사내 모델 전환 |
| OpenAI 호환 API | 에이전트는 `base_url`만 바꾸면 됨 — 어떤 프레임워크든 |

### 감사 로그에 무엇을 남길 것인가

| 항목 | 이유 | LiteLLM 기본 제공 |
|---|---|---|
| 타임스탬프, request_id | 사고 조사, 에이전트 로그와 연결 | ○ |
| 호출 주체 (가상 키·사용자·팀) | 누가 요청했는가 (SSO 연동 시 사용자 ID) | ○ |
| 모델명, 제공자, api_base | 어느 모델로 어디로 나갔는가 | ○ |
| 토큰 수, 비용 | 비용 관리, 부서별 정산 | ○ |
| 성공/실패, 오류, 지연 | 장애 분석 | ○ |
| **프롬프트·응답 원문** | 무엇이 나갔는가 | **× (기본 미저장)** — 별도 설정 또는 커스텀 로거 |
| 도구 호출 내역 | 에이전트가 어떤 사내 시스템을 건드렸는가 | × — 에이전트 로그에서 |

**프롬프트 원문 저장 여부는 고객사와 합의할 사항입니다.** 개인정보가 섞일 수 있으면 해시와 길이만 남기고, 원문은 별도 보관 정책(암호화, 보존 기간, 접근 권한)을 따르는 방식을 제안하세요. Day 8에서 본 것처럼 TLS 검사 장비도 원문을 볼 수 있으므로, "원문이 어디에 몇 벌 남는가"를 정리해 두면 보안팀이 좋아합니다.

### 관측성 기초 — 파일럿 성과 측정의 전제

"파일럿이 성공했는가"를 말하려면 숫자가 필요합니다. 응답 시간, 성공률, 사용량, 비용. 이걸 나중에 붙이려면 늦고, 처음부터 세 가지를 갖춰야 합니다.

| 요소 | 최소 요건 | 이 문서의 에이전트 |
|---|---|---|
| 구조화 로그 | JSON Lines, 요청마다 한 줄, `request_id`·경로·상태·소요 시간 | stdout에 JSON |
| 메트릭 | 요청 수·상태 코드·지연을 숫자로. Prometheus 텍스트 형식이 표준 | `/metrics` |
| 요청 ID 전파 | 게이트웨이 → 에이전트 → LLM 게이트웨이까지 같은 ID | `X-Request-Id` 헤더 |

고객사에는 대개 로그 수집 시스템(Splunk, ELK, Datadog)과 메트릭 시스템(Prometheus·Grafana)이 있습니다. 컨테이너가 **stdout에 JSON으로** 남기면 수집 에이전트(fluent-bit, filebeat)가 그대로 가져갑니다. 파일에 쓰거나 자체 포맷을 쓰면 연동 작업이 생깁니다.

## 실습 13-2 — 전 구간 관통과 통제 확인

```bash
echo "① 에이전트 → 게이트웨이 → 모델"
docker compose exec -T probe curl -s -X POST http://agent:8000/ask -H 'Content-Type: application/json' \
  -d '{"question":"샘플 계약 건수를 알려주세요"}' | jq '{answer, mode, model, usage: .usage.total_tokens, elapsed_ms}'

echo "② 게이트웨이를 OpenAI 호환 API로 직접 호출"
curl -s localhost:4000/v1/chat/completions -H "Authorization: Bearer sk-pilot-local-key" -H 'Content-Type: application/json' \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"안녕"}]}' | jq -c '{model, content: .choices[0].message.content}'

echo "③ 잘못된 키 → 거부"
curl -s -o /dev/null -w "%{http_code}\n" localhost:4000/v1/chat/completions -H "Authorization: Bearer wrong" \
  -H 'Content-Type: application/json' -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"x"}]}'

echo "④ 등록되지 않은 모델 → 거부 (에이전트가 임의 모델을 못 씀)"
curl -s localhost:4000/v1/chat/completions -H "Authorization: Bearer sk-pilot-local-key" -H 'Content-Type: application/json' \
  -d '{"model":"claude-3-opus","messages":[{"role":"user","content":"x"}]}' | jq -r '.error.message' | cut -c1-120

echo "⑤ 에이전트는 인터넷에 직접 못 나간다"
docker compose exec -T probe curl -s "http://agent:8000/egress?url=http://example.com" | jq -c '{ok,error_type}'
```

!!! expect
    ```text
    ① {"answer":"샘플 계약은 3건이며 합계는 47,030,000원입니다. (출처: sample_records)","mode":"llm","model":"gpt-4o-mini","usage":30,"elapsed_ms":73}
    ② {"model":"gpt-4o-mini","content":"샘플 계약은 3건이며 ..."}
    ③ 401
    ④ /chat/completions: Invalid model name passed in model=claude-3-opus. Call `/v1/models` to view available models for your key.
    ⑤ {"ok":false,"error_type":"gaierror"}
    ```
    ③④⑤가 통제의 증거입니다. 키 없이는 못 부르고, 등록된 모델만 쓸 수 있고, 에이전트는 게이트웨이 외에는 아무 데도 못 갑니다.

!!! verified
    실습 13-1·13-2는 세션 안에서 실행해 위 출력을 확인했습니다. 실제 외부 API 호출(모의 응답 제거 후)은 키가 없어 검증하지 못했습니다. 그 경로는 Day 7의 프록시 로그(`TCP_TUNNEL/200 CONNECT api.openai.com:443`)로 확인하면 됩니다.

## 실습 13-3 — 감사 로그 확인

```bash
# 요청을 몇 개 더 보낸 뒤
for i in $(seq 1 6); do
  docker compose exec -T probe curl -s -X POST http://agent:8000/ask -H 'Content-Type: application/json' \
    -H "X-Request-Id: req-$i" -d "{\"question\":\"질문 $i\"}" >/dev/null
done
sleep 8    # 로그 적재는 비동기

docker compose exec -T audit-db psql -U audit -d auditdb \
  -c 'SELECT count(*) AS 건수, sum(total_tokens) AS 토큰합계, round(sum(spend)::numeric, 6) AS 비용 FROM "LiteLLM_SpendLogs";'
docker compose exec -T audit-db psql -U audit -d auditdb \
  -c 'SELECT request_id, model, prompt_tokens, completion_tokens, "startTime" FROM "LiteLLM_SpendLogs" ORDER BY "startTime" DESC LIMIT 3;'
# 어떤 컬럼이 있는가 — 프롬프트 원문 컬럼은 없다
docker compose exec -T audit-db psql -U audit -d auditdb \
  -tAc 'SELECT column_name FROM information_schema.columns WHERE table_name=$$LiteLLM_SpendLogs$$ ORDER BY ordinal_position;' | tr '\n' ' '
```

!!! expect
    ```text
     건수 | 토큰합계 |   비용
    ------+----------+----------
        8 |      240 | 0.000108
                  request_id                   |    model    | prompt_tokens | completion_tokens |        startTime
    -----------------------------------------------+-------------+---------------+-------------------+-------------------------
     chatcmpl-f33495b8-e299-4fff-ab59-592ff11770e4 | gpt-4o-mini |            10 |                20 | 2026-09-22 06:52:27.113
     ...
    request_id call_type api_key spend total_tokens prompt_tokens completion_tokens startTime endTime completionStartTime
    model model_id model_group custom_llm_provider api_base user metadata cache_hit cache_key request_tags team_id end_user requester_ip_address
    ```
    누가(`api_key`, `user`, `team_id`), 언제, 어떤 모델로(`model`, `api_base`), 얼마나(`tokens`, `spend`) 나갔는지가 한 테이블에 있습니다. **프롬프트 원문 컬럼은 없습니다** — 기본 설정에서는 저장하지 않습니다. 원문 보관이 요구되면 LiteLLM의 커스텀 콜백이나 별도 로거를 게이트웨이 앞에 두는 방식을 씁니다.

!!! say
    "에이전트가 외부로 나가는 경로는 사내 LLM 게이트웨이 한 곳뿐이고, 게이트웨이를 지나는 모든 호출은 사내 DB에 호출자·시각·모델·토큰·비용 단위로 기록됩니다. 프롬프트 원문의 보관 여부와 보존 기간은 개인정보 정책에 맞춰 함께 정하겠습니다. 부서별 가상 키를 발급하면 사용량과 비용이 부서 단위로 집계됩니다."

## 실습 13-5 — 관측성 기초: 구조화 로그와 메트릭

에이전트가 남기는 JSON 로그를 `jq`만으로 분석합니다. 고객사의 Splunk/ELK가 하는 일의 축소판이고, 파일럿 보고서의 숫자가 여기서 나옵니다.

```bash
echo "## 원본 (JSON Lines)"
docker compose logs agent --no-log-prefix --tail 3

echo "## 경로별 건수·평균·최대 지연"
docker compose logs agent --no-log-prefix | grep '"event": "request"' \
  | jq -s 'group_by(.path) | map({path: .[0].path, count: length, avg_ms: (map(.ms) | add / length | floor), max_ms: (map(.ms) | max)})'

echo "## 요청 ID로 추적 (nginx → 에이전트 → 게이트웨이가 같은 ID를 공유)"
docker compose logs agent --no-log-prefix | grep 'req-3' | jq -c '{request_id, path, status, ms}'

echo "## Prometheus 형식 메트릭"
docker compose exec -T probe curl -s http://agent:8000/metrics
```

!!! expect
    ```text
    {"event": "request", "method": "POST", "path": "/ask", "status": 200, "ms": 16, "request_id": "req-5", "ts": "2026-09-22T06:52:26+0000", "level": "INFO", "service": "agent", "version": "0.2.0", "host": "ae6930cfde53"}
    [
      { "path": "/ask",     "count": 10, "avg_ms": 14, "max_ms": 75 },
      { "path": "/egress",  "count": 1,  "avg_ms": 1,  "max_ms": 1 },
      { "path": "/healthz", "count": 15, "avg_ms": 0,  "max_ms": 4 }
    ]
    {"request_id":"req-3","path":"/ask","status":200,"ms":8}
    # HELP agent_requests_total 요청 수
    # TYPE agent_requests_total counter
    agent_requests_total{path="/ask",status="200"} 7
    agent_requests_total{path="/ask",status="502"} 3      ← 게이트웨이가 뜨기 전의 실패
    agent_requests_total{path="/healthz",status="200"} 15
    ```

첫 케이스의 애플리케이션에 요구할 최소 조건입니다.

| 요구 | 이유 |
|---|---|
| 요청마다 JSON 한 줄, stdout | 고객사 수집기(fluent-bit/filebeat)가 그대로 가져감 |
| `request_id`를 받아서 전파 (`X-Request-Id`) | 게이트웨이·에이전트·LLM 게이트웨이 로그를 하나로 묶음 |
| 지연(ms)·상태 코드·경로 | p50/p95 응답 시간, 성공률 |
| LLM 호출별 모델·토큰·지연 | 비용과 병목 |
| `/metrics` (Prometheus 텍스트) | 고객사 Grafana에 바로 연결 |
| 로그에 개인정보·프롬프트 원문 금지 | 로그 시스템은 보안 등급이 낮은 경우가 많음 |

!!! check
    - 고객사 로그 수집 시스템과 연동 방식: 컨테이너 stdout을 자동 수집하는지, 파일 경로를 지정해야 하는지, 별도 에이전트를 컨테이너에 넣어야 하는지(사이드카).
    - 메트릭: Prometheus가 있고 우리 네임스페이스를 스크랩해 주는지(`ServiceMonitor` 필요 여부).
    - 로그 보관 기간과 접근 권한 — 감사 로그 요건(보통 1년 이상)과 다를 수 있음.

## 실습 13-6 (선택) — 사내 모델 호스팅: vLLM <span class="badge opt">선택 · GPU 필요</span>

"외부 API 전면 불가" 고객을 대비한 실습입니다. GPU가 있어야 하므로 클라우드 GPU 인스턴스 1시간 대여로 충분합니다.

```bash
# GPU가 있는 환경에서
docker run -d --gpus all --name vllm -p 8001:8000 \
  -v "$HOME/.cache/huggingface:/root/.cache/huggingface" \
  vllm/vllm-openai:v0.6.3 \
  --model Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.9

# OpenAI 호환 API로 호출된다
curl -s localhost:8001/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"Qwen/Qwen2.5-7B-Instruct","messages":[{"role":"user","content":"안녕"}]}' | jq -c '.choices[0].message.content'
```

핵심은 **엔드포인트만 바꾸면 에이전트 코드는 그대로**라는 점입니다. `gateway/config.yaml`의 주석 처리된 `qwen2.5-7b` 항목을 살리면 게이트웨이가 사내 vLLM으로 라우팅하고, 에이전트는 `LLM_MODEL`만 바꾸면 됩니다. 이 구조를 만들어 두면 고객사 정책이 어느 쪽이든 대응할 수 있습니다.

!!! unverified
    vLLM은 GPU가 없어 세션에서 실행하지 못했습니다. 명령은 vLLM 공식 문서의 표준 형식이며, 모델 파일(Qwen2.5-7B는 약 15GB)은 폐쇄망에서 **별도 반입** 대상입니다 — Day 9의 "실행 시 외부 다운로드" 항목에 해당하므로 `HF_HUB_OFFLINE=1`과 모델 디렉터리 마운트로 처리합니다. 버전 태그가 오래되어 동작하지 않으면 `vllm/vllm-openai` 최신 안정 태그로 바꾸세요.

!!! check
    - 사내 GPU 자원 유무, 확보 경로(신규 구매는 분기 단위), GPU 노드가 쿠버네티스에 있는지.
    - 허용 모델 목록(라이선스 검토 여부), 모델 파일 반입 절차(수십 GB).
    - 사내 모델의 품질이 파일럿 목표를 만족하는지 — "외부 API 전면 불가"면 사내 모델로 파일럿 목표를 재조정해야 합니다.
