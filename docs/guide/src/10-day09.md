# Day 9 — 폐쇄망 이미지 반입: 오프라인 빌드 · save/load · 사내 레지스트리 · 스캔 · SBOM

<div class="day-meta"><span><b>소요</b> 3시간</span><span><b>만드는 것</b> 반입 패키지 한 벌 (tar.gz + 해시 + 스캔 리포트 + SBOM + 신청서)</span><span><b>눈으로</b> 레지스트리 UI, dive</span><span><b>누적 점검</b> 2차 (Day 6–9)</span></div>

!!! why
    폐쇄망 고객사에서 코드를 전달하는 유일한 경로가 "반입"입니다. 반입 담당자에게 USB(또는 반입용 전송 시스템)로 파일을 넘기면, 악성코드 검사·취약점 스캔·승인을 거쳐 며칠 뒤 폐쇄망 안의 서버에 도착합니다. **이 절차가 며칠씩 걸리기 때문에, 반입 횟수를 줄이는 설계가 프로젝트 일정을 좌우합니다.**

    Day 5에서 설정을 이미지 밖으로 뺀 이유가 여기서 드러납니다. 프롬프트 한 줄 바꾸려고 3일짜리 반입 절차를 다시 타야 한다면 튜닝이 불가능합니다. 그리고 반입 담당자가 tar 파일만 들고 온 사람을 돌려보내는 이유 — 해시, 스캔 결과, 구성 요소 목록이 없어서 — 를 오늘 전부 준비합니다.

## 핵심 개념

### 반입 경로의 세 가지 형태

| 형태 | 설명 | 흔한 정도 | 우리가 준비할 것 |
|---|---|---|---|
| 사내 레지스트리 미러 | 승인된 외부 이미지를 사내 Harbor가 미러링. `docker pull`이 사내 주소로 동작 | 성숙한 고객사 | 미러 요청서 (이미지명·태그·다이제스트) |
| **파일 반입** | `docker save`로 tar를 만들어 반입 절차(승인·스캔)를 거쳐 전달 | **가장 흔함** | tar.gz + sha256 + 스캔 리포트 + SBOM + 신청서 |
| 소스 반입 후 사내 빌드 | 소스를 반입해 사내 빌드 서버에서 빌드 | 보안이 가장 강한 곳 | 오프라인 빌드가 되는 Dockerfile + 의존성(wheel) 묶음 |

두 번째가 기본이라고 생각하고 준비하되, 첫 주에 어느 방식인지 확인하세요. 세 번째 형태라면 오늘의 실습 9-1이 핵심입니다.

### 오프라인 빌드가 필요한 이유

폐쇄망에서 `pip install`이나 `apt-get install`은 동작하지 않습니다. 사내 미러(Nexus, Artifactory)가 있으면 그 주소를 쓰고, 없으면 **의존성을 미리 받아서 이미지에 넣어야** 합니다.

```text
[사내 미러가 있는 경우]
pip install --index-url https://nexus.corp.local/repository/pypi/simple -r requirements.txt

[미러가 없는 경우]
인터넷 되는 곳에서 wheel 파일을 전부 다운로드 → 반입 → --no-index 로 설치
```

첫 주 질문 목록에 "사내 pip/npm/yum 미러가 있습니까?"를 꼭 넣으세요. 있으면 일이 절반으로 줄어듭니다.

### 반입 심의를 통과하는 이미지의 조건

| 항목 | 요구사항 | 이 문서에서 |
|---|---|---|
| 베이스 이미지 | 고객사 승인 목록 내 (보통 RHEL UBI 또는 특정 버전) | Day 3 |
| 태그 | `latest` 금지, 명시적 버전 + 다이제스트 | Day 3 |
| 실행 사용자 | non-root | Day 3 |
| 취약점 | HIGH/CRITICAL 0건 (또는 예외 승인) | Day 3, 오늘 오프라인 스캔 |
| 비밀 정보 | 이미지 내 미포함 (스캔으로 검증됨) | Day 3 |
| SBOM | 구성 요소 목록 제출 요구 증가 추세 | 오늘 |
| 무결성 | sha256 해시가 신청서와 일치 | 오늘 |
| 크기 | 작을수록 심의·전송이 빠름. 반입 매체 용량 제한(예: 2GB) 확인 | |
| 오프라인 동작 | 실행 시 외부 다운로드 없음 (모델 파일, 토크나이저 포함) | 오늘 `--network=none` |

마지막 항목이 AI 에이전트에서 특히 문제가 됩니다. 토크나이저(`tiktoken`)나 임베딩 모델이 **첫 실행 시 인터넷에서 파일을 받는** 라이브러리가 많습니다. 폐쇄망에서는 기동 자체가 실패합니다. 오늘의 `--network=none` 검증이 이것을 잡아냅니다.

## 실습 9-1 — 오프라인 빌드

```bash
cd ~/onprem-lab/day09
cp ~/onprem-lab/agent/app.py ~/onprem-lab/agent/requirements.txt .

# ① 인터넷이 되는 환경에서 wheel을 전부 받는다 (베이스 이미지와 같은 파이썬·플랫폼으로!)
mkdir -p wheels
docker run --rm -v "$PWD:/w" -w /w python:3.12.14-slim pip download -q --dest /w/wheels -r requirements.txt
ls wheels/; du -sh wheels/
```

!!! expect
    ```text
    PyYAML-6.0.2-cp312-cp312-manylinux_2_17_x86_64.manylinux2014_x86_64.whl
    756K	wheels/
    ```
    파일명의 `cp312`(파이썬 3.12)와 `manylinux_x86_64`가 베이스 이미지와 맞아야 합니다. **맥(arm64)에서 호스트의 pip으로 받으면 arm64 wheel이 내려와 폐쇄망 x86 서버에서 설치가 안 됩니다.** 그래서 컨테이너 안에서 받습니다. 고객 서버가 arm64(드묾)라면 `--platform linux/arm64`를 붙입니다.

!!! os
    Apple Silicon 맥에서는 위 `docker run`에 `--platform linux/amd64`를 붙이세요. 그렇지 않으면 arm64 wheel이 내려옵니다. 이미지 빌드도 `docker build --platform linux/amd64`로 해야 고객사 x86 서버에서 돕니다. **반입 후 `exec format error`가 나면 이것입니다.**

```dockerfile
#file: Dockerfile.offline
# 폐쇄망 빌드 서버용: 네트워크를 전혀 쓰지 않는다. wheels/ 는 인터넷 되는 곳에서 미리 받아 온다.
ARG BASE=python:3.12.14-slim
ARG APP_VERSION=0.2.0

FROM ${BASE} AS builder
WORKDIR /build
COPY wheels /tmp/wheels
COPY requirements.txt .
RUN pip install --no-index --find-links=/tmp/wheels --no-cache-dir --target=/build/deps -r requirements.txt

FROM ${BASE}
ARG APP_VERSION
RUN useradd --create-home --uid 10001 --gid 0 appuser \
 && mkdir -p /app/config /app/tmp && chgrp -R 0 /app && chmod -R g=u /app
WORKDIR /app
COPY --from=builder /build/deps /app/deps
COPY app.py .
ENV PYTHONPATH=/app/deps PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 HOME=/app APP_VERSION=${APP_VERSION}
USER 10001
EXPOSE 8000
HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')"
CMD ["python", "app.py"]
```

```bash
# ② 네트워크를 끊고 빌드 — 폐쇄망 빌드 서버 흉내. 이 검증을 개발 단계에 해 두면 반입 후 당황하지 않는다.
docker build --network=none -f Dockerfile.offline --build-arg APP_VERSION=0.2.0 -t agent:0.2.0-offline .
docker run -d --rm --name off -p 127.0.0.1:8000:8000 agent:0.2.0-offline && sleep 2
curl -s localhost:8000/healthz | jq -c .
docker rm -f off

# ③ 비교: 온라인용 Dockerfile을 네트워크 없이 빌드하면 (의도된 실패)
docker build --network=none -f ~/onprem-lab/agent/Dockerfile -t x:fail ~/onprem-lab/agent 2>&1 | grep -m1 -oE "Temporary failure in name resolution|Could not find a version"
```

!!! expect
    ```text
    {"status":"ok","version":"0.2.0","host":"107f59992bf9"}
    ```

!!! fail
    ```text
    Temporary failure in name resolution
    ```
    ③이 폐쇄망 빌드 서버에서 보게 될 화면입니다. `pip`이 PyPI에 닿지 못해 재시도 후 실패합니다. 이 실패를 **고객사가 아니라 내 PC에서** 먼저 보는 것이 오늘의 목적입니다.

!!! tip
    실행 시 외부 다운로드를 하는 라이브러리(HuggingFace 토크나이저, `tiktoken`, NLTK 데이터, `playwright install`)가 있으면 컨테이너를 `--network none`으로 실행해 기동 테스트를 하세요: `docker run --rm --network none agent:0.2.0-offline python -c "import app"`. 폐쇄망 반입 후 "기동이 안 된다"의 흔한 원인입니다. 필요한 파일은 빌드 시 이미지에 넣거나(`ENV HF_HUB_OFFLINE=1 TIKTOKEN_CACHE_DIR=/app/cache` + 파일 COPY) 볼륨으로 반입합니다.

## 실습 9-2 — save / load 반입 패키지

```bash
# ① 이미지를 파일로
docker save agent:0.2.0-offline -o agent-0.2.0-offline.tar
ls -lh agent-0.2.0-offline.tar | awk '{print $5, $9}'

# ② 압축 (반입 매체 용량 제한이 있는 곳이 많다)
gzip -9 -k -f agent-0.2.0-offline.tar
ls -lh agent-0.2.0-offline.tar.gz | awk '{print $5, $9}'

# ③ 무결성 해시 — 반입 신청서에 기재. 반입 담당자가 대조한다
sha256sum agent-0.2.0-offline.tar.gz | tee agent-0.2.0-offline.sha256

# ④ 반입 후 (고객사 서버에서 실행할 명령) — 로컬 이미지를 지우고 진짜 적재되는지 본다
docker rmi agent:0.2.0-offline
sha256sum -c agent-0.2.0-offline.sha256
docker load -i agent-0.2.0-offline.tar
docker images agent --format '{{.Repository}}:{{.Tag}} {{.ID}}'
```

!!! expect
    ```text
    43M agent-0.2.0-offline.tar
    42M agent-0.2.0-offline.tar.gz        ← 레이어가 이미 압축되어 있어 gzip 효과는 작다
    53fb0923b514a6dd8e9561e3cb3e1c24a598927bac500d3c5bcde179ac73a910  agent-0.2.0-offline.tar.gz
    agent-0.2.0-offline.tar.gz: OK
    Loaded image: agent:0.2.0-offline
    agent:0.2.0-offline 1e2d87f47d82
    ```

!!! note
    `docker load`는 `.tar`와 `.tar.gz` 둘 다 읽습니다. 여러 이미지를 한 파일로 묶으려면 `docker save agent:0.2.0-offline nicolaka/netshoot:v0.13 postgres:16.4-alpine -o bundle.tar` — **반입 목록에 진단용 이미지(netshoot)와 의존 이미지(DB, nginx, LiteLLM)를 전부 포함**하세요. 에이전트만 반입하고 nginx를 빠뜨리면 반입을 한 번 더 타야 합니다.

### 폐쇄망 서버에서 정말 도는지 — 네트워크 없는 도커 데몬으로 검증

`docker load`가 되는 것과 폐쇄망에서 **기동**되는 것은 다릅니다. 인터넷이 전혀 없는 별도의 도커 데몬(docker-in-docker)을 띄워 검증합니다.

```bash
docker run -d --privileged --network none --name airgap docker:27-dind
sleep 12
docker exec airgap docker info --format 'Server={{.ServerVersion}} images={{.Images}}'
docker exec airgap docker pull alpine:3.20 2>&1 | tail -1          # 인터넷이 없음을 확인

docker cp agent-0.2.0-offline.tar airgap:/agent.tar
docker exec airgap docker load -i /agent.tar
docker exec airgap sh -c 'docker run -d --name agent agent:0.2.0-offline >/dev/null && sleep 3 \
  && docker exec agent python -c "import urllib.request;print(urllib.request.urlopen(\"http://127.0.0.1:8000/healthz\").read().decode())"'
docker rm -f airgap
```

!!! expect
    ```text
    Server=27.5.1 images=0
    Error response from daemon: Get "https://registry-1.docker.io/v2/": dial tcp: lookup registry-1.docker.io ... network is unreachable.
    Loaded image: agent:0.2.0-offline
    {"status": "ok", "version": "0.2.0", "host": "bc53a18487ea"}
    ```
    `pull`은 실패하고(인터넷 없음) `load`한 이미지는 기동됩니다. 반입 전날 이 검증을 하면 "폐쇄망에서 안 뜬다"는 전화를 받을 일이 크게 줄어듭니다.

!!! verified
    실습 9-1·9-2는 세션 안에서 실행해 위 출력을 확인했습니다. `docker:27-dind`는 `--privileged`가 필요하므로 회사 정책상 안 되는 PC도 있습니다. 그 경우 VM(예: WSL2 안의 별도 배포판)에서 `docker load`로 대신합니다.

## 실습 9-3 — 사내 레지스트리 재현 (Harbor 대역)

고객사 Harbor를 흉내 내어, 반입한 이미지를 사내 레지스트리에 올리고 그것으로 배포하는 흐름을 만듭니다. 레지스트리 UI로 **눈으로 확인**합니다.

```yaml
#file: compose.yaml
name: day09

services:
  registry:                            # 사내 레지스트리 (Harbor 대역)
    image: registry:2.8.3
    ports:
      - "127.0.0.1:5000:5000"
    environment:
      REGISTRY_STORAGE_DELETE_ENABLED: "true"
      # UI가 브라우저에서 API를 직접 부르므로 CORS 허용
      REGISTRY_HTTP_HEADERS_Access-Control-Allow-Origin: "[http://localhost:8082]"
      REGISTRY_HTTP_HEADERS_Access-Control-Allow-Methods: "[HEAD,GET,OPTIONS,DELETE]"
      REGISTRY_HTTP_HEADERS_Access-Control-Allow-Headers: "[Authorization,Accept,Cache-Control]"
      REGISTRY_HTTP_HEADERS_Access-Control-Expose-Headers: "[Docker-Content-Digest]"
    volumes:
      - regdata:/var/lib/registry
    restart: unless-stopped

  registry-ui:                         # 레지스트리를 눈으로
    image: joxit/docker-registry-ui:2.5.7
    ports:
      - "127.0.0.1:8082:80"
    environment:
      REGISTRY_TITLE: "사내 레지스트리 (실습)"
      REGISTRY_URL: "http://localhost:5000"
      SINGLE_REGISTRY: "true"
      DELETE_IMAGES: "true"
      SHOW_CONTENT_DIGEST: "true"
      CATALOG_ELEMENTS_LIMIT: "100"
    depends_on: [registry]
    restart: unless-stopped

volumes:
  regdata:
```

```bash
docker compose up -d && sleep 4

# 사내 레지스트리 주소로 태그를 바꿔 올린다 (프로젝트/이미지:태그 형식 — Harbor와 같다)
docker tag agent:0.2.0-offline localhost:5000/ax/agent:0.2.0
docker push localhost:5000/ax/agent:0.2.0
docker tag nicolaka/netshoot:v0.13 localhost:5000/tools/netshoot:v0.13
docker push -q localhost:5000/tools/netshoot:v0.13

# 레지스트리 API로 목록·다이제스트 확인
curl -s localhost:5000/v2/_catalog
curl -s localhost:5000/v2/ax/agent/tags/list
curl -sI -H "Accept: application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.v2+json" \
  localhost:5000/v2/ax/agent/manifests/0.2.0 | grep -i docker-content-digest

# 로컬 이미지를 지우고 레지스트리에서 받아 실행 — 고객 서버의 동작
docker rmi localhost:5000/ax/agent:0.2.0 agent:0.2.0-offline
docker run -d --rm --name from-reg -p 127.0.0.1:8000:8000 localhost:5000/ax/agent:0.2.0 && sleep 2
curl -s localhost:8000/healthz | jq -c .version
docker rm -f from-reg
```

!!! expect
    ```text
    {"repositories":["ax/agent","tools/netshoot"]}
    {"name":"ax/agent","tags":["0.2.0"]}
    Docker-Content-Digest: sha256:1e2d87f47d82c1ff7247856c6bbb7540262a1370ad4cbf1fbf24225a4492fb74
    0.2.0: Pulling from ax/agent
    ...
    Status: Downloaded newer image for localhost:5000/ax/agent:0.2.0
    "0.2.0"
    ```

!!! eye
    **레지스트리 UI** — 브라우저에서 `http://localhost:8082`. 저장소 목록 → `ax/agent` → 태그 목록에서 **Content Digest**, 크기, 아키텍처(amd64)를 봅니다. 고객사 Harbor UI도 같은 정보를 보여 주며, 거기에 취약점 스캔 결과와 "pull 차단" 여부가 추가됩니다. 반입 신청서의 다이제스트와 UI의 다이제스트가 같은지 대조하는 것이 반입 담당자의 확인 절차입니다.

### 실제 Harbor에서 추가로 마주칠 것

| 항목 | 내용 | 대응 |
|---|---|---|
| 인증 | `docker login harbor.corp.local` — 프로젝트별 계정 발급 | 로봇 계정(robot$ax+deploy) 요청. 사람 계정은 비밀번호 만료로 배포가 깨짐 |
| 프로젝트 | `harbor.corp.local/<프로젝트>/<이미지>:<태그>` | 프로젝트 생성 권한이 없으면 요청 |
| 자체 서명 인증서 | Harbor가 사내 CA 인증서를 쓰면 `docker pull`이 `x509: certificate signed by unknown authority` | 아래 명령. Day 8의 지식이 여기서 또 쓰임 |
| 스캔 정책 | Harbor가 Trivy로 자동 스캔, 기준 초과 시 **pull 차단** | 기준을 사전 확인, 반입 전 같은 기준으로 스캔 |
| 보존 정책 | 오래된 태그 자동 삭제 | 롤백용 태그가 지워지지 않도록 immutable 태그 요청 |
| 프록시 캐시 프로젝트 | Docker Hub를 미러링하는 프로젝트가 있으면 반입 없이 pull 가능 | 첫 미팅에서 확인 |

```bash
# 도커 데몬에 사내 레지스트리의 CA 등록 (고객 서버에서, sudo 필요)
sudo mkdir -p /etc/docker/certs.d/harbor.corp.local
sudo cp corp-ca.crt /etc/docker/certs.d/harbor.corp.local/ca.crt
# 데몬 재시작 불필요. 안 되면 sudo systemctl restart docker
docker login harbor.corp.local
```

!!! warn
    `/etc/docker/daemon.json`의 `insecure-registries`에 넣으면 TLS 검증을 끄는 것입니다. Day 8의 `verify=False`와 같은 문제이고 보안 심의에서 지적됩니다. CA를 등록하세요.

## 실습 9-4 — 폐쇄망 취약점 스캔과 SBOM

폐쇄망 안에서 스캔하려면 취약점 DB도 반입해야 합니다. DB는 하루에 몇 번 갱신되므로 반입 직전에 받습니다.

```bash
# ① 인터넷 되는 곳에서 DB만 받기 (2026년 9월 기준 약 1.4GB)
mkdir -p trivy-cache
docker run --rm -v "$PWD/trivy-cache:/root/.cache/" aquasec/trivy:0.56.2 image --download-db-only
du -sh trivy-cache

# ② 폐쇄망 안에서 (네트워크 없이) 스캔 — 갱신 시도를 끈다
docker run --rm --network none -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --severity HIGH,CRITICAL --scanners vuln --skip-db-update --skip-java-db-update \
  --format table --output trivy-agent-0.2.0.txt localhost:5000/ax/agent:0.2.0
grep -E "^localhost|Total:" trivy-agent-0.2.0.txt

# ③ SBOM (CycloneDX) — 구성 요소 목록 제출용
docker run --rm --network none -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --format cyclonedx --skip-db-update --output /root/.cache/sbom.json localhost:5000/ax/agent:0.2.0
mv trivy-cache/sbom.json sbom-agent-0.2.0.cdx.json
python3 -c "
import json; d=json.load(open('sbom-agent-0.2.0.cdx.json')); c=d.get('components',[])
print('구성 요소 수:', len(c))
print('pypi:', [(x['name'],x['version']) for x in c if x.get('purl','').startswith('pkg:pypi')])"
```

!!! expect
    ```text
    1.4G	trivy-cache
    localhost:5000/ax/agent:0.2.0 (debian 13.7)
    Total: 44 (HIGH: 44, CRITICAL: 0)
    구성 요소 수: 90
    pypi: [('pip', '25.0.1'), ('PyYAML', '6.0.2')]
    ```
    SBOM에는 OS 패키지 88개와 파이썬 패키지 2개가 들어 있습니다. "이 이미지 안에 무엇이 있습니까?"라는 심의 질문에 대한 기계가 읽을 수 있는 답입니다. 반입 담당자가 SBOM을 요구하지 않더라도 첨부하면 심의가 빨라집니다.

!!! verified
    ②③은 `--network none`으로 실제 실행했습니다. trivy DB 크기는 시점에 따라 다르며 앞으로 더 커집니다. 반입 매체 용량 제한이 있으면 `tar czf`로 압축해 반입하세요(압축률이 좋습니다).

### 반입 횟수를 줄이는 설계 점검

이미지를 만들 때마다 스스로 확인하세요.

- [ ] 프롬프트가 이미지 밖에 있는가 (볼륨 또는 ConfigMap)
- [ ] rubric·임계값이 이미지 밖에 있는가
- [ ] LLM 엔드포인트·모델명이 환경변수인가
- [ ] DB·API 접속 정보가 환경변수 또는 시크릿인가
- [ ] 로그 레벨을 환경변수로 바꿀 수 있는가
- [ ] 기능 on/off 플래그가 있는가
- [ ] 진단 엔드포인트(`/diag`, `/egress`, `/tcp`)가 있는가
- [ ] 진단용 이미지(netshoot)를 반입 목록에 포함했는가
- [ ] 의존 이미지(nginx, DB, 게이트웨이)를 반입 목록에 포함했는가
- [ ] 인터넷 없이 빌드·기동되는지 `--network none`으로 검증했는가
- [ ] non-root로 실행되는가
- [ ] 취약점 스캔을 통과했는가 (또는 예외 근거가 있는가)
- [ ] SBOM을 생성했는가
- [ ] 아키텍처가 고객 서버와 같은가 (amd64)

마지막 줄까지 체크되면 고객사 반입 담당자 입장에서 "일 잘하는 업체"가 됩니다. 실무적으로는, 첫 반입 이후 프롬프트와 임계값 튜닝을 며칠 대기 없이 할 수 있습니다.

## 오류 대응

!!! rollback
    - `pip download`가 `No matching distribution` → 플랫폼·파이썬 버전 불일치. 컨테이너 안에서 받았는지, `--platform`을 맞췄는지.
    - `docker build --network=none`이 베이스 이미지를 못 찾음 → 베이스 이미지가 로컬에 없으면 pull을 시도하다 실패합니다. 먼저 `docker pull python:3.12.14-slim`.
    - `docker push`가 `http: server gave HTTP response to HTTPS client` → 레지스트리가 HTTP인데 localhost가 아닌 주소로 접근. 실습에서는 `localhost:5000`만 쓰세요(도커는 localhost를 예외로 HTTP 허용).
    - 레지스트리 UI가 목록을 못 불러옴 → CORS 환경변수 오타. `curl localhost:5000/v2/_catalog`는 되는지 먼저 확인.
    - trivy `--skip-db-update`인데 DB가 없다고 함 → `trivy-cache/trivy/db/trivy.db`가 있는지. 마운트 경로는 `/root/.cache/`(끝 슬래시 포함).
    - dind가 안 뜸 → `--privileged` 불가 환경. WSL2 별도 배포판이나 VM으로 대체.
