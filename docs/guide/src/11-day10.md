# Day 10 — Kubernetes 기초: Pod · Deployment · Service · probe

<div class="day-meta"><span><b>소요</b> 3시간</span><span><b>만드는 것</b> k3d 클러스터, 첫 배포, STATUS 판별표</span><span><b>눈으로</b> k9s</span></div>

!!! why
    Compose로 올린 파일럿이 성공하면 정식 전환 논의에서 반드시 쿠버네티스가 나옵니다. 그리고 국내 대기업 온프렘 컨테이너 플랫폼은 **OpenShift 비중이 높습니다**(Red Hat의 쿠버네티스 배포판). 고객사에 이미 OpenShift가 있다면 배포는 훨씬 쉬워지고(VM 신청·도커 설치 협의가 사라짐), 없다면 VM + Compose가 현실적입니다.

    첫 주에 반드시 물어볼 질문: **"사내에 컨테이너 플랫폼이 있습니까? OpenShift입니까? 저희에게 네임스페이스(프로젝트)를 하나 내어 주실 수 있습니까?"** 이 답 하나로 배포 계획의 절반이 정해집니다.

    오늘은 쿠버네티스가 Compose와 무엇이 다른지를 Day 5의 장애 3종으로 직접 비교하고, 고객 환경에서 Pod가 안 뜰 때 5분 안에 원인 범위를 좁히는 순서를 익힙니다.

## 핵심 개념

### 쿠버네티스가 추가로 해 주는 것

Day 5에서 정리한 Compose의 한계가 그대로 쿠버네티스의 존재 이유입니다.

| 필요 | Compose | 쿠버네티스의 답 |
|---|---|---|
| 노드가 죽으면 다른 노드에서 재기동 | × | 스케줄러가 자동 재배치 |
| 응답 없는 컨테이너 교체 | × (Day 5 ③) | **liveness probe** |
| 준비되지 않은 컨테이너에 트래픽 차단 | × (Day 5 ②) | **readiness probe** |
| 무중단 배포 | × | 롤링 업데이트 + 롤백 |
| 수평 확장 | × | `replicas`, HPA |
| 선언한 상태 유지 | 부분 | 컨트롤러 루프 |

핵심 사상은 **선언형**입니다. "이 상태가 되어야 한다"를 적어 두면 쿠버네티스가 계속 그 상태로 맞춥니다. Compose는 "이 명령을 실행해라"에 가깝습니다.

### 최소한의 오브젝트

| 오브젝트 | 역할 | Compose 대응 | 어느 Day |
|---|---|---|---|
| **Pod** | 컨테이너 1개 이상의 최소 실행 단위. IP를 하나 가짐 | 컨테이너 | 오늘 |
| **Deployment** | Pod를 몇 개 유지할지 관리, 롤링 업데이트 | (없음) | 오늘 |
| **Service** | Pod 묶음에 고정 이름·IP 부여, 부하 분산 | 서비스 이름 DNS | 오늘 |
| **Namespace** | 논리적 구획. 권한·자원 할당 단위 | 프로젝트 | 오늘 |
| ConfigMap / Secret | 설정값 / 비밀값 | 환경변수·볼륨 / env_file | Day 11 |
| Ingress | 외부 HTTP 진입점 | ports + nginx | Day 11 |
| NetworkPolicy | Pod 간 통신 제어 | 네트워크 분리 | Day 12 |
| PVC | 영속 저장소 요청 | volumes | (개념만) |

### Service의 타입 — 온프렘에서 LoadBalancer가 Pending인 이유

| 타입 | 동작 | 언제 |
|---|---|---|
| `ClusterIP` | 클러스터 내부에서만 접근. 기본값 | 대부분 |
| `NodePort` | 모든 노드의 고정 포트(30000~32767)로 노출 | 테스트, 임시 |
| `LoadBalancer` | 외부 로드밸런서 연결 | 클라우드 |

온프렘에서는 `LoadBalancer`가 그냥 안 됩니다. 외부 LB를 붙여 주는 컴포넌트(클라우드 컨트롤러, MetalLB)가 없으면 `EXTERNAL-IP`가 영원히 `<pending>`입니다. 온프렘은 보통 **Ingress + 사내 로드밸런서(L4/L7 스위치)** 조합을 씁니다(Day 11). 이걸 모르면 고객 환경에서 `LoadBalancer` 서비스가 왜 안 되는지 헤매게 됩니다.

### Pod 네트워크와 방화벽 — 출발지 IP가 무엇인가

Pod는 각자 IP(예: 10.42.0.38)를 갖습니다. 그런데 이 대역은 대개 **클러스터 안에서만 유효**하고, Pod가 외부(DB존, 프록시)로 나갈 때는 노드 IP로 SNAT됩니다(Day 2의 MASQUERADE와 같은 원리). 그래서 방화벽 신청서의 출발지는 **노드 대역**입니다. 다만 CNI 설정에 따라 Pod IP가 그대로 라우팅되는 경우(Calico BGP 등)와, OpenShift처럼 네임스페이스별 **egress IP**를 주는 경우가 있습니다.

!!! check
    - 출발지를 무엇으로 적을지: 노드 대역 / Pod 대역 / egress IP. 플랫폼 운영팀에 "Pod에서 외부로 나갈 때 방화벽에 보이는 IP가 무엇입니까?"라고 물으세요.
    - **Pod CIDR·Service CIDR이 사내 대역과 겹치는지.** 겹치면 그 사내 시스템에 Pod가 영원히 못 갑니다 (Day 4의 도커 대역 충돌과 같은 문제).
    - 노드에서 프록시·CA가 어떻게 설정되어 있는지(kubelet의 이미지 pull은 노드 설정을 따름). "노드가 사내 레지스트리에서 pull이 되는가"는 우리가 아니라 플랫폼팀 소관입니다.

### kubectl과 권한

고객사는 클러스터 관리자 권한을 주지 않습니다. 보통 **네임스페이스 하나에 대한 RBAC 권한**과 kubeconfig 파일을 받습니다. 그 안에서 할 수 있는 것과 없는 것을 미리 확인합니다.

```bash
kubectl auth can-i --list -n <내-네임스페이스> | head -20    # 무엇을 할 수 있는가
kubectl auth can-i create networkpolicies -n <내-네임스페이스>
kubectl auth can-i get nodes                                 # 보통 no
```

## 실습 10-1 — 클러스터 만들기

k3d는 도커 컨테이너를 노드로 써서 가벼운 쿠버네티스(k3s)를 띄웁니다. 노드 3개(컨트롤 1 + 워커 2)와 사내 레지스트리 역할의 컨테이너를 함께 만듭니다.

```bash
mkdir -p ~/onprem-lab/day10 && cd ~/onprem-lab/day10

k3d cluster create onprem \
  --servers 1 --agents 2 \
  --registry-create onprem-registry:0.0.0.0:5001 \
  --port "8080:80@loadbalancer"          # Day 11 Ingress용: 호스트 8080 → 클러스터 80
kubectl get nodes
kubectl cluster-info | head -1
```

!!! expect
    ```text
    INFO[0032] Cluster 'onprem' created successfully!
    NAME                  STATUS   ROLES                  AGE   VERSION
    k3d-onprem-agent-0    Ready    <none>                 10s   v1.30.4+k3s1
    k3d-onprem-agent-1    Ready    <none>                 10s   v1.30.4+k3s1
    k3d-onprem-server-0   Ready    control-plane,master   15s   v1.30.4+k3s1
    Kubernetes control plane is running at https://0.0.0.0:35757
    ```
    `--registry-create`가 사내 Harbor 역할입니다. 호스트에서는 `localhost:5001`, 클러스터 안에서는 `onprem-registry:5000`으로 보입니다. 이미지를 여기 올려서 배포합니다.

```bash
docker tag agent:0.2.0 localhost:5001/ax/agent:0.2.0 && docker push -q localhost:5001/ax/agent:0.2.0
docker tag agent:0.3.0 localhost:5001/ax/agent:0.3.0 && docker push -q localhost:5001/ax/agent:0.3.0   # 롤링 업데이트용 (없으면 아래 참고)
curl -s localhost:5001/v2/ax/agent/tags/list
```

!!! note
    `agent:0.3.0`은 롤링 업데이트를 눈으로 보기 위한 "다음 버전"입니다. `cd ~/onprem-lab/agent && docker build --build-arg BASE=python:3.12.14-slim --build-arg APP_VERSION=0.3.0 -t agent:0.3.0 .`으로 만듭니다. 내용은 버전 문자열만 다릅니다.

!!! verified
    k3d 클러스터 생성과 노드 Ready까지는 세션 안에서 확인했습니다. 다만 이 문서를 만든 세션의 커널이 k3d 노드 안의 중첩 컨테이너 실행을 허용하지 않아, **이후 실습(10-2~10-6, Day 11·12)은 같은 매니페스트를 호스트에 직접 설치한 k3s(v1.30.4, 동일 버전)에서 실행해 검증했습니다.** 학습자 PC(Docker Desktop, WSL2, 일반 리눅스)에서는 k3d가 정상 동작합니다. 매니페스트와 출력은 동일하며, 노드 이름만 다릅니다.

## 실습 10-2 — 첫 배포

파일 세 개입니다. `securityContext` 블록은 Day 3의 심의 항목을 쿠버네티스 언어로 옮긴 것입니다.

```yaml
#file: 00-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: ax-pilot
  labels:
    zone: biz               # 업무망 존을 라벨로 표현 (Day 12의 NetworkPolicy가 이 라벨을 쓴다)
```

```yaml
#file: 10-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent
  namespace: ax-pilot
  labels: { app: agent }
spec:
  replicas: 2
  selector:
    matchLabels: { app: agent }
  template:
    metadata:
      labels: { app: agent, zone: biz }
    spec:
      securityContext:                      # Pod 수준
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 0
        fsGroup: 0
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: agent
          image: onprem-registry:5000/ax/agent:0.2.0     # 클러스터 안에서 보이는 사내 레지스트리 주소
          imagePullPolicy: IfNotPresent
          ports:
            - { containerPort: 8000, name: http }
          env:
            - { name: LOG_LEVEL, value: "INFO" }
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: "1",  memory: 512Mi }
          securityContext:                  # 컨테이너 수준
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - { name: tmp, mountPath: /app/tmp }
          readinessProbe:                   # 트래픽을 받아도 되는가
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:                    # 살아 있는가 (아니면 재시작)
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 10
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
      volumes:
        - { name: tmp, emptyDir: {} }
```

```yaml
#file: 20-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: agent
  namespace: ax-pilot
spec:
  type: ClusterIP
  selector: { app: agent }
  ports:
    - { name: http, port: 8000, targetPort: http }
```

```bash
kubectl apply -f 00-namespace.yaml -f 10-deployment.yaml -f 20-service.yaml
kubectl -n ax-pilot rollout status deployment/agent --timeout=120s
kubectl -n ax-pilot get all -o wide
```

!!! expect
    ```text
    namespace/ax-pilot created
    deployment.apps/agent created
    service/agent created
    deployment "agent" successfully rolled out
    NAME                         READY   STATUS    RESTARTS   AGE   IP           NODE
    pod/agent-5d6b6bc996-4x55h   1/1     Running   0          4s    10.42.0.16   k3d-onprem-agent-0
    pod/agent-5d6b6bc996-65sll   1/1     Running   0          4s    10.42.0.15   k3d-onprem-agent-1

    NAME            TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE   SELECTOR
    service/agent   ClusterIP   10.43.240.216   <none>        8000/TCP   4s    app=agent

    NAME                    READY   UP-TO-DATE   AVAILABLE   AGE   IMAGES
    deployment.apps/agent   2/2     2            2           4s    onprem-registry:5000/ax/agent:0.2.0
    ```
    Pod 두 개가 서로 다른 노드에 배치된 것을 보세요. 노드 하나가 죽어도 하나는 남습니다.

### securityContext — 보안 심의의 핵심

| 항목 | 의미 | 없으면 |
|---|---|---|
| `runAsNonRoot: true` | root로 실행 시 기동 거부 | 심의 지적 1순위 |
| `runAsUser: 10001` / `runAsGroup: 0` | 실행 UID·GID 고정 | OpenShift는 무시하고 임의 UID 부여 (Day 12) |
| `allowPrivilegeEscalation: false` | setuid로 권한 상승 차단 | |
| `readOnlyRootFilesystem: true` | 파일시스템 쓰기 차단. 쓰기 필요 경로는 `emptyDir`로 | 앱이 `/tmp`에 쓰다 실패 |
| `capabilities.drop: ["ALL"]` | 리눅스 커널 권한 전부 제거 | |
| `seccompProfile: RuntimeDefault` | 위험한 시스템콜 차단 | |

이 블록을 그대로 쓰면 보안 검토에서 지적받을 일이 거의 없습니다. 대신 애플리케이션이 이 제약 안에서 동작하는지 Day 3 실습 3-2에서 미리 확인해 두었습니다(`--read-only`, non-root). **Pod Security Standards의 `restricted` 프로파일**이 정확히 이 조합이고, 고객사 네임스페이스에 이 정책이 강제되어 있는 경우가 많습니다.

## 실습 10-3 — Service로 접근하기, 그리고 port-forward의 한계

```bash
# 클러스터 안의 진단 Pod
kubectl -n ax-pilot run probe --image=nicolaka/netshoot:v0.13 --restart=Never --command -- sleep 3600
kubectl -n ax-pilot wait --for=condition=Ready pod/probe --timeout=60s

# Service 이름으로 호출 — 두 Pod에 분산된다
kubectl -n ax-pilot exec probe -- sh -c 'for i in $(seq 1 8); do curl -s http://agent:8000/healthz | jq -r .host; done | sort | uniq -c'
kubectl -n ax-pilot exec probe -- sh -c 'nslookup agent | tail -2'

# 개발·진단용: 로컬 포트를 Service로 포워딩
kubectl -n ax-pilot port-forward svc/agent 8000:8000 &
sleep 2
for i in 1 2 3 4; do curl -s localhost:8000/healthz | jq -r .host; done | sort | uniq -c
kill %1
```

!!! expect
    ```text
          3 agent-64c5d66bdf-gfp8m
          5 agent-64c5d66bdf-pdmlm         ← Service가 두 Pod에 분산
    Name:	agent.ax-pilot.svc.cluster.local
    Address: 10.43.240.216

          4 agent-64c5d66bdf-pdmlm         ← port-forward는 Pod 하나에 고정
    ```
    `port-forward`는 **부하 분산을 하지 않습니다.** Service를 지정해도 Pod 하나를 골라 붙습니다. 진단·개발용이지 운영 경로가 아니며, SAC 환경(Day 1)에서는 아예 못 씁니다. 부하 분산을 보려면 클러스터 안에서 Service를 호출해야 합니다.

    Service의 완전한 DNS 이름은 `<서비스>.<네임스페이스>.svc.cluster.local`입니다. 다른 네임스페이스에서 부를 때 필요하고, `NO_PROXY`에 `.svc,.cluster.local`을 넣어야 하는 이유입니다(Day 7).

## 실습 10-4 — 자가 치유, 확장, 무중단 롤링 업데이트

```bash
# ① Pod를 지우면 즉시 새 Pod가 생긴다
kubectl -n ax-pilot delete pod $(kubectl -n ax-pilot get pod -l app=agent -o jsonpath='{.items[0].metadata.name}')
kubectl -n ax-pilot get pods -l app=agent

# ② replicas를 늘린다
kubectl -n ax-pilot scale deployment/agent --replicas=4 && sleep 8
kubectl -n ax-pilot get pods -l app=agent
kubectl -n ax-pilot scale deployment/agent --replicas=2

# ③ 롤링 업데이트 — 진행 중에도 요청이 끊기지 않는지 동시에 관찰
kubectl -n ax-pilot exec probe -- sh -c 'for i in $(seq 1 30); do curl -s -m2 http://agent:8000/healthz | jq -r .version; sleep 0.5; done | sort | uniq -c' &
kubectl -n ax-pilot set image deployment/agent agent=onprem-registry:5000/ax/agent:0.3.0
kubectl -n ax-pilot rollout status deployment/agent
wait

# ④ 이력과 롤백
kubectl -n ax-pilot rollout history deployment/agent
kubectl -n ax-pilot rollout undo deployment/agent
kubectl -n ax-pilot rollout status deployment/agent
kubectl -n ax-pilot get deployment agent -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

!!! expect
    ```text
    pod "agent-5d6b6bc996-4x55h" deleted
    NAME                     READY   STATUS    RESTARTS   AGE
    agent-5d6b6bc996-2fq5j   1/1     Running   0          1s        ← 새 Pod
    agent-5d6b6bc996-65sll   1/1     Running   0          57s

    (scale 4 후 4개, 다시 2개)

    Waiting for deployment "agent" rollout to finish: 1 out of 2 new replicas have been updated...
    Waiting for deployment "agent" rollout to finish: 1 old replicas are pending termination...
    deployment "agent" successfully rolled out
         19 0.2.0
         11 0.3.0                          ← 30번 요청 모두 성공. 구버전→신버전이 섞이며 넘어감
    REVISION  CHANGE-CAUSE
    1         <none>
    2         <none>
    deployment.apps/agent rolled back
    onprem-registry:5000/ax/agent:0.2.0    ← 롤백 완료
    ```
    ③이 중요합니다. **30번의 요청 중 실패가 없습니다.** 새 Pod가 readiness를 통과한 뒤에야 트래픽을 받고, 그 뒤에 구 Pod가 내려갑니다. vSphere HA는 VM을 다른 호스트에서 **재기동**하므로 수 분간 중단되지만(Day 1), 쿠버네티스는 남은 Pod가 트래픽을 받는 동안 새 Pod를 띄우므로 무중단입니다. 정식 운영 전환 시 쿠버네티스를 요구받는 이유입니다.

    노드 하나를 비우는 `kubectl drain <노드> --ignore-daemonsets --delete-emptydir-data` → Pod가 다른 노드로 이동 → `kubectl uncordon <노드>` 절차는 검증 환경이 단일 노드라 실행하지 못했습니다. k3d(노드 3개)에서는 `kubectl get pods -o wide`로 NODE 열이 바뀌는 것을 볼 수 있습니다. 고객사 플랫폼팀이 노드 점검 시 하는 작업이 이것이고, 우리 Pod가 `replicas: 1`이면 그 순간 서비스가 끊깁니다 — **운영은 최소 2**로 두는 이유입니다.

## 실습 10-5 — liveness가 Day 5의 "살아 있지만 무응답"을 해결한다

Day 5 실습 5-2 ③에서 Compose가 못 살린 상태를 그대로 만듭니다.

```bash
P=$(kubectl -n ax-pilot get pod -l app=agent -o jsonpath='{.items[0].metadata.name}')
IP=$(kubectl -n ax-pilot get pod $P -o jsonpath='{.status.podIP}')
kubectl -n ax-pilot exec probe -- curl -s -m5 "http://$IP:8000/_lab/hang"
sleep 50                                  # liveness: 10초 간격 × 3회 실패 + 여유
kubectl -n ax-pilot get pod $P
kubectl -n ax-pilot describe pod $P | grep -E "Unhealthy|Killing" | tail -3
```

!!! expect
    ```text
    {"hang": true}
    NAME                     READY   STATUS    RESTARTS      AGE
    agent-7f87967cf6-f84vl   1/1     Running   1 (20s ago)   6m5s        ← RESTARTS 1
      Warning  Unhealthy  27s (x3 over 47s)  kubelet  Liveness probe failed: Get "http://10.42.0.38:8000/healthz": context deadline exceeded
      Normal   Killing    27s                kubelet  Container agent failed liveness probe, will be restarted
      Warning  Unhealthy  1s (x12 over 46s)  kubelet  Readiness probe failed: ...
    ```
    사람이 개입하지 않았는데 재시작되었습니다. 그리고 **readiness가 먼저 실패**해서 그 Pod로 가던 트래픽이 다른 Pod로 옮겨진 뒤, liveness가 재시작했습니다. 두 probe의 역할 차이가 이것입니다.

| probe | 질문 | 실패 시 |
|---|---|---|
| readiness | 트래픽을 받아도 되는가 | Service에서 제외 (재시작 안 함) — DB 연결 대기, 워밍업 |
| liveness | 살아 있는가 | 컨테이너 재시작 — 데드락, 무한 대기 |
| startup | 기동이 끝났는가 | 기동이 오래 걸리는 앱(모델 로딩)에서 liveness가 너무 일찍 죽이는 것 방지 |

!!! warn
    liveness를 너무 공격적으로(짧은 `timeoutSeconds`, 낮은 `failureThreshold`) 잡으면 **LLM 응답을 기다리느라 바쁜 정상 Pod를 죽이는 사고**가 납니다. 에이전트는 `/healthz`가 LLM 호출과 무관하게 즉시 응답하도록 만들고(우리 에이전트는 그렇게 되어 있음), liveness의 `timeoutSeconds`는 넉넉히(3~5초) 둡니다. 모델을 로딩하는 앱은 `startupProbe`를 반드시 넣으세요.

!!! verified
    실습 10-2~10-5는 k3s v1.30.4에서 실행해 위 출력을 확인했습니다.

## 실습 10-6 — Pod가 안 뜰 때: 진단 순서와 STATUS 판별표

고장 다섯 개를 일부러 배포해 각각의 STATUS를 봅니다. `broken/` 디렉터리에 있습니다([부록 F](#부록-f-전체-실습-파일-트리)).

```bash
kubectl apply -f broken/
sleep 60
kubectl -n ax-pilot get pods | grep "b-"
```

!!! fail
    ```text
    b-configerror-5d86b95c76-xnmmb   0/1   CreateContainerConfigError   0            100s
    b-crashloop-76f96fcdb-7brsm      0/1   CrashLoopBackOff             4 (15s ago)  100s
    b-imagepull-6c78958d45-cmt8l     0/1   ImagePullBackOff             0            100s
    b-notready-5cd84bc7c4-vcb4s      0/1   Running                      0            100s
    b-pending-7c74794f46-m4p5k       0/1   Pending                      0            100s
    ```

진단은 이 순서입니다. 대부분 2번에서 끝납니다.

```bash
# 1. 상태 요약 — STATUS 열이 원인의 범주를 알려준다
kubectl -n ax-pilot get pods

# 2. 이벤트와 상세 — 원인의 90%가 여기 있다 (맨 아래 Events)
kubectl -n ax-pilot describe pod -l app=b-imagepull   | grep -A8 "^Events"
kubectl -n ax-pilot describe pod -l app=b-pending     | grep -A8 "^Events"
kubectl -n ax-pilot describe pod -l app=b-configerror | grep -A8 "^Events"
kubectl -n ax-pilot describe pod -l app=b-notready    | grep -A8 "^Events"

# 3. 애플리케이션 로그 (CrashLoop은 --previous 로 죽기 직전 로그)
kubectl -n ax-pilot logs deploy/b-crashloop
kubectl -n ax-pilot logs -l app=b-crashloop --previous

# 4. 네임스페이스 전체 이벤트 (시간순)
kubectl -n ax-pilot get events --sort-by=.lastTimestamp | tail -20

# 5. 컨테이너 안으로 / 진단 Pod
kubectl -n ax-pilot exec -it probe -- sh
```

!!! expect
    ```text
    Failed to pull image "onprem-registry:5000/ax/agent:9.9.9": ... manifest unknown / not found
    0/1 nodes are available: 1 Insufficient cpu, 1 Insufficient memory.
    Error: secret "agent-secret-typo" not found
    Readiness probe failed: HTTP probe failed with statuscode: 404
    설정 파일 없음: /app/config/required.yaml                    ← logs
    ```

| STATUS | 의미 | 확인할 것 |
|---|---|---|
| `ImagePullBackOff` / `ErrImagePull` | 이미지를 못 받음 | 레지스트리 주소·태그 오타, 인증(`imagePullSecrets`) 누락, 레지스트리 인증서, **노드의 프록시 설정** |
| `CrashLoopBackOff` | 기동 후 즉시 종료 반복 | `logs --previous`. 설정 누락, 권한, 포트 충돌 |
| `Pending` | 스케줄 안 됨 | 자원 부족(requests가 너무 큼), nodeSelector 불일치, PVC 미바인딩, 네임스페이스 쿼터 |
| `CreateContainerConfigError` | ConfigMap/Secret 없음 | 참조 이름 확인 |
| `Running` 이지만 `0/1` | readiness 실패 | probe 경로·포트, 기동 시간이 `initialDelaySeconds`보다 김 |
| `Init:0/1` | initContainer 대기 | initContainer 로그 |
| `OOMKilled` (describe의 Last State) | 메모리 상한 초과 | `limits.memory` 상향, Day 2 cgroup |
| `Terminating`에서 멈춤 | 종료 신호 무시 | 앱의 SIGTERM 처리, `terminationGracePeriodSeconds` |

**폐쇄망에서 `ImagePullBackOff`가 가장 흔합니다.** 원인은 대개 사내 레지스트리 인증 누락 또는 레지스트리 인증서 문제입니다(Day 8·9의 지식이 여기서 이어집니다).

```bash
# imagePullSecrets 만드는 방법 (고객사 Harbor용)
kubectl -n ax-pilot create secret docker-registry harbor-cred \
  --docker-server=harbor.corp.local --docker-username='robot$ax+deploy' --docker-password='<비밀번호>'
# Deployment의 spec.template.spec 에 추가:
#   imagePullSecrets:
#     - name: harbor-cred
```

```bash
kubectl delete -f broken/
```

!!! warn
    **노드 디스크가 85%를 넘으면 kubelet이 사용하지 않는 이미지를 지웁니다**(image GC). 이 문서를 만드는 세션에서도 실제로 겪었습니다 — 반입해 둔 이미지가 어느 날 사라져 `ImagePullBackOff`가 납니다. 고객사 VM에 디스크를 작게 받았다면 반드시 만나는 문제입니다. 대응: 노드 디스크 여유 확보, 사내 레지스트리에서 다시 pull 가능하게 유지, 반입 이미지 tar를 서버에 보관.
