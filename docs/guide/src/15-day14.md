# Day 14 — Walking Skeleton 종합: 전 구간 관통, 검증 스크립트, 런북, 이관

<div class="day-meta"><span><b>소요</b> 3~4시간</span><span><b>만드는 것</b> 첫 케이스 1주 차에 그대로 꺼내 쓸 키트 (<code>skeleton/</code>)</span><span><b>눈으로</b> verify.sh 결과, lazydocker, LiteLLM 대시보드</span><span><b>누적 점검</b> 최종</span></div>

!!! why
    지금까지 배운 것을 하나로 합칩니다. 결과물은 **첫 케이스 1주 차에 그대로 꺼내 쓸 수 있는 키트**입니다.

    Walking skeleton(tracer bullet)은 기능은 거의 없지만 **모든 층을 처음부터 끝까지 실제로 관통하는 최소 시스템**입니다. 목적은 기능 시연이 아니라 막히는 지점을 전부 드러내는 것입니다. 고객 환경에 이 skeleton을 1~2주 차에 올려 두면, 방화벽·인증서·이미지 반입·계정 발급의 **실제 리드타임을 숫자로** 알게 됩니다. 그 숫자가 있어야 정식 전환 로드맵이 추정이 아니라 실측이 됩니다.

    그리고 키트에는 코드보다 문서가 더 중요합니다 — 런북, 방화벽 신청서, 보안 협의 패키지, 정식 전환 조건. 기술 산출물은 프로젝트마다 다르지만 이 문서들은 거의 그대로 재사용되고, 보안심의 리드타임을 직접 줄입니다.

## 오늘 만들 구성

<pre class="diagram">
  사용자 PC
      │  (사내 DNS + 사내 LB)                                              [admin 망]
  [ nginx ]  ◀── DMZ. 유일한 인바운드 입구. /_lab/* 차단                 [ admin-proxy ] → 대시보드 /ui
      │                                                                        │
  [ agent ]  ◀── 업무망 + DB존. 인터넷 경로 없음                               │
      ├─────▶ [ postgres ]        ◀── DB존. 조회 전용 계정 ro_user            │
      └─────▶ [ llm-gateway ]  ◀── 업무망 + egress. 유일한 아웃바운드 ◀───────┘
                    │  ├─▶ [ audit-db ]   ◀── 감사 로그 (호출자·모델·토큰·비용)
                    ▼
              [ proxy (squid) ]  ◀── 화이트리스트. 목적지 1개
                    │
               외부 LLM API
</pre>

핵심 원칙 네 가지를 구현합니다. 각 원칙에는 이를 **증명하는 검증 항목**이 있습니다.

| 원칙 | 구현 | verify.sh 항목 |
|---|---|---|
| 에이전트는 인터넷에 직접 접근하지 않는다 | `biz`·`dbzone`은 `internal: true` | 3 |
| 아웃바운드 목적지는 게이트웨이 하나뿐이다 | `llm-gateway`만 `egress`에 걸침, 프록시 화이트리스트 | 5, 7 |
| 외부로 나간 모든 요청·응답이 사내에 기록된다 | LiteLLM → audit-db | 6 |
| 실데이터를 밖으로 꺼내지 않고 진단할 수 있다 | `/diag`, `/tcp`, `/egress` + 조회 전용 계정 | 2, 4 |

`compose.yaml` 전문은 [부록 F](#부록-f-전체-실습-파일-트리)에 있습니다. Day 6·7·13에서 만든 것을 합친 것이라 새로운 내용은 두 가지뿐입니다.

- **모든 이미지·비밀값이 `.env`로 빠져 있음** — `${AGENT_IMAGE:-agent:0.2.0}` 형식. 고객사에서는 `.env` 한 파일만 바꿉니다.
- **DB 초기화 스크립트가 조회 전용 계정을 만듦** — 보안 협의에서 "최소 권한" 근거가 됩니다.

```bash
#file: config/init-ro.sh
#!/bin/bash
# 최초 기동 시 1회 실행: 샘플 테이블 + 조회 전용 계정. 보안 협의에서 "최소 권한" 근거가 된다.
set -e
psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" <<SQL
CREATE TABLE IF NOT EXISTS sample_records (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    amount NUMERIC(14,2),
    created_at TIMESTAMPTZ DEFAULT now()
);
INSERT INTO sample_records (title, amount) VALUES
    ('샘플 계약 A', 1200000), ('샘플 계약 B', 830000), ('샘플 계약 C', 45000000);

CREATE USER ro_user WITH PASSWORD '${RO_DB_PASSWORD:-ro_pass}';
GRANT CONNECT ON DATABASE appdb TO ro_user;
GRANT USAGE ON SCHEMA public TO ro_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO ro_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO ro_user;
SQL
```

docker compose up -d

## 실습 14-2 — 관통 검증: verify.sh

이 스크립트가 키트의 핵심입니다. 고객 환경에서 배포 직후 한 번 돌려 결과를 배포 확인서에 첨부합니다. "됩니다"가 아니라 "15개 항목이 이렇게 통과했습니다"가 됩니다.

```bash
#file: verify.sh
#!/usr/bin/env bash
# 배포 직후 전 경로 관통 검증. 결과를 그대로 배포 확인서에 첨부한다.
# 사용법: ./verify.sh [BASE_URL]   (기본 http://localhost:8080)
set -u
BASE="${1:-http://localhost:${PUBLIC_PORT:-8080}}"
pass=0; fail=0
chk() { # chk <설명> <기대> <실제>
  if [ "$2" = "$3" ]; then printf "  [OK]   %s\n" "$1"; pass=$((pass+1))
  else printf "  [FAIL] %s (기대=%s 실제=%s)\n" "$1" "$2" "$3"; fail=$((fail+1)); fi
}
j() { docker compose exec -T "$@"; }

echo "== 1. 사용자 진입 (DMZ → 업무망)"
code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/healthz")
chk "GET /healthz" "200" "$code"
ver=$(curl -s "$BASE/healthz" | python3 -c 'import sys,json;print(json.load(sys.stdin)["version"])' 2>/dev/null)
chk "버전 = ${AGENT_VERSION:-0.2.0}" "${AGENT_VERSION:-0.2.0}" "$ver"
code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/_lab/hang")
chk "실습용 엔드포인트 차단 (/_lab/*)" "403" "$code"

echo "== 2. 환경 진단 (실데이터 노출 없음)"
diag=$(curl -s "$BASE/diag")
chk "LLM 엔드포인트 = 게이트웨이" "http://llm-gateway:4000/v1" "$(echo "$diag" | python3 -c 'import sys,json;print(json.load(sys.stdin)["llm_base_url"])')"
chk "프롬프트 파일 마운트됨" "True" "$(echo "$diag" | python3 -c 'import sys,json;print(json.load(sys.stdin)["prompt_exists"])')"
chk "non-root (uid 10001)" "10001" "$(echo "$diag" | python3 -c 'import sys,json;print(json.load(sys.stdin)["uid"])')"

echo "== 3. 에이전트 인터넷 직접 접근 차단"
out=$(curl -s "$BASE/egress?url=http://example.com" | python3 -c 'import sys,json;print(json.load(sys.stdin)["ok"])')
chk "에이전트 → 인터넷 직접" "False" "$out"

echo "== 4. DB — 조회 전용 계정 (읽기 허용 / 쓰기 차단)"
out=$(curl -s "$BASE/tcp?host=postgres&port=5432" | python3 -c 'import sys,json;print(json.load(sys.stdin)["ok"])')
chk "에이전트 → DB 포트 도달" "True" "$out"
r=$(j postgres psql -tAq -U ro_user -d appdb -c "SELECT count(*) FROM sample_records;" 2>/dev/null | tr -d '[:space:]')
chk "조회 전용 계정 읽기 (3건)" "3" "$r"
w=$(j postgres psql -tAq -U ro_user -d appdb -c "INSERT INTO sample_records(title) VALUES ('x');" 2>&1 | grep -qi "denied" && echo DENIED || echo ALLOWED)
chk "조회 전용 계정 쓰기 차단" "DENIED" "$w"

echo "== 5. LLM 게이트웨이 경유 호출과 통제"
ans=$(curl -s -X POST "$BASE/ask" -H 'Content-Type: application/json' -d '{"question":"검증 질문"}' | python3 -c 'import sys,json;print(json.load(sys.stdin).get("mode"))')
chk "에이전트 → 게이트웨이 → 모델" "llm" "$ans"
code=$(curl -s -o /dev/null -w '%{http_code}' "http://localhost:${ADMIN_PORT:-4000}/v1/chat/completions" -H "Authorization: Bearer wrong-key" -H 'Content-Type: application/json' -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"x"}]}')
chk "게이트웨이 잘못된 키 거부" "401" "$code"

echo "== 6. 감사 로그 적재"
sleep 6
n=$(j audit-db psql -tAq -U audit -d auditdb -c 'SELECT count(*) FROM "LiteLLM_SpendLogs";' 2>/dev/null | tr -d '[:space:]')
[ "${n:-0}" -ge 1 ] && chk "감사 DB 기록 ≥ 1건 (${n}건)" "yes" "yes" || chk "감사 DB 기록" "yes" "no"

echo "== 7. 프록시 화이트리스트 (게이트웨이 → 외부)"
# LiteLLM 이미지에는 curl이 없으므로 파이썬으로 (프록시 환경변수는 컨테이너에 이미 설정됨)
pyprobe='import sys,urllib.request
try: print(urllib.request.urlopen(sys.argv[1],timeout=10).status)
except Exception as e: print(getattr(e,"code",type(e).__name__))'
ok=$(j llm-gateway python3 -c "$pyprobe" http://example.com 2>/dev/null | tr -d '[:space:]')
chk "허용 목적지 example.com" "200" "$ok"
deny=$(j llm-gateway python3 -c "$pyprobe" http://www.google.com 2>/dev/null | tr -d '[:space:]')
chk "비허용 목적지 차단 (403)" "403" "$deny"

echo
echo "결과: 통과 $pass / 실패 $fail"
[ "$fail" -eq 0 ] || exit 1
```

```bash
./verify.sh
```

!!! verified
    실습 14-1·14-2는 세션 안에서 실행해 15개 항목 전부 통과를 확인했습니다. 항목 7은 LiteLLM 이미지에 curl이 없어 파이썬으로 확인합니다 — 폐쇄망에서 "진단 도구가 이미지에 없다"는 흔한 상황의 예이기도 합니다.

한 항목이라도 FAIL이면 배포 완료가 아닙니다. 어느 항목이 실패했느냐가 곧 누구에게 무엇을 요청할지를 알려 줍니다.

| 실패 항목 | 의미 | 요청 대상 |
|---|---|---|
| 1 | 진입 경로 | LB·DNS·방화벽 #1·#2 (네트워크팀) |
| 2 | 설정 누락 | 나 (`.env`, 마운트) |
| 3 | 에이전트가 인터넷에 열려 있음 | 나 (네트워크 구성 실수 — Day 6) |
| 4 | DB 방화벽 또는 계정 | 방화벽 #3, DBA |
| 5 | 게이트웨이·키 | 나 (`gateway/config.yaml`) |
| 6 | 감사 DB | 나 (`DATABASE_URL`) |
| 7 | 프록시·화이트리스트 | 프록시 운영팀, 방화벽 #5 |

## 실습 14-4 — 배포 런북

키트의 마지막 구성 요소입니다. 이 문서가 있으면 고객사 운영 조직에 이관할 수 있습니다. `RUNBOOK.md` 전문은 [부록 F](#부록-f-전체-실습-파일-트리)에 있고, 구성은 다음과 같습니다.

| 절 | 내용 | 누가 읽는가 |
|---|---|---|
| 1. 사전 조건 | VM, 방화벽 #1~#7, 레지스트리/반입, CA, 프록시, DB 계정, 키, DNS | 배포 전 나 |
| 2. 배포 절차 | load/pull → `.env` → config → `compose up` → `verify.sh` → 가상 키 | 운영 담당자 |
| 3. 검증 항목 | verify.sh 7개 그룹의 기대값 | 배포 확인서 |
| 4. 운영 절차 | 로그, 프롬프트 변경(재시작 불필요), 버전 업, 롤백, 감사 로그 조회, 디스크 정리 | 운영 담당자 |
| 5. 장애 대응 | 증상 → 1차 확인 → 조치 (502, 무응답, LLM 무응답, 인증서, DB, 디스크, 이미지 소실) | 운영 담당자 |
| 6. 이관 인수 항목 | 이미지 이력, 설정, 런북, 방화벽 내역, 감사 로그 정책, 가상 키, 전환 조건 | 이관 시 양측 |
| 7. 정식 전환 조건 | 파일럿에서 미충족인 것과 정식 요건 | 스폰서 |

7절이 특히 중요합니다. Day 5에서 확인한 Compose의 한계가 그대로 전환 조건이 됩니다.

| 항목 | 파일럿 현재 | 정식 요건 |
|---|---|---|
| 고가용성 | VM 1대 (단일 장애점) | 쿠버네티스/OpenShift 2노드 이상, replicas ≥ 2, liveness probe |
| 무응답 복구 | 사람이 재시작 | liveness probe 자동 재시작 |
| 인증 | 없음 (사내망 신뢰) | SSO(OIDC) 연동, 사용자별 권한·가상 키 |
| 부하 | 동시 5명 수준 검증 | 목표 동시 사용자 수 부하 시험, HPA |
| 관제 | 컨테이너 로그·`/metrics` | 사내 로그 수집·Grafana 연동, 알람 |
| 비밀 관리 | `.env` 평문 | Vault/KMS 연동 또는 Secret + RBAC |
| 백업 | 없음 | 감사 로그·설정 백업 정책, DR 대상 여부 |
| 배포 | 수동 `compose up` | Helm 차트 + 파이프라인(ArgoCD/Jenkins), 변경관리 절차 |
| 운영 주체 | FDE 팀 | 고객사 운영 조직 (지정 필요) + SLA |

!!! say
    "파일럿 구성은 VM 한 대의 Compose이고, 이 표의 왼쪽 열이 현재 상태입니다. 정식 서비스로 가려면 오른쪽 열이 필요하고, 각 항목의 담당과 예상 리드타임을 `docs/정식전환-조건.md`에 정리했습니다. 이 중 고가용성과 인증은 고객사 플랫폼팀·IT기획의 결정이 필요합니다."

## 실습 14-5 — 쿠버네티스가 있는 고객사라면: `k8s/`

고객사에 OpenShift/쿠버네티스가 있으면 `skeleton/k8s/`를 씁니다. Day 10~12의 매니페스트를 kustomize로 묶은 것이고, NetworkPolicy까지 포함합니다.

```bash
cd ~/onprem-lab/skeleton/k8s
kubectl -n ax-pilot create secret generic agent-secret \
  --from-literal=LLM_API_KEY='sk-pilot-local-key' --from-literal=DB_DSN='postgresql://...' --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -k .
kubectl -n ax-pilot rollout status deployment/agent
kubectl -n ax-pilot get netpol
curl -s -H "Host: agent.local" http://localhost:8080/healthz | jq -c '{version}'      # k3d
```

!!! expect
    ```text
    networkpolicy.networking.k8s.io/agent-egress created
    networkpolicy.networking.k8s.io/allow-ingress-controller created
    networkpolicy.networking.k8s.io/default-deny-ingress created
    deployment "agent" successfully rolled out
    NAME                       POD-SELECTOR   AGE
    agent-egress               app=agent      0s
    allow-ingress-controller   app=agent      0s
    default-deny-ingress       <none>         0s
    {"version":"0.2.0"}
    ```

`50-netpol.yaml`의 egress에서 **클러스터 밖 목적지(DB존 DB 서버)는 `ipBlock`으로** 적습니다 — `namespaceSelector`는 클러스터 안에서만 의미가 있습니다. 고객사 값(DB IP, Ingress 컨트롤러 네임스페이스, 이미지 주소, 호스트)으로 바꿀 곳은 파일 안에 주석으로 표시해 두었습니다. Helm 형태가 필요하면 Day 11의 `ax-agent` 차트를 씁니다.

!!! verified
    `kubectl apply -k`는 k3s에서 실행해 위 출력을 확인했습니다.

## 오류 대응

!!! rollback
    - `verify.sh` 항목 6이 FAIL → LiteLLM이 아직 DB 스키마를 만드는 중. 30초 뒤 다시.
    - 항목 4의 "읽기 3건" FAIL → `init-ro.sh`는 **볼륨이 처음 만들어질 때만** 실행됩니다. `docker compose down -v` 후 다시 `up`.
    - 항목 7 FAIL → `gateway/squid.conf`가 없거나 proxy가 재시작 중. `docker compose logs proxy`.
    - `.env`를 바꿨는데 반영이 안 됨 → `docker compose up -d`(재생성)를 해야 합니다. `restart`는 환경변수를 다시 읽지 않습니다.
    - 전부 다시: `docker compose down -v && docker compose up -d`.
