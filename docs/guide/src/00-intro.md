# 들어가며 — 이 가이드북을 쓰는 법

<p class="lead">2주 뒤, 고객사 인프라·보안 담당자와 마주 앉아 "어느 존에 올릴지, 어떤 경로로 나갈지, 무엇을 반입할지"를 그들의 언어로 이야기하고, 직접 배포하고, 막히면 원인을 스스로 좁힐 수 있는 상태가 되는 것이 목표입니다.</p>

## 누구를 위한 문서인가

| 전제 | 내용 |
|---|---|
| 배경 | 컴퓨터공학 전공. 에이전트 아키텍처 설계와 문제 정의에는 능숙함 |
| 경험 | 파이썬으로 RAG 에이전트를 직접 만들어 AWS EC2에 배포한 적이 있음 |
| 약한 곳 | 최근 구현을 AI 코딩 도구에 위임하면서 인프라·네트워크·배포 계층의 depth가 얕음 |
| 앞으로 | 컨설팅사 Forward Deployed Engineer. 고객은 국내 대기업. 온프렘·망분리·폐쇄망에 에이전트를 배포 |
| 학습 조건 | 혼자 학습. 옆에서 알려줄 사람이 없음 |

이 문서는 초보자용이 아닙니다. "컨테이너가 무엇인지"는 설명하지 않고, "고객사 보안팀이 컨테이너를 VM만큼 신뢰하지 않는 이유와 그때 무엇을 제안해야 하는지"를 설명합니다.

## 무엇을 얻는가 — 세 가지 목표

1. **속성** — 14일, 하루 2~3시간. 이론 완성도보다 현장 대응력.
2. **대기업 환경 이해** — vSphere, 망분리, DMZ, 프록시, 사내 CA, 폐쇄망 반입, 보안심의, 계열사 SI 구조가 실제로 어떻게 작동하는지.
3. **인프라·네트워크 개념 + 배포 역량** — 컨테이너·쿠버네티스·네트워크를 이해하고, 고객사 환경에 직접 배포하고, 막혔을 때 원인을 스스로 찾는 수준.

이 문서를 끝냈을 때 할 수 있어야 하는 것은 [부록 G의 자가 점검 목록](#부록-g-다음-단계-로드맵)에 있습니다. 시작 전에 한 번 읽어 두면 각 Day가 왜 그 순서로 배치되었는지 보입니다.

## 설계 원칙 — 코드보다 도구

이 가이드북의 실습은 **터미널 명령, 설정 파일(YAML/conf), 공개 이미지의 조합**으로 이루어집니다. 애플리케이션 코드를 쓰는 일은 거의 없습니다. 이유는 단순합니다. 고객사 현장에서 막히는 지점은 코드가 아니라 그 아래 계층이기 때문입니다.

| 원칙 | 구현 |
|---|---|
| 직접 작성하는 코드 최소화 | 웹 서버·에코 서버는 `nginx`, `traefik/whoami`, `hashicorp/http-echo` 같은 공개 이미지로 대체 |
| 학습용 에이전트는 한 번만 | `lab/agent/`에 바로 실행되는 형태로 제공. 코드 설명에 지면을 쓰지 않음 ([부록 F](#부록-f-전체-실습-파일-트리)) |
| 눈으로 확인 | Day마다 최소 하나의 GUI/TUI 도구로 상태를 봄 — lazydocker, dive, mitmweb, k9s, 레지스트리 UI, LiteLLM 대시보드 |
| 로컬 PC 한 대에서 완결 | 클라우드 계정은 Day 13의 선택 실습 하나에만 |
| 멱등 | 모든 실습은 다시 실행해도 깨지지 않고, 끝에 정리 명령이 있음 |

## 표기 규칙

이 문서에서 쓰는 상자의 의미입니다. 색만 보고도 구분할 수 있게 해 두었습니다.

!!! why
    이 절이 고객사 현장의 어떤 장면과 연결되는지. 각 절은 이 상자로 시작합니다.

!!! expect
    명령을 실행했을 때 이렇게 나오면 성공입니다. 출력의 일부(호스트명, IP, 시간)는 환경마다 다릅니다.

!!! fail
    일부러 실패시키는 실습입니다. 이 오류가 나오는 것이 정상이며, 그 오류를 현장에서 알아보는 것이 목적입니다.

!!! eye
    어떤 GUI/TUI 도구를 왜 여는지, 화면의 어디를 봐야 하는지.

!!! check
    고객사마다 다른 사항. 단정하지 않고 첫 미팅에서 확인해야 할 것.

!!! os
    macOS / Windows+WSL2 / Linux 에서 동작이 다른 지점.

!!! rollback
    실습이 어긋났을 때 되돌아가는 방법.

!!! say
    고객사 인프라·보안 담당자에게 그대로 쓸 수 있는 문장.

!!! verified
    이 문서를 만들 때 세션 안에서 실제로 실행해 출력을 확인한 명령입니다.

!!! unverified
    세션 안에서 실행해 보지 못한 명령입니다(GPU, 실제 OpenShift, 고객사 전용 도구 등). 대안이나 확인 방법을 함께 적어 두었습니다.

체크박스가 있는 항목은 실제로 체크할 수 있고, 진행 상황이 이 브라우저에 저장됩니다(저장이 안 되는 환경에서도 문서는 정상 동작합니다). 좌측 목차에서 Day별 진행률을 볼 수 있습니다.

## 실습 환경 한눈에 보기

모든 실습은 `~/onprem-lab/` 아래에서 진행하며, 전체 파일 트리는 [부록 F](#부록-f-전체-실습-파일-트리)에 있습니다. 파일을 하나씩 만들지 않고 부록 F의 압축본을 풀어서 시작해도 됩니다.

```text
~/onprem-lab/
├── agent/          # 학습용 에이전트 (한 번 빌드, 계속 재사용)
├── day01 … day13/  # Day별 실습 디렉터리
├── skeleton/       # Day 14 walking skeleton (첫 케이스에 가져갈 키트)
└── bootstrap.sh    # Day 0 부트스트랩
```

실습에 쓰는 이미지와 태그는 고정되어 있습니다. 시간이 지나 태그가 사라졌을 때의 대안은 각 Day에 적어 두었습니다.

| 역할 | 이미지 | 비고 |
|---|---|---|
| 웹/리버스 프록시 | `nginx:1.27-alpine` | |
| 에코 서버 | `traefik/whoami:v1.10`, `hashicorp/http-echo:1.0` | 호스트명·헤더를 그대로 보여줌 |
| 진단 도구 모음 | `nicolaka/netshoot:v0.13` | dig, curl, nc, tcpdump 포함. **폐쇄망 반입 목록에 반드시 포함** |
| DB | `postgres:16.4-alpine` | |
| 포워드 프록시 | `ubuntu/squid:5.2-22.04_beta` | |
| TLS 검사 프록시 | `mitmproxy/mitmproxy:11.0.0` | 사내 CA 역할 |
| 레지스트리 | `registry:2.8.3` + `joxit/docker-registry-ui:2.5.7` | Harbor 대역 |
| 취약점 스캔 | `aquasec/trivy:0.56.2` | |
| LLM 게이트웨이 | `ghcr.io/berriai/litellm:main-v1.55.8` | |
| 쿠버네티스 | k3d v5.7.4 (k3s v1.30) | |

## 시간 배분 권장

하루 2~3시간 기준입니다. "핵심 개념"은 30분을 넘기지 말고 실습으로 넘어가세요. 개념은 실습이 끝난 뒤 다시 읽으면 훨씬 빨리 들어옵니다.

| 구간 | 시간 |
|---|---|
| 왜 중요한가 + 핵심 개념 | 30분 |
| 실습 | 60~90분 |
| 눈으로 확인 + 체크포인트 | 20~30분 |
| 막혔을 때 여유 | 30분 |

막혔을 때는 먼저 그 Day의 "오류 대응" 상자를, 그다음 [부록 C 트러블슈팅 플레이북](#부록-c-트러블슈팅-플레이북-증상-원인)을 보세요.
