# Day 3 — Docker 이미지·레이어·컨테이너, 그리고 심의를 통과하는 이미지

<div class="day-meta"><span><b>소요</b> 2~3시간</span><span><b>만드는 것</b> 보안 심의 요건을 만족하는 <code>agent:0.2.0</code>, 취약점 스캔 리포트</span><span><b>눈으로</b> dive(레이어), lazydocker, trivy 리포트</span></div>

!!! why
    고객사에 무엇을 전달하느냐를 정하는 날입니다. 답은 거의 항상 **컨테이너 이미지 하나**입니다. 이유는 세 가지입니다. 고객 서버마다 파이썬 버전과 라이브러리가 다른 문제가 없어지고, 폐쇄망 반입 절차가 이미지 단위로 정립되어 있는 고객이 많으며, 나중에 쿠버네티스로 옮길 때 그대로 씁니다.

    그런데 대기업 반입 심의를 통과하려면 "돌아가는 이미지"가 아니라 **"심의를 통과하는 이미지"**여야 합니다. 보안팀의 반입 담당자는 이렇게 묻습니다.

    > "베이스 이미지가 승인 목록에 있나요? root로 실행되나요? 취약점 스캔 결과 첨부해 주세요. CRITICAL은 0건이어야 합니다. 이미지 안에 비밀번호나 키가 들어 있지 않다는 걸 어떻게 보증하시죠?"

    오늘 끝나면 이 네 질문에 리포트로 답할 수 있습니다.

## 핵심 개념

### 이미지 = 레이어의 쌓임

- **이미지** — 파일시스템 스냅샷 + 실행 설정(어떤 명령을, 어떤 사용자로, 어떤 포트로). 읽기 전용. 클래스에 해당.
- **컨테이너** — 이미지를 기반으로 실행 중인 인스턴스 + 얇은 쓰기 가능 레이어. 인스턴스에 해당.

이미지는 **레이어**의 쌓임입니다. Dockerfile의 명령 하나(`RUN`, `COPY`, `ADD`)가 레이어 하나를 만들고, 각 레이어는 캐시됩니다. 앞쪽 레이어가 바뀌지 않으면 다시 빌드하지 않습니다.

<pre class="diagram">
  agent:0.2.0
  ┌──────────────────────────────┐
  │ COPY app.py .         20 kB  │ ← 자주 바뀜 (코드) → 맨 위
  │ COPY /build/deps     3.1 MB  │ ← 가끔 바뀜 (의존성)
  │ RUN useradd ...       66 kB  │ ← 거의 안 바뀜
  │ python:3.12.14-slim  ~140 MB │ ← 베이스. 승인 목록에 있어야 함
  └──────────────────────────────┘
  각 레이어는 sha256 해시로 식별. 같은 레이어는 이미지가 달라도 한 번만 저장·전송.
</pre>

이 구조가 실무에서 의미하는 것 세 가지:

1. **비밀은 지워도 남습니다.** 앞 레이어에 넣은 파일을 뒤 레이어에서 `rm` 해도 앞 레이어에 그대로 있습니다. 오늘 직접 꺼내 봅니다.
2. **자주 바뀌는 것을 뒤로** 두면 빌드가 빠르고, 반입할 때도 바뀐 레이어만 전송됩니다(레지스트리 경유 시).
3. **베이스 이미지의 취약점은 내 것**입니다. `FROM`에 적은 이미지의 CVE가 스캔 리포트에 전부 나옵니다.

### 폐쇄망·심의 관점에서 중요한 설계

| 원칙 | 이유 | 이 문서의 구현 |
|---|---|---|
| 베이스 이미지 태그를 **패치 버전까지** 고정 | 재현성, 심의 추적. `python:3.12`는 매주 내용이 바뀜 | `ARG BASE=python:3.12.14-slim` |
| non-root 사용자로 실행 | 보안 심의 기본 항목. OpenShift는 아예 강제 | `USER 10001` |
| GID 0에 쓰기 권한 | OpenShift가 임의 UID로 실행해도 동작 (Day 12) | `chgrp -R 0 /app && chmod -R g=u /app` |
| 멀티스테이지 빌드 | 빌드 도구·캐시를 최종 이미지에서 제거 → 크기·취약점 감소 | `FROM ... AS builder` |
| `.dockerignore` | `.env`, `.git`이 이미지에 섞이는 사고 방지 | 제공됨 |
| 설정은 환경변수·마운트로 | 같은 이미지를 개발·고객사에서 그대로 사용 | `LLM_BASE_URL`, `PROMPT_PATH` |
| **비밀은 이미지에 넣지 않음** | 레이어는 누구나 열어볼 수 있음 | 실습 3-4에서 증명 |
| `HEALTHCHECK` | Compose의 `depends_on: condition` 과 운영 감시의 근거 | 제공됨 |
| `latest` 태그 금지 | "어떤 것을 반입했는가"를 말할 수 없음 | 항상 `agent:0.2.0` 형식 |

### 태그와 다이제스트

태그(`agent:0.2.0`)는 사람이 붙이는 이름이고 언제든 다른 내용을 가리킬 수 있습니다. 다이제스트(`sha256:...`)는 내용의 해시라서 바뀌지 않습니다. 반입 신청서에는 **태그와 다이제스트를 둘 다** 적습니다. 심의를 받은 것과 실제로 올린 것이 같다는 증거가 다이제스트입니다.

## 실습 3-2 — 심의 항목을 직접 확인하기

심의 담당자가 확인하는 것을 우리가 먼저 확인합니다.

```bash
# ① 실제로 non-root로 도는가
docker run --rm agent:0.1.0 id

# ② root가 아니라서 실패해야 하는 것 (의도된 실패)
docker run --rm agent:0.1.0 sh -c 'touch /etc/test; echo "종료코드=$?"'

# ③ 루트 파일시스템을 읽기 전용으로 띄워도 동작하는가 (쿠버네티스 readOnlyRootFilesystem 대비)
docker run --rm --read-only agent:0.1.0 sh -c 'touch /app/x; echo "종료코드=$?"'
docker run --rm --read-only --tmpfs /app/tmp agent:0.1.0 sh -c 'touch /app/tmp/x && echo "tmpfs 쓰기 OK"'

# ④ 헬스체크가 정의되어 있는가
docker inspect agent:0.1.0 --format '{{json .Config.Healthcheck.Test}}'
```

!!! expect
    ```text
    uid=10001(appuser) gid=0(root) groups=0(root)
    ```

!!! fail
    ```text
    touch: cannot touch '/etc/test': Permission denied
    종료코드=1
    touch: cannot touch '/app/x': Read-only file system
    종료코드=1
    tmpfs 쓰기 OK
    ["CMD-SHELL","python -c \"import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')\""]
    ```
    ②와 ③의 실패가 정상입니다. ③은 특히 중요합니다. 쿠버네티스 보안 정책에서 `readOnlyRootFilesystem: true`를 요구하면, 애플리케이션이 쓰는 경로(`/tmp`, 캐시)를 미리 알아 두고 별도 볼륨으로 빼야 합니다. 우리 에이전트는 `/app/tmp`만 쓰도록 만들어 두었습니다.

## 실습 3-3 — 취약점 스캔과 대응

대기업 이미지 반입 절차에는 거의 항상 취약점 스캔이 포함됩니다. 미리 통과시켜 두면 반입 리드타임이 줄어듭니다.

```bash
mkdir -p ~/onprem-lab/day03 && cd ~/onprem-lab/day03
# Trivy를 컨테이너로 실행. DB(수십 MB)를 처음 한 번 받으므로 캐시 디렉터리를 마운트해 둔다.
mkdir -p trivy-cache
docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --severity HIGH,CRITICAL --scanners vuln agent:0.1.0 | tail -40
```

!!! expect
    (2026년 9월 기준 실제 결과. 시간이 지나면 숫자는 커집니다)
    ```text
    agent:0.1.0 (debian 12.8)
    Total: 104 (HIGH: 95, CRITICAL: 9)

    ┌──────────┬────────────────┬──────────┬──────────────┬───────────────────┬────────────────────┬───────────────────┐
    │ Library  │ Vulnerability  │ Severity │ Status       │ Installed Version │ Fixed Version      │ Title             │
    ├──────────┼────────────────┼──────────┼──────────────┼───────────────────┼────────────────────┼───────────────────┤
    │ libcap2  │ CVE-2026-4878  │ HIGH     │ fixed        │ 1:2.66-4          │ 1:2.66-4+deb12u3   │ libcap: ...       │
    │ zlib1g   │ CVE-2023-45853 │ CRITICAL │ will_not_fix │ 1:1.2.13.dfsg-1   │                    │ zlib: integer ... │
    ...
    ```
    Day 0에서 `python:3.12.7-slim`(2024년 11월 빌드)을 그대로 썼기 때문입니다. **패치 태그를 고정하는 것과, 그 고정을 정기적으로 올리는 것은 다른 일**입니다. 첫 케이스에서 반입 직전에 스캔하면 이 화면을 봅니다.

`Status` 열이 대응 방법을 알려 줍니다.

| Status | 뜻 | 대응 |
|---|---|---|
| `fixed` | 패치된 버전이 있음 | 베이스 이미지 태그를 올리거나 `apt-get upgrade` |
| `affected` / `fix_deferred` | 배포판이 아직 패치 안 함 | 베이스 배포판 자체를 올림 (Debian 12 → 13), 또는 예외 승인 |
| `will_not_fix` | 배포판이 패치 안 할 것 | 예외 승인 (영향 없음을 근거로) |

가장 빠른 조치는 **베이스 이미지를 최신 패치 태그로 올려 재빌드**하는 것입니다. Dockerfile은 `ARG BASE`로 받게 되어 있으므로 파일을 고칠 필요가 없습니다.

```bash
cd ~/onprem-lab/agent
docker build --build-arg BASE=python:3.12.14-slim --build-arg APP_VERSION=0.2.0 -t agent:0.2.0 .
docker run --rm agent:0.2.0 python --version

cd ~/onprem-lab/day03
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --severity HIGH,CRITICAL --scanners vuln --skip-db-update agent:0.2.0 | grep -E "^agent|Total:"
# 패치가 존재하는 것만 세기 (예외 승인 대상을 분리)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --severity HIGH,CRITICAL --scanners vuln --skip-db-update --ignore-unfixed agent:0.2.0 | grep -E "Total:"
```

!!! expect
    ```text
    Python 3.12.14
    agent:0.2.0 (debian 13.7)
    Total: 44 (HIGH: 44, CRITICAL: 0)      ← CRITICAL 9 → 0
    Total: 0 (HIGH: 0, CRITICAL: 0)        ← 남은 44건은 전부 "패치 없음" (예외 승인 대상)
    ```

!!! verified
    위 두 스캔은 세션 안에서 실행한 실제 결과입니다. `apt-get upgrade`를 추가로 실행해 봤지만 3.12.14-slim은 이미 최신 패치라 숫자가 바뀌지 않았습니다.

!!! say
    "CRITICAL 0건입니다. HIGH 44건은 전부 Debian이 아직 패치를 제공하지 않는 항목(`--ignore-unfixed` 리포트 첨부)이고, 우리 애플리케이션은 해당 라이브러리(util-linux의 mount 등)를 호출하지 않으므로 예외 승인을 요청드립니다. 패치가 나오면 베이스 태그를 올려 재반입하겠습니다."

    "0건으로 만들어 오세요"라는 요구를 받으면 `alpine` 기반이나 distroless(`gcr.io/distroless/python3`)로 옮기는 방법이 있지만, 파이썬 패키지 컴파일 문제로 빌드가 복잡해집니다. 첫 케이스에서는 위 문장으로 협의하는 편이 빠릅니다.

**이후 모든 Day는 `agent:0.2.0`을 씁니다.**

## 실습 3-4 — 비밀은 지워도 남는다

"Dockerfile에서 넣었다가 지웠으니 괜찮다"가 왜 틀린지 직접 꺼내 봅니다.

```bash
mkdir -p ~/onprem-lab/day03/leak && cd ~/onprem-lab/day03/leak
echo "sk-live-in-a-file" > secret.txt
cat > Dockerfile <<'EOF'
FROM alpine:3.20
ENV API_KEY=sk-live-DO-NOT-DO-THIS
COPY secret.txt /root/secret.txt
RUN rm /root/secret.txt
EOF
docker build -q -t leak:1 .

# 컨테이너 안에서는 안 보인다
docker run --rm leak:1 ls /root/

# 그러나 이미지 메타데이터에 ENV가 그대로 있고
docker inspect leak:1 --format '{{.Config.Env}}'

# 지운 파일도 레이어 안에 남아 있다
docker save leak:1 -o leak.tar && mkdir -p x && tar xf leak.tar -C x
for b in x/blobs/sha256/*; do
  tar tf "$b" 2>/dev/null | grep -q "root/secret.txt" && echo "레이어 $(basename "$b" | cut -c1-12) 안에: $(tar xOf "$b" root/secret.txt)"
done
rm -rf x leak.tar; docker rmi leak:1 >/dev/null
```

!!! expect
    ```text
    (빈 출력 — 컨테이너 안에는 없음)
    [PATH=/usr/local/sbin:... API_KEY=sk-live-DO-NOT-DO-THIS]     ← ENV는 영구히 남는다
    레이어 7cbcbbc0be25 안에: sk-live-in-a-file                   ← rm 했지만 앞 레이어에 그대로
    ```
    이미지를 받은 사람은 누구나 5줄짜리 셸로 이걸 꺼낼 수 있습니다. 비밀은 **실행 시점에** 환경변수·볼륨·Secret(Day 11)으로 넣습니다. 빌드 시점에 꼭 필요하면(사내 PyPI 인증 등) BuildKit 시크릿(`RUN --mount=type=secret`)을 씁니다.

## 실습 3-5 — 반입 패키지 초안

Day 9에서 완성할 반입 신청서의 이미지 항목을 지금 채워 둡니다.

```bash
cd ~/onprem-lab/day03
docker image inspect agent:0.2.0 --format 'ID={{.Id}}
User={{.Config.User}}
Exposed={{json .Config.ExposedPorts}}
Size={{.Size}}
Base={{index .Config.Env 0}}' 
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/trivy-cache:/root/.cache/" \
  aquasec/trivy:0.56.2 image --severity HIGH,CRITICAL --scanners vuln --skip-db-update \
  --format table --output trivy-agent-0.2.0.txt agent:0.2.0 && head -5 trivy-agent-0.2.0.txt
```

| 항목 | 값 (agent:0.2.0) | 근거 |
|---|---|---|
| 이미지명:태그 | `agent:0.2.0` | |
| 이미지 ID / 다이제스트 | `docker image inspect` 출력 | 심의본 = 반입본 증명 |
| 베이스 이미지 | `python:3.12.14-slim` (Debian 13.7) | 고객사 승인 목록 대조 |
| 실행 사용자 | UID 10001 / GID 0 (non-root) | `docker run --rm agent:0.2.0 id` |
| 노출 포트 | 8000/TCP | |
| 취약점 | CRITICAL 0 / HIGH 44 (전부 패치 미제공, 예외 요청) | `trivy-agent-0.2.0.txt` 첨부 |
| 비밀 정보 포함 | 없음 | ENV 목록 + `.dockerignore` |
| 읽기 전용 루트 FS | 지원 (`/app/tmp`만 쓰기) | 실습 3-2 |
| 헬스체크 | `/healthz` | |

!!! check
    - 고객사 **승인 베이스 이미지 목록**이 있으면 `python:*-slim`(Debian)이 아니라 RHEL UBI(`registry.access.redhat.com/ubi9/python-312`)만 허용하는 곳이 많습니다. 그 경우 Dockerfile의 패키지 명령(`apt` → `dnf`/`microdnf`)과 CA 경로(Day 8)가 달라집니다. 첫 미팅에서 확인하세요.
    - 취약점 기준: "CRITICAL 0"인 곳, "HIGH 이상 0"인 곳, "패치 있는 것만 0"인 곳이 섞여 있습니다. 기준을 문서로 받아 두세요.

## 눈으로 확인 — lazydocker에서 이미지와 레이어

!!! eye
    **lazydocker → Images** 탭에서 `agent:0.2.0`을 고르면 오른쪽에 레이어 목록(`docker history`와 같은 내용)이 나옵니다. 총 크기가 200MB 아래인지, `<none>` 태그의 이미지(dangling)가 쌓이고 있지 않은지 봅니다. 고객사 VM의 디스크를 채우는 흔한 원인이 재빌드할 때마다 남는 `<none>` 이미지입니다. lazydocker에서 이미지를 고르고 <kbd>d</kbd>를 누르면 지울 수 있고, 한 번에 정리하려면 `docker image prune -f`입니다.

## 오류 대응

!!! rollback
    - trivy가 `TOOMANYREQUESTS` 또는 DB 다운로드 실패 → 회사 프록시(Day 7·8) 또는 GitHub 컨테이너 레지스트리 접근 제한. `-e HTTPS_PROXY=...`를 컨테이너에 넘기거나, 인터넷 되는 곳에서 `trivy image --download-db-only` 후 캐시 디렉터리를 통째로 반입합니다. **폐쇄망에서는 이것이 정식 절차**입니다.
    - trivy가 `unable to initialize a docker client` → `-v /var/run/docker.sock:/var/run/docker.sock` 누락, 또는 rootless 도커. 대안: `docker save agent:0.2.0 -o a.tar` 후 `trivy image --input a.tar`.
    - `python:3.12.14-slim` 태그가 사라졌다면(오래된 패치는 Docker Hub에서 지워지기도 함) `docker run --rm python:3.12-slim python --version`으로 현재 패치 버전을 확인하고 그 태그로 고정하세요.
    - dive 오류 `could not find 'blobs/sha256/...'` → dive 0.13.1 이상으로.
