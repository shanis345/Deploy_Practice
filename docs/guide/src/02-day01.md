## 핵심 개념

### 다섯 개의 층

아래에서 위로 다섯 층입니다. 각 층은 아래 층이 주는 것만 쓸 수 있고, 위 층에 대해서는 아무것도 모릅니다.

<pre class="diagram">
┌──────────────────────────┐
│ 애플리케이션 프로세스     │ ← 에이전트 코드. 파이썬 인터프리터 위에서 실행
├──────────────────────────┤
│ 컨테이너                 │ ← 커널 기능(namespace·cgroup)으로 파일시스템·네트워크·프로세스 격리
├──────────────────────────┤
│ 게스트 OS (VM 안의 리눅스)│ ← RHEL 8/9, Ubuntu. 여기에 Docker/containerd가 설치됨
├──────────────────────────┤
│ 하이퍼바이저 (ESXi)      │ ← 물리 자원을 쪼개 VM에 배분. 그 자체가 얇은 OS
├──────────────────────────┤
│ 물리 서버                │ ← CPU·메모리·디스크·NIC. 데이터센터 랙에 꽂혀 있음
└──────────────────────────┘
</pre>

**하이퍼바이저**는 물리 서버 한 대를 여러 대처럼 쓰게 합니다. VMware ESXi가 대표이고, 리눅스의 KVM, 마이크로소프트의 Hyper-V, 최근 국내에서 늘고 있는 Nutanix AHV가 같은 부류입니다. ESXi는 OS 위에 설치하는 프로그램이 아니라 그 자체가 물리 서버에 직접 설치되는 얇은 OS입니다(type-1). 여러분의 노트북에서 도는 VirtualBox나 Docker Desktop의 VM은 OS 위의 프로그램(type-2)입니다.

**vCenter**는 ESXi 호스트 수십~수백 대를 묶어 관리하는 중앙 콘솔입니다. 대기업이 vSphere를 쓰는 진짜 이유가 여기에 있습니다.

| 기능 | 하는 일 | 내가 얻는 것 |
|---|---|---|
| HA | 호스트가 죽으면 VM을 다른 호스트에서 **재기동** | 하드웨어 장애 시 자동 복구 (몇 분 중단) |
| vMotion | 서비스 중단 없이 VM을 다른 호스트로 이동 | 하드웨어 점검 시 무중단 |
| DRS | 부하에 따라 VM 배치 자동 조정 | 자원 효율 |
| 템플릿 | 표준 OS 이미지를 복제해 VM 생성 | 보안 설정이 끝난 서버를 빠르게 |
| 스냅샷 | 특정 시점의 VM 상태 저장 | 롤백 |
| 리소스 풀 | 부서·프로젝트별 자원 할당 상한 | "우리 몫"이 얼마인지 |

여기서 **중요한 오해 하나**를 짚고 갑니다. vSphere HA는 "VM"을 되살립니다. VM 안에서 죽은 컨테이너나 프로세스는 되살리지 않습니다. 그래서 VM 한 대에 Docker Compose로 올린 서비스는 컨테이너가 죽으면 그대로 멈춥니다(`restart: always`를 걸면 도커가 재시작해 주지만, VM 전체가 문제면 소용없고, 프로세스가 살아 있는데 응답만 못 하는 상태는 잡지 못합니다). 쿠버네티스가 필요해지는 첫 번째 이유가 이것입니다. Day 5에서 직접 재현합니다.

### VM과 컨테이너의 차이 — 보안팀이 보는 관점

| | VM | 컨테이너 |
|---|---|---|
| 격리 단위 | 하드웨어 수준 (가상 CPU·디스크) | 커널 기능 수준 (namespace·cgroup) |
| OS | 각자 게스트 OS를 통째로 가짐 | 호스트 커널을 공유 |
| 기동 시간 | 수십 초~수 분 | 수백 밀리초~수 초 |
| 크기 | 수 GB~수십 GB | 수십 MB~수 GB |
| 보안 경계 | 강함 | VM보다 약함 (커널 공유) |
| 장애 시 되살리는 주체 | vSphere HA | 도커 데몬 또는 쿠버네티스 |

대기업 현장에서 이 차이가 드러나는 지점: 보안팀은 컨테이너의 격리를 VM만큼 신뢰하지 않습니다. 그래서 "에이전트가 코드를 실행하는 기능이 있다"거나 "외부 문서를 파싱한다"고 하면 컨테이너가 아니라 **별도 VM으로 격리**하라는 요구가 나옵니다. 이건 기술적으로 타당한 요구이고, 여기에 맞서기보다 "그 기능만 별도 VM(또는 별도 노드 풀)로 분리하겠다"고 답하는 편이 빠릅니다.

!!! say
    "에이전트 런타임 자체는 컨테이너로 올리되, 코드 실행이나 외부 파일 파싱처럼 위험도가 높은 기능은 별도 VM으로 분리하겠습니다. 그 VM은 업무망 안에서도 에이전트 VM과만 통신하도록 방화벽을 잡겠습니다."

### 컨테이너 격리의 실체

컨테이너는 마법이 아니라 리눅스 커널의 두 가지 기능입니다.

- **네임스페이스(namespace)** — "무엇을 볼 수 있는가"를 제한합니다. PID 네임스페이스가 다르면 다른 프로세스가 안 보이고, 네트워크 네임스페이스가 다르면 다른 네트워크 인터페이스와 라우팅 테이블을 갖습니다. 마운트 네임스페이스가 다르면 다른 파일시스템 트리를 봅니다.
- **cgroup** — "얼마나 쓸 수 있는가"를 제한합니다. CPU, 메모리, I/O 상한.

이걸 알아야 하는 실무적 이유: 고객 환경에서 "컨테이너 안에서만 DNS가 안 된다", "컨테이너에서만 사내망이 안 보인다" 같은 문제를 만나면, 원인은 거의 항상 **네트워크 네임스페이스가 호스트와 다르다**는 데서 출발합니다. Day 2에서 이 네임스페이스를 손으로 직접 만들어 봅니다.

### 국내 대기업 IT 조직 — 누구에게 무엇을 물어야 하는가

기술 계층만큼 중요한 것이 **조직 계층**입니다. 국내 대기업은 대체로 아래 구조입니다. 회사마다 이름은 다르지만 역할은 비슷합니다.

<pre class="diagram">
[사업부(현업)] ─── 우리를 부른 사람. 예산·요구사항 소유. 인프라 권한 없음
      │
[정보전략/IT기획] ─ 시스템 도입 승인, 표준(아키텍처·보안 가이드) 관리, 예산 집행
      │
   ┌──┴──────────────────────────────────────────────┐
[정보보호(보안팀)]                        [IT운영 = 그룹 SI 계열사 또는 외주]
 · 보안심의(보안성 검토)                     · vSphere/VM 발급, 네트워크·방화벽 "작업"
 · 방화벽 정책 "승인"                        · DB 계정, 레지스트리, 모니터링
 · 취약점 스캔 기준, 반입 심사               · 장애 대응, 변경관리(CAB)
 · 개인정보·데이터 반출 규정                 · 실제 명령을 치는 사람들
</pre>

| 내가 필요한 것 | 누가 결정 | 누가 실행 | 통상 리드타임 |
|---|---|---|---|
| VM 발급 | IT기획(예산) → IT운영 | IT운영(SI) | 3~10 영업일 |
| 방화벽 개방 | **보안팀 승인** | IT운영(네트워크 파트) | 3~10 영업일 (승인 후 작업일 별도) |
| 인터넷 아웃바운드/화이트리스트 | 보안팀 | 네트워크/프록시 운영 | 5~15 영업일 |
| 이미지 반입 | 보안팀(반입 심사) | 반입 담당자 | 2~5 영업일/회 |
| DB 계정 | 데이터 owner 부서 + DBA | DBA | 3~7 영업일 |
| 외부 LLM API 사용 | 보안팀 + 법무/개인정보 | — | 2주~수개월 (정책 유무에 따라) |
| 운영 데이터 접근 | 데이터 owner + 보안심의 | DBA | 보안심의 후 |

!!! check
    - 리드타임은 회사마다 크게 다릅니다. 위 수치는 감을 잡기 위한 것이고, **첫 미팅에서 항목마다 실제 소요 기간을 물어 [부록 A-7 리드타임 집계표](#a-7-리드타임-집계표)에 적는 것**이 Day 1의 진짜 숙제입니다.
    - "IT운영"이 그룹 SI 계열사(삼성SDS, LG CNS, SK C&C, 현대오토에버, 포스코DX 등)인 경우, 계열사의 변경관리 절차(CAB, 정기 배포일)가 별도로 있습니다. "배포 가능 요일과 시간대"를 반드시 물으세요. 금요일 배포 금지, 월말 결산 기간 변경 동결(freeze)이 흔합니다.
    - 보안팀은 "승인"하고 IT운영은 "실행"합니다. 둘은 다른 조직이고 서로의 일정을 모릅니다. 승인 났다고 열린 것이 아닙니다.

### 서버 접근 방식 — SAC

대기업은 대부분 서버에 직접 SSH를 못 합니다. **서버접근제어(SAC, Server Access Control)** 솔루션(예: 넷앤드 HIWARE, 시큐어키, CyberArk 등)을 통해서만 접속하고, 세션이 녹화됩니다. 이것이 개발 방식에 주는 영향은 큽니다.

| 제약 | 결과 | 대응 |
|---|---|---|
| 파일 전송 제한 (scp 불가, 웹 업로드만) | 이미지 tar 전달이 번거로움 | 반입 절차와 통합, 횟수 최소화 (Day 9) |
| 포트 포워딩 불가 | `kubectl port-forward`, 로컬 브라우저로 대시보드 못 봄 | TUI 도구(k9s, lazydocker)를 서버에 반입 |
| 세션 타임아웃(10~30분) | 긴 빌드가 끊김 | `nohup`, `tmux`(허용 시), 빌드는 로컬에서 하고 이미지만 반입 |
| 클립보드 붙여넣기 제한 | 긴 명령 입력 곤란 | 스크립트 파일로 반입 (`verify.sh`, Day 14) |
| sudo 제한 | 도커 데몬 설정 변경 불가 | 필요한 설정을 **VM 신청서에 미리** 포함 |

이 문서가 GUI 대신 TUI 도구(lazydocker, k9s)를 기준으로 하는 이유가 이것입니다. 포트 포워딩이 안 되는 서버에서도 동작합니다.

    화면 공유를 받으면 **VM의 Summary 탭**을 보여 달라고 하세요. 거기에 게스트 OS, vCPU·메모리, 연결된 포트그룹(네트워크), 데이터스토어, VMware Tools 상태가 한 번에 나옵니다. 포트그룹 이름에 VLAN 번호와 존 이름이 들어 있는 경우가 많아서, 그것만 봐도 어느 망에 있는지 알 수 있습니다.

## 실습 1-2 — VM 신청서 항목 만들기

첫 케이스에서 그대로 쓸 **VM 신청 시 물어볼 항목**입니다. 아래 표를 복사해 답을 채우세요.

| # | 항목 | 왜 필요한가 | 답 |
|---|---|---|---|
| 1 | vCPU / 메모리 / 디스크 — 그리고 증설 절차와 소요 기간 | 파일럿 후 부하 시험에서 늘려야 함 | |

## 실습 1-3 (선택) — Ansible로 VM 초기 설정 자동화 맛보기 <span class="badge opt">선택</span>

VM이 두 대만 되어도 "두 번째 VM에도 똑같이 해 주세요"라는 말이 나옵니다. 그때 손으로 하지 않고 **플레이북**으로 하는 감각만 익힙니다. 실제 VM 대신 컨테이너를 VM처럼 취급합니다(Ansible의 docker 연결 플러그인).

```bash
cd ~/onprem-lab/day01 2>/dev/null || mkdir -p ~/onprem-lab/day01 && cd ~/onprem-lab/day01
python3 -m venv .venv && . .venv/bin/activate
pip install -q ansible-core && ansible-galaxy collection install community.docker

# "VM" 두 대 (컨테이너로 흉내)
docker run -d --rm --name vm-agent-01 python:3.12.7-slim sleep infinity
docker run -d --rm --name vm-agent-02 python:3.12.7-slim sleep infinity
```

```ini
#file: inventory.ini
[agent_vms]
vm-agent-01 ansible_connection=community.docker.docker
vm-agent-02 ansible_connection=community.docker.docker

# 실제 VM이라면 이렇게 바뀝니다 (SAC 경유 시 ProxyCommand 필요)
# vm-ai-agent-01 ansible_host=10.20.30.41 ansible_user=svc_deploy
```

```yaml
#file: prepare-vm.yaml
- name: 에이전트 VM 기본 준비
  hosts: agent_vms
  gather_facts: true
  vars:
    app_user: appuser
    app_uid: 10001
    proxy_url: "http://proxy.corp.example:3128"
    no_proxy: "localhost,127.0.0.1,.corp.example,10.0.0.0/8"
  tasks:
    - name: 서비스 계정 생성
      ansible.builtin.user:
        name: "{{ app_user }}"
        uid: "{{ app_uid }}"
        shell: /usr/sbin/nologin
        create_home: true
    - name: 애플리케이션 디렉터리
      ansible.builtin.file:
        path: /opt/agent/{{ item }}
        state: directory
        owner: "{{ app_user }}"
        mode: "0750"
      loop: [config, data, logs]
    - name: 도커 데몬 설정 (로그 로테이션 + 프록시)   # 실제 VM에서는 /etc/docker/daemon.json
      ansible.builtin.copy:
        dest: /etc/docker-daemon.json
        mode: "0644"
        content: |
          {
            "log-driver": "json-file",
            "log-opts": { "max-size": "10m", "max-file": "3" },
            "proxies": {
              "http-proxy": "{{ proxy_url }}",
              "https-proxy": "{{ proxy_url }}",
              "no-proxy": "{{ no_proxy }}"
            }
          }
    - name: 사실 확인 — OS와 메모리
      ansible.builtin.debug:
        msg: "{{ ansible_distribution }} {{ ansible_distribution_version }}, mem {{ ansible_memtotal_mb }}MB, cpu {{ ansible_processor_vcpus }}"
```

```bash
ansible-playbook -i inventory.ini prepare-vm.yaml
# 한 번 더 — 바뀐 것이 없으면 changed=0 이어야 한다 (멱등)
ansible-playbook -i inventory.ini prepare-vm.yaml | tail -3
```

!!! expect
    첫 실행:

    ```text
    PLAY [에이전트 VM 기본 준비] ***************************************************

    TASK [Gathering Facts] *********************************************************
    ok: [vm-agent-01]
    ok: [vm-agent-02]

    TASK [서비스 계정 생성] ********************************************************
    changed: [vm-agent-01]
    changed: [vm-agent-02]

    TASK [애플리케이션 디렉터리] ***************************************************
    changed: [vm-agent-01] => (item=config)
    ...
    TASK [사실 확인 — OS와 메모리] *************************************************
    ok: [vm-agent-01] => {
        "msg": "Debian 12.8, mem 8032MB, cpu 2"
    }

    PLAY RECAP *********************************************************************
    vm-agent-01                : ok=5    changed=3    unreachable=0    failed=0 ...
    vm-agent-02                : ok=5    changed=3    unreachable=0    failed=0 ...
    ```

    두 번째 실행은 `changed=0`입니다. "이미 그 상태면 아무것도 하지 않는다"가 Ansible의 핵심이고, 고객사 IT운영이 플레이북을 좋아하는 이유입니다. 같은 것을 두 번 돌려도 사고가 나지 않습니다.

!!! verified
    이 플레이북은 세션 안에서 실행해 위 출력을 확인했습니다. `ansible_connection=docker`(짧은 이름)는 최신 ansible-core에서 동작하지 않아 `community.docker.docker`로 써야 합니다.

```bash
docker rm -f vm-agent-01 vm-agent-02
deactivate
```

!!! note
    Terraform은 VM을 "만드는" 도구(vSphere provider로 VM 생성), Ansible은 만들어진 VM을 "설정하는" 도구입니다. 국내 대기업에서 FDE가 VM 생성 권한을 받는 일은 드물기 때문에 이 문서는 Ansible만 맛봅니다. 고객사가 Terraform으로 VM을 찍어 낸다면 `tfvars`에 우리 스펙을 넣어 달라고 요청하는 것으로 충분합니다.

## 오류 대응

    - `ansible-galaxy collection install`이 실패하면 회사 프록시 문제입니다. `pip`과 마찬가지로 `HTTPS_PROXY`를 잡거나(Day 7), 오프라인 tarball을 받아 `ansible-galaxy collection install ./community-docker-*.tar.gz`로 설치합니다.
    - `the connection plugin 'docker' was not found` → 인벤토리의 `ansible_connection` 값을 `community.docker.docker`로 바꾸세요.
